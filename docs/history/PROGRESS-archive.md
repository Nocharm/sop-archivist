- **계획 1 Task 10: 문장 검사(숫자·단위·부정)** — 순수 `app/sop/checks.py` `check_sentence(출처들, 새 문장)`가 `number_mismatch`·`unit_mismatch`·`negation_mismatch`를 값 토큰만 담아 돌려준다. 단위는 숫자 바로 뒤(공백·하이픈 허용)만 세고 라틴 단위 뒤 라틴 글자는 다른 낱말이라 `분리`·`Label`이 걸리지 않는다. 출처가 여럿이면 숫자는 다중집합 합집합(max)이라 한/영 짝 출처의 같은 숫자를 두 번 세지 않는다. 부정 사전은 `불가피`·`No. 5`를 부정으로 보지 않는다.

- **계획 1 Task 11: 관계 묶음 저장·일괄 처분·배정 지우기·떼어 내기** — 사람의 저장 단위는 연결 요소 전체라 서버가 닫힘(이어진 새 문장을 다 보냈는가, 출처가 다 보낸 단위 안인가)을 먼저 보고, 검사 11가지를 쓰기 전에 모두 끝내 낡은 revision 하나도 전체 409로 아무것도 바꾸지 않는다. 변경 종류는 구조(신규·합침·나눔)를 코드가 먼저 정하고, 글자가 원문과 같으면 `as_is`로 고정하며 다르면 `as_is`를 받지 않는다. 표 `as_is`는 원문 격자·칸 자리를 지키고(R27), 문장 새 문장은 문장·제목·칸 문장에서만 온다(R28). 상위 칸 N/A는 하위 칸 배정도 막는다(R8). 떼어 내기(`detach.py`)는 배정 지우기·문서 삭제(확인 플래그, 새 문서는 입구 2 새 문장도)·쪼개기 편집이 함께 쓰고, 묶음 ID·표 접기는 `groups.py` 하나(결과물도 쓴다). 큰 표·문서에서 IN 목록이 asyncpg 인자 상한을 넘지 않게 5,000개씩 나눠 읽는다. 일회용 postgres 16에서도 새 테스트가 통과했다.

- **계획 1 Task 12: 입구 2 새 문장·같은 글자 후보·한 번에 확정** — 새 문서를 올리면 업로드 트랜잭션 안에서 단위마다 미배정 `new_doc` 새 문장(원문 그대로, 절 경로 = 앞 제목 단계 스택, 머리말·꼬리말·제목 제외, 표는 표+칸 새 문장)을 만들고, 수동 짝 맞추기는 Task 11 관계 묶음 저장을 그대로 쓴다. 한 번에 확정은 코드가 확인할 수 있는 것만(같은 글자 1:1 → 그대로, 출처 없는 새 문장 → 신규) 묶음 잠금 아래 항목마다 다시 확인해 전부 아니면 무(422 `not_identical`·`not_new`)로 쓴다. 칸 문장·칸 새 문장은 표와 한 관계 묶음이라 1:1 후보에서 빼고(같은 글자 수에는 세어 모호하면 빠진다), 신규로 표를 확정하려면 칸을 모두 함께 담아야 한다. 편집 뒤 맞추기는 `sync_new_doc_targets`(Task 13).

- **계획 2 Task 2: AI 호출 경계** — 임베딩은 채팅과 서버·모델이 달라 `EMBED_*`를 따로 두되 동시성 세마포어는 `call_ai`와 공유한다(동시 상한이 전체 AI 부하 기준이라서). 느린 AI 호출 동안 DB 연결을 잡지 않으려고 `call_ai_recorded`에서 세션 인자를 없애고 `record_ai_usage`가 호출 뒤 자기 짧은 세션으로 기록한다. `ping_ai`는 권한 판정이 잡은 요청 세션을 호출 직전에 닫는다.
- 실패 기록이 실패해도 원래 AI 오류를 가리지 않는 동작은 그대로이고, 그 경고 로그는 트레이스백 대신 예외 클래스 이름만 남긴다(값이 로그에 실리지 않게).
- **계획 2 Task 3: 스키마 0007** — AI 작업·제안·지침·임베딩 표 4개와 판단·새 문장·짝의 `suggestion_id`(제안이 지워져도 행은 남는 SET NULL), 번역 출처 칸 `translation_source_unit_id`(`TargetSource`와 따로, 단위가 지워지면 CASCADE)를 더했다. 지침의 "키당 활성 하나"는 부분 유일 인덱스라 sqlite·Postgres 방언 인자를 둘 다 달았고, sqlite는 길이를 강제하지 않아 코드 값 튜플이 컬럼 길이에 들어가는지를 테스트로 묶었다.
- `ai_suggestions`의 CHECK 둘은 `result`·`adoption`(`kind`는 작업 쪽 CHECK가 막는다). 마이그레이션은 일회용 Postgres 16에서 upgrade·downgrade·`alembic check`와 제약·CASCADE 동작을 실측했다.
- 묶음을 지우면 제안 행마다 SET NULL이 `suggestion_id` 3곳(판단·새 문장·짝)과 `ai_jobs.document_id`를 찾으므로, 프로젝트의 "CASCADE·SET NULL이 닿는 FK는 인덱스" 관례대로 네 곳에 인덱스를 달았다(표 전체 순차 스캔 방지).
- **계획 2 Task 4: 지침·프롬프트 버전** — 규칙 문서와 프롬프트 4종은 `app/sop/ai/seeds/`에 둔다(도커 이미지가 `app/`만 복사). `rules.md`는 도메인 문서의 바이트 복사본이라 테스트가 같음을 지키고, 기동 때 버전이 없는 키만 v1 활성으로 시드한다. `prompt.pair`는 일부러 없다(한/영 짝은 임베딩과 사람). Excel 정보 시트의 지침 버전은 `"-"` 대신 활성 규칙 버전(`rules v1`)이다.
- 새 버전 번호를 `max+1`로 셀 때 "그 키의 모든 행을 FOR UPDATE로 읽기"는 막아 주지 못했다(일회용 Postgres 16에서 동시 생성 6건 중 UNIQUE 위반): 기다리던 쪽은 앞선 쪽이 새로 넣은 행을 못 본다. 그래서 키의 가장 오래된 행 하나를 뮤텍스로 잠근 뒤 번호를 따로 읽고, 활성화는 이전 활성을 먼저 끄는 벌크 UPDATE로 순서를 고정한다(부분 유일 인덱스).
- **계획 2 Task 4 수정: 지침 버전 경로 범위** — `version` 경로 값에 하한 1·Postgres INTEGER 상한을 걸었다(기존 `IdPath` 관례). 상한 밖 값은 sqlite에선 404지만 Postgres에선 비교 중 500이 되는데 sqlite 테스트는 이를 못 본다. 권한 의존성이 먼저라 권한 없는 사람은 여전히 403이다.
- **계획 2 Task 5: 작업 실행기와 진행 API** — 뒤따르는 모든 AI 작업이 얹히는 틀이다. 상태 전이는 `running`인 행에만 걸어 그사이 온 취소가 실패·낡음으로 덮이지 않고, 워커가 종료로 끊은 작업은 `running`으로 남겨 재시작이 회수한다(세 번째로 끊기면 `failed`/`interrupted`).
- 적용 단계는 설계의 `lock_bundle` 대신 `session.get(with_for_update=True)`로 읽기와 잠금을 한 문장으로 했다(`ingest`와 같은 방식). 일회용 Postgres 16에서 잠금을 기다리는 동안 묶음이 지워지면 `lock_bundle`의 refresh가 `InvalidRequestError`를 내는 것을 확인했고, sqlite는 행 잠금이 없어 테스트로 보이지 않는다.
- `scope_required`는 다른 AI 거절과 같이 `detail.code`로 읽히도록 업무 규칙 거절로 내고, 범위 목록 상한은 넘친 단위가 422가 아니라 `limit_reached`로 돌아가게 작업 상한보다 크게 뒀다. 묶음 목록(`BundleListItem`)은 `build_bundle_out`을 타지 않고 계약도 `BundleOut`뿐이라 `ai_jobs`를 더하지 않았다.
- **계획 2 Task 5 수정: 핸들러 import 실패** — `process_job` 안의 지연 import가 `try` 밖이라 핸들러 모듈이 깨지면 예외가 태스크로 새어 작업이 `running`에 갇혔다. import를 `try` 안으로 옮겨 그 작업의 `failed`/`internal`로 끝낸다.
- **계획 2 Task 6: 임베딩 캐시와 유사도** — 임베딩 호출의 모든 실패(HTTP·망가진 본문·NaN·영벡터)를 재시도 뒤 `EmbeddingUnavailable("failed")` 하나로 모아 Task 8이 `reason`(`disabled`/`failed`)으로 검색 상태를 가른다. 캐시는 배치마다 써서 뒤 배치가 실패해도 앞 배치가 남고, 쓰기는 dialect별 `on_conflict_do_nothing`이라 같은 글의 동시 삽입이 충돌하지 않는다(일회용 Postgres 16에서도 확인). 테스트 conftest에 `EMBED_ENABLED=false`를 고정했다(켜져 있으면 lifespan 워커가 `run_jobs()`와 겨룬다).
- **계획 2 Task 6 수정: 캐시 조회 나눠 읽기** — 캐시 읽기가 글 해시 전부를 한 `IN (...)`에 실어 asyncpg 바인드 상한(32767)을 넘으면 `EmbeddingUnavailable`이 아닌 DB 오류로 작업 전체가 내부 실패가 됐다. 저장소 규칙대로 `select_in_chunks`(`IN_CHUNK_SIZE`)로 나눠 읽고, 이 함수의 타입은 정수 id와 문자열 해시를 함께 받게 `ChunkKey`로 넓혔다(동작 불변).
- **계획 2 Task 7: LLM 경계와 맥락** — 원문은 시스템 메시지가 아니라 사용자 메시지의 nonce 구분 줄 사이 JSON 한 줄로만 간다(줄바꿈이 이스케이프라 원문이 닫는 줄을 흉내 낼 수 없다). 프롬프트 시드가 모델에게 알리는 표지(`<<<DATA {nonce}>>>`)와 코드가 내보내는 표지가 갈라지지 않게 테스트로 묶었다. 재시도 대상은 시간 초과·5xx·연결 오류에 깨진 본문까지(`server_error`)이고, 본문이 객체가 아닐 때 나는 `AttributeError`도 여기 넣었다(브리프는 네 예외만 적었다). 설정 오류는 호출 전에 `config`로 가려 사용량 행을 남기지 않는다.
- `load_unit_context`는 질의 5번 고정(단위·순서·이웃 글·첫 블록 절·표 칸)이다. 이웃은 순서 열만 읽어 두고 뽑힌 단위의 글만 가져오며, 표 단위의 이웃에서는 자기 칸 문장을 뺀다(표 Markdown이 이미 싣는다). 표 행 단위도 전체 표를 싣는다(큰 표를 행마다 보내면 프롬프트가 커지는 비용은 Task 8에서 보고 정한다). 일회용 Postgres 16에서 질의 수와 조각 읽기를 확인했다.
- **계획 2 Task 7 수정: 깨진 응답 분류·표 맥락 크기** — UTF-8이 아닌 200 본문(`UnicodeDecodeError`)과 글이 아닌 `content`(목록·숫자)가 분류를 건너뛰어 재시도 없이 `internal`로 끝나거나 `parse_reply`에서 터졌다. 둘 다 깨진 본문으로 보고 `server_error`로 재시도한다. 표 맥락은 칸 번호(DOCX `gridBefore`·`gridSpan`에서 옴)로 격자를 만들던 탓에 조작한 파일의 칸 하나가 메모리를 채울 수 있었다. 실제로 칸이 있는 행·열만 남겨 압축하고 앞쪽 200행·50열·2만 자로 자르며, 표 하나는 호출마다 한 번만 그린다.
- **계획 2 Task 8: To-Be 칸 후보 추리기** — 임베딩이 꺼진 것(`no_index`)과 호출이 끝내 실패한 것(`embedding_failed`)은 같은 글자 유사도 폴백이어도 다른 `retrieval` 상태로 남겨 Task 9·화면이 둘을 구분한다. 하위 칸 라벨은 도메인 문서가 "넣는 것"을 비워 둔 칸이라 이름 앞에 상위 칸을 붙여(`Procedures > Troubleshooting`) 라벨만으로 어느 칸인지 보이게 했다. 후보 키는 문서 순서 열 순으로 `c1`부터 매겨 같은 입력이면 같은 키다.
- **계획 2 Task 8 수정: 제목 없는 문서 라벨** — `TargetDoc.title`은 비어 있을 수 있고 문서를 가르는 값은 번호뿐이라, 빈 제목 문서 둘이 같은 라벨(` / Purpose: …`)을 내고 WI 머리가 `()`가 됐다. SOP·WI·부모 모두 `title or code`로 쓴다(Excel 내보내기와 같은 폴백).
- **계획 2 Task 9: 분류와 고쳐 쓰기** — 첫 실제 작업 핸들러다. 낡음은 판단 revision에 글자·언어 해시를 더해 본다(언어 고치기는 판단 revision을 안 올리는데 언어별 고쳐 쓰기를 어긋나게 한다). 고른 자리는 적용 때 `list_candidates`를 다시 돌려 확인해 N/A·단계 삭제·입구 변경을 한 규칙으로 잡고, 표·행·그림은 자리만 고른다(글자는 그대로).
- 제안 하나가 짝을 덮으므로 일부 단위만 다시 받아도 제안을 통째로 걷는다(남기면 새 문장 없는 `ai_suggested` 판단이 생긴다). `GroupTargetOut.suggestion_id`는 계획상 Task 10 몫이지만 이 작업의 시험이 읽어 먼저 더했고, `fake_ai` 픽스처는 시험 인자로 쓰면 import가 F811이라 `conftest.py`에 뒀다. 일회용 Postgres 16에서 적용·교체·표·무효 경로를 IN 조각 2로 돌려 확인했다.
- **계획 2 Task 9 수정: 검토 판정 반영** — 문서 범위는 미배정만 받는다. 끝난 앞쪽을 다시 받으면 작업 상한을 넘는 문서의 뒤쪽이 영영 처리되지 않아서다(§7.8). 고른 단위는 AI가 쓸 수 있는 짝을 함께 보낸다(§7.8 "대상 단위(와 짝)", 제안은 확정이 아니라 §7.7의 "담긴 것만"과 부딪치지 않는다). 제안 기록에 고쳐 쓴 문장을 남겨(§6.11) 밀린 뒤에도 글이 사라지지 않게 했고, AI 경고는 Excel이 읽는 `check_sentence` 모양으로 맞췄다. 사람이 정한 짝을 지키는 상태 조건 두 개에 시험을 달았다.
- **계획 2 Task F1: 프런트 1차 요청 세 건** — 보낼 곳 없는 보류가 `POST /groups/save`에서 `assigned_without_targets`로 막혀 있어(§6.8 미배정 → 보류, 쪼개기 `H`) `UnitDecisionIn.disposition`에 `unassigned`를 더하고 보류 저장에서만 새 문장 없이 받는다(확정이면 `hold_required`). 그 상태는 시스템 보류 `hold_invalid`와 같은 모양이라 배정 지우기·검토 조건(`units_on_hold`)·결과물 A·AI 대상 고르기는 고칠 것 없이 시험으로 묶었고, `list_identical_candidates`는 이미 상태까지 걸러 같은 시험으로 닫았다.
- `GET /api/bundles` 항목에 `is_synthetic`, `/units` 행에 `pair_id`(`/documents/{id}/view`와 같은 뜻, `select_in_chunks`로 질의 하나)를 더했다. 목록 키 집합을 고정하던 기존 단언(`test_list_shows_only_my_bundles_with_my_role`)에 `is_synthetic`을 넣었다.
- **계획 2 Task 10: 사람 확정과 채택 기록** — 판정은 제안 기록(`content`)을 이 저장에 담긴 단위 몫만 꺼내 견주고(짝이 제안 하나를 나눠 쓴다) 먼저 정한 판정이 남는다. 채택이 기록된 제안은 짝 다른 쪽을 다시 받아도 `stale`로 바꾸지 않고, 보류만 한 쪽은 밀린 뒤 확정해도 채택률에 들게 `as_is`·`edited`·`rejected`는 결과와 무관하게 센다. `pending`은 사람이 아직 정할 수 있는 제안만이다 — 편집으로 은퇴해 아무 판단·새 문장도 가리키지 않는 제안을 세면 대기가 영영 줄지 않는다(그 제안은 `applied`에는 남는다).
- 브리프 밖 하나: 보류한 제안 단위는 일괄 처분을 지날 수 있어(`dispose_units`의 409는 `ai_suggested`만) 거기서도 채택을 남긴다. 표·칸은 제안 기록에 글이 없어 원문 그대로를 제안 모습으로 본다. `test_person_owned_mate_survives_reclassify_of_other_side`의 결과 단언은 확정이면 `applied`로 바꿨다(결정 이월). 일회용 Postgres 16에서 IN 조각 2로 채택·분류 시험을 돌렸다.
- **계획 2 Task 10 수정: 표 구성 변경·사람 변경 종류** — 칸 글이 같은 표를 다른 격자로 저장해도 `as_is`가 됐고 첫 판정이 남아 고칠 길이 없었다. 표의 "그대로"는 격자·칸 자리까지 같을 때뿐이라(§6.7) `table_restructured` 저장은 `edited`다. `text`를 비운 변경 종류 이어받기는 AI 글이 있는 행에만 둔다 — 사람이 쓴 새 문장은 출처를 바꾸고 비워 보내면 예전처럼 `change_type_required`다(§6.7 사람이 고른다).
- **계획 2 Task 11: 번역 제안·결과물 번역 줄** — 번역은 출처 연결 없이 `translation_source_unit_id`로만 단위를 가리켜 관계 묶음·닫힘·커버 숫자를 흔들지 않고(칸 번역만 부모로 그 표에 묶인다), 자리는 출처 새 문장에 잠근다(사람은 글만 고치고, 비운 자리는 지금 값). 번역 행에 출처 새 문장 칸이 없어 "같은 번역"은 제안 기록의 `source_target_id`로 가린다 — 단위·언어만 보면 나눔의 둘째 작업이 첫 조각의 번역을 밀어낸다. 합친 새 문장은 어느 출처로 물어도 번역이 하나다.
- 떼어 내기와 AI 재분류가 출처를 지우면 AI 번역은 지우고 사람이 정한 번역은 보류한다(§7.5). 표가 지워질 때 칸 번역이 CASCADE로 조용히 사라지지 않게 표에서 떼어 남기고, 은퇴한 단위의 보류 번역은 결과물 A 끝에 위치 없이 보인다. 제안 기록에는 계약의 네 칸에 `text`를 더했다(§6.11, 밀린 뒤에도 글이 남게 — Task 9 `rewrites`와 같은 이유). 일회용 Postgres 16에서 IN 조각 2로 번역·채택·분류·판단·입구 2·결과물 시험을 돌렸다.
- **계획 2 Task 11 수정: 출처가 바뀌면 번역 다시 보게 하기** — 번역은 단위만 가리켜서, 사람이 출처를 지우거나(배정→삭제) 합친 새 문장의 다른 출처를 떼거나 입구 2 새 단위가 은퇴해도 `confirmed`로 남아 옛 글의 번역이 결과물로 나갔다. 찾는 열쇠를 출처 새 문장(제안 기록 `source_target_id`)으로 바꾼 `sweep_translations` 하나로 모았다(AI 번역은 지우고 제안 `stale`, 사람이 정한 번역은 보류). 저장의 지운 출처와 글·자리가 바뀐 출처(같은 저장에 담긴 번역은 빼고, AI 글 그대로 확정은 변경이 아니다), `detach_units`, `PUT /targets/order`의 단계 변경, 입구 2 다시 맞추기의 자리 변경이 부른다.
- 번역 줄의 단계 변경은 `PUT /targets/order`도 `translation_locked`로 막아 잠금이 모든 쓰기 길에서 같다. 이전 번역은 출처 새 문장이 없어진 것까지 보고, 확정·보류 확인은 합친 새 문장도 새 문장 기준으로 본다. 무효 응답은 이제 이전 AI 번역을 지우지 않는다(분류와 달리 보류가 없어 쓸 수 있는 글만 잃는다). 일회용 Postgres 16에서 IN 조각 2로 JSON 경로 질의를 확인했다.
- **계획 2 Task 11 수정 2: 보류된 번역이 출처를 따라감** — 번역의 자리는 출처와 같아야 하고(§7.9) 잠겨 있어서, 출처가 옮겨 간 뒤 옛 자리에 보류해 두면 사람이 고친 번역을 지우는 수밖에 없었다. `sweep_translations`가 남기는 번역을 출처 자리(문서·칸·단계·부분·절 경로)로 옮기고, 같은 저장에 담겨 보류되지 않는 번역도 같은 이유로 옮긴다. 출처가 없어졌으면 자리는 그대로다.
- **계획 2 Task 11 수정 3: 표 칸 번역 규칙 마무리** — 표 저장은 닫힘 때문에 칸 번역을 늘 담아서, 같은 저장에 담겼다는 것을 면제로 보면 칸 글을 고쳐도 옛 번역이 확정으로 남았다. 면제는 그 저장이 번역 글을 고쳤을 때뿐이고, 되보낸 번역은 아예 쓰지 않고 쓸어 낸다(쓰면 AI 번역이 확정이 되고 채택이 남는다). 자리 잠금은 출처의 저장 뒤 자리도 받아 표를 통째로 옮기는 저장이 통과하고, 끝자리는 늘 출처의 자리다. 트리거에 칸 좌표·부모·출처 단위 집합을 더했고 번역은 좌표·부모까지 따른다. 재분류 쓸기는 다시 지우기 전으로 옮겼다(표와 함께 CASCADE로 사라진 AI 번역의 제안이 `applied`로 남았다).
- **계획 2 Task 12: 입구 2 짝 계획** — 계획 작업은 LLM을 부르지 않고 묶음 전체를 한 번에 묶는다. 문장 그룹만 `match` 작업으로 쌓고 표·그림·남은 항목은 바로 제안을 쓰는데, 작업이 `match_plan`이어도 제안 종류는 `match`이고 문서는 그 항목의 것이라 같은 종류 규칙·화면·문서 거르기가 한 벌로 돈다. 낡음은 항목마다 봐서 바뀐 행이 든 그룹만 건너뛰고, revision이 못 보는 언어 고치기가 같은 언어 규칙을 깨지 않게 적용 때 글·언어까지 견준다. 빈 글은 임베딩에 보내지 않는다(서버가 거절하면 묶음 전체가 임베딩을 잃는다).
- 다시 돌리기가 입구 2 새 문장을 지우면 새 문서의 글이 사라져, Task 13 몫이던 `clear_previous_suggestion`의 새 문장 처리를 여기서 고쳤다(출처를 떼고 미배정으로, 번역 쓸기도 탄다). 판단 없는 신규 제안도 걷게 `targets`를 받는다. 브리프 밖 결정 둘: 격자가 같아도 옛 칸 문장이 남으면 그대로로 저장할 수 없어(`table_cells_missing`) 표 구성 변경으로 제안하고, 묶음 전체 요청의 `already_queued`는 가리킬 단위가 없어 `unit_id: 0`으로 낸다. 일회용 Postgres 16에서 IN 조각 2로 계획·분류·번역·채택 시험을 돌렸다.
- **계획 2 Task 12 수정: 반복 글자·글자 없는 단위** — 같은 문장이 되풀이되면 점수가 모두 같아 N:M이 되고, 한쪽으로 줄이면 거짓 나눔과 거짓 삭제 후보가 나왔다(§13 "같은 문장 반복"). 글이 똑같은 항목을 먼저 id 순으로 1:1로 잇고 그 행·열을 지워 남는 항목이 다시 붙지 못하게 했다. 이 짝은 한 번에 확정이 아니라 변경 종류 작업으로 간다. 표·그림은 서로 최고인 간선만 쓰면 문장 경로가 지키는 쌍을 잃어서, 같은 별을 만든 뒤 별마다 가장 높은 쌍만 남긴다.
- 캡션 없는 그림처럼 글자가 없는 단위는 비교할 수 없어(§7.10 사람이 손으로) `load`에서 빼고, 그래서 삭제 후보·신규가 되지 않고 임베딩에도 가지 않는다. 표 칸 숫자 경고는 제안 행에도 실어 `SuggestionOut.warnings`로 읽히고, 계획이 쓴 표·그림·삭제 제안이 `POST /groups/save`로 확정되는 것을 시험으로 묶었다.
- **계획 2 Task 13: 입구 2 변경 종류 제안** — 문장 그룹마다 LLM에 변경 종류만 묻고 새 문장 글은 그대로 둔 채 출처만 잇는다. 나눔·합침과 같은 글자가 응답보다 먼저라 분류의 `decide_ai_change_type`을 그대로 쓰고, 그룹은 한 덩어리라 한 행만 바뀌어도 통째로 `stale`이다.
- 채택은 새 문장의 글·자리가 잠겨 있어 출처만 견준다(같으면 그대로, 모두 비면 버림, 그 밖은 고침). 사람이 출처를 바꾸면 옛 단위 처분도 따라 바뀌어 처분 검사를 빼고 제안의 새 문장으로 범위를 잡는다. 삭제 후보는 처분만 보고, 판단 행이 없는 신규는 새 문장에서 찾으며 지울 때는 `reset_target` 전에 버림을 남긴다. 제안 기록에 칸 연결이 없어 표는 표 새 문장만 견준다.
- **계획 2 Task 13 수정: 문서 걸친 짝과 제안 종류 채택** — 나눔은 같은 새 문서 안에서만이라(§6.7, §6.9) 문서에 걸친 1:N은 모습만 `split`이고 종류는 새 문장마다 그 문서 안의 수로 정한다. 짝 하나와 표는 LLM·코드가 낸 것이 종류뿐이라 종류만 고쳐도 `edited`로 세어 채택률이 지침을 고치는 근거가 되게 했다.
- 글과 종류를 비워 보내면 두 입구 모두 제안을 받는다. 입구 2는 `ai_text`가 없어 제안이 있고 출처가 그대로일 때만 받고, 손으로 맞춘 짝과 출처를 바꾼 저장은 여전히 422다. 계획 뒤 언어를 고치면 revision이 그대로라 `load`에서 언어가 갈린 그룹을 낡음으로 끝내고, 시드는 띄어쓰기만 다른 짝을 `tone`으로 옮겼다(글이 다르면 그대로일 수 없다).
- **계획 2 Task 14: 한/영 따로 짝 제안** — 임베딩만 쓰는 작업이라 LLM·지침이 없고, `POST /pair`는 `require_ai_enabled` 대신 임베딩 관문(409 `embedding_disabled`)을 건다(채팅이 꺼져 있어도 돈다). 문서 하나에 작업 하나로, 짝 없는 활성 한글·영어 글자 단위(표·행에 묶인 칸 문장은 코드 짝처럼 제외)를 서로 최고이고 `PAIR_THRESHOLD` 이상인 1:1만 `suggested`·출처 `ai` 짝으로 쓴다. 낡음은 쌍마다 봐서 호출 중 짝이 생기거나 은퇴하거나 언어가 바뀐 단위가 든 쌍만 건너뛰고, 배치가 바뀌거나 문서가 지워졌으면 작업이 `stale`이다.
- `confirm_pair`는 `as_is`, `delete_pair`는 `rejected`를 남기되 짝 행을 지우기 전에 쓴다(지운 뒤엔 `suggestion_id`로 제안을 찾을 길이 없다). `can_decide`에 `UnitPair.suggestion_id`를 더해 `pair` 제안도 `pending`에 잡힌다. 브리프 밖 결정: 임베딩이 꺼진 채 시작한 작업은 `config`, 호출 실패는 `connection`으로 끝내고, AI가 짝을 써도 문서 revision은 올리지 않으며(제안이라 열어 둔 화면의 저장을 막지 않는다).
- **계획 2 Task 14 수정: 바뀐 AI 짝 채택·같은 부분 안의 짝** — 사람이 `create_pair`로 AI 제안 짝을 대신하면 제안이 채택 없이 `pending`에서 빠졌다. 지우기 전에 짝의 단위 집합이 새 짝과 같으면 `as_is`, 다르면 `rejected`를 남긴다(코드 짝·이미 채택된 제안은 그대로). AI 후보는 본문 문장이 머리말·꼬리말·각주의 다른 언어 문장과 짝지어질 수 있어, 점수 행렬에서 부분이 다른 칸을 -inf로 가려 같은 부분의 최고만 쓰게 했다(표 경계는 넘는다 — 한글 표와 영어 표가 짝인 배치).
- **계획 2 Task 15: 복합 문장 나누기 제안** — 제안은 나눌 글자 위치(`offsets`)만 기록하고 단위·판단·새 문장은 건드리지 않는다(나누기는 사람이 `SplitOp`으로, 그래서 무효 응답도 분류와 달리 보류하지 않는다). 응답 조각이 원문을 빈 글자만 빼고 순서대로 그대로 덮을 때만 위치로 바꾸고(`find_split_offsets`, 아니면 `parts_mismatch`로 무효·응답 글 미보관), 조각 하나가 문장 전체면 제안을 쓰지 않는다. 낡음은 판단 revision에 글자 해시를 더해 보며(언어 고치기는 위치와 무관해 낡음이 아니다), 위치는 늘 보이는 글자 위라 두 블록에 걸친 단위의 줄바꿈 이음 글자 위에 놓이지 않는다.
- `POST /split`의 문서 범위는 묶이지 않은 문장·칸 문장 중 미배정만 받고, 열린 나누기 제안이 있으면 `already_suggested`, `MIN_SPLIT_CHARS`보다 짧으면 `too_short`다(고른 단위는 둘 다 없이 다시 물을 수 있고, 제목·표·묶인 칸은 문서 범위에서 알리지 않으며 고른 단위면 묶인 칸은 `bound_cell`, 제목·그림·표는 요청 전체를 막지 않고 `not_splittable`로 단위마다 건너뛴다). `POST /suggestions/{id}/adoption`은 적용된 나누기 제안의 채택을 한 번만 받고(다른 종류·이미 채택·낡음·무효는 409 `not_manual_adoption`) 작업 기록은 남기지 않으며(누가·언제는 제안 행), 이어진 행이 없는 나누기 제안은 채택이 비어 있는 동안 `pending`이다.
- 새 답(나누라는 답도 나누지 말라는 답도)이 오면 같은 단위의 열린 이전 제안을 `stale`로 내린다(묶음 잠금 안, 문서의 열린 제안을 읽어 `content.unit_id`를 파이썬에서 거른다). 채택이 있는 제안은 `applied` 그대로고, 무효·낡은 새 답은 이전 제안을 내리지 못한다. 일회용 Postgres 16에서 IN 조각 2로 나누기·채택·짝 시험을 돌렸다(이 수정 전 구현 기준).
- **계획 2 Task 16: 가짜 AI로 두 입구 끝까지·데모 AI 단계** — `SyntheticAnswers`는 응답 하나에 담을 수 있는 답만 정답으로 주고(한 자리, 같은 언어, 짝이면 자리와 변경 종류까지 같을 때) 합침·중복 배정·표·외부 이동은 무효로 돌려 보류 → 사람 경로를 타게 한다. 임베딩은 정답끼리 같은 벡터를 줘 상위 3개 후보와 입구 2 계획이 정답을 고르게 할 뿐 유사도 값에는 뜻이 없다. 드라이버는 일괄 삭제를 AI 앞에 두고(`ai_suggested_units`) 제안을 글·종류를 비운 `POST /groups/save`로 받으며, 대기 0이 사람의 확정에서 나왔는지는 받은 수 = 채택 `as_is` 합으로 묶었다.
- 데모 단계 4는 `fake_ai_session()` 안에서만 돌고 시드는 lifespan 워커를 끈다: 로컬 `.env`가 AI를 켠 채면 워커가 `run_jobs_until_idle`과 작업을 다투고 남은 작업이 가짜 전송이 풀린 뒤 실제 주소로 나간다. `reset_db`가 지침을 시드한다(비면 떠 있는 백엔드의 `export.xlsx`가 재시작 전까지 500). Node 가짜 서버에 task별 응답과 `/v1/embeddings`를 더했다. 시험과 손 확인 모두 합성이고 실제 모델 연결이 아니다.
- **계획 2 Task 17: 문서·버전 v0.3.0** — 구현 중 판단 약 70건 가운데 동작이 바뀐 것을 설계 문서의 해당 절에 한 줄씩 "(계획 2에서 정함)"으로 옮겼다(§6.10 `prompt.pair` 없음, §6.11 작업 종류 `match_plan`·종류별 채택, §7.5 번역 쓸어 내기, §7.7 일괄 거절·제안 받기, §7.8~7.11, §8.2~8.3, §14 프런트 병행). `CLAUDE.md`는 `app/sop/ai/` 구조와 `load/compute/apply`·합성 임계값·번역 쓸어 내기를 불변식으로 더했고, `setup-once.md`에 `EMBED_*`를 더했다.

- **계획 2 Task 17 수정: v0.3.0 문서를 코드에 맞게 정정** — 검토에서 문서가 코드보다 단정적인 곳 다섯 군데를 고쳤다: 새 제안이 이전 제안을 `stale`로 내려도 채택이 남은 제안은 `applied` 그대로, 검토 요청은 실행기가 작업을 `cancelled`로 끝내고(`stale` 아님), 번역 자리 잠금의 오류 모양은 저장 경로와 순서 바꾸기가 다르며, 말투 판정은 지침 시드와 코드 보정의 합이다. 문서만 고쳤고 코드·버전은 그대로다.
- **계획 2 최종 검토 수정: 표 칸 번역·AI 끄기** — 표가 보류돼도 자기 출처가 그대로인 AI 번역은 일반 보류에서 뺐다(확정 글이 빈 보류가 결과물 C에 빈 줄로 나가고 `already_translated`로 다시 번역도 막았다). 저장 쪽은 닫힘·`_is_echoed`·`_resolve_text`가 이미 다뤄 고치지 않았다. `call_llm` 맨 앞에서 AI 꺼짐을 `config`로 막아, 임베딩만 켜진 워커가 재시작 복구·다시 시도 작업의 원문을 `AI_BASE_URL`로 보내던 길을 닫았다.
- **계획 2 최종 검토 수정: 글자 유사도 속도** — 2-gram을 항목마다 한 번만 세어 재사용하고 겹침은 키 교집합으로 구해, 합성 글 1000×1000이 20초에서 1.6초, 3000×3000이 14초가 됐다(앞 50자가 같은 최악에 가까운 글은 59초). 값은 `text_similarity` 정의 그대로이고 프로세스 풀은 넣지 않았다.
- **계획 2 최종 검토 수정: 임베딩 4xx·unit_not_found** — 임베딩도 채팅과 같은 기준으로 4xx는 재시도 없이 바로 `failed`다(5xx·시간 초과·깨진 응답은 그대로 재시도). AI 요청 세 곳의 `unit_not_found`는 `ensure_units_found` 하나로 모아 id를 `MAX_SKIPPED_REPORTED`까지 싣고 `missing_total`을 더했다(필드 추가라 프런트 병행 작업과 어긋나지 않는다).
- **계획 2 최종 검토 수정: 끝낼 수 없는 작업은 아무것도 보내지 않기** — `call_llm` 관문만으로는 분류가 후보 추리기 임베딩을 먼저 보내고, 다시 시도한 `match_plan`은 묶음 전체를 임베딩한 뒤 모두 실패할 작업을 쌓았다. `ensure_llm_enabled`를 두 `compute` 맨 앞에도 둬 임베딩 호출도 없이 `config`로 끝낸다. 임베딩만 쓰는 `pair`는 그대로 돈다.
- **v0.3.0 최종 검토 마감** — 브랜치 전체 검토 뒤 지적 수정분까지 재검토했다. sqlite 1879개 통과, 임시 Postgres 16은 1870개 통과에 시험 환경 때문에 실패한 8개뿐이다. 합성 검증이고 실제 모델은 아직 시험하지 않았다.
