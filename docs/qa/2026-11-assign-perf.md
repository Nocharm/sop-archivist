# Assign 반응 시간 — 명령 큐 · 필터 덩어리 앞뒤 (2026-11-26)

쪼개기 먼저 패치의 반응속도 스텝(설계 `docs/architecture/decisions.md`의 `## 2026-11-25-split-first` 6-1절)의 실측이다. 같은 기계에서 같은 시드로 앞뒤를 쟀다.

## 어떻게 쟀나

- `frontend/scripts/pw-perf-assign.mjs`(`SCENARIO` · `REPEAT` · `CPU`), 로컬 운영 빌드(`next build` → `next start`) + sqlite, localhost가 아닌 LAN 주소(`<lan-ip>`), 창 1440.
- 자료는 `seed_sop_worst`의 합성 문서 — 큰 문서 289박스(문장 207 미배정), 작은 문서 시연 묶음 첫 문서. 시나리오마다 DB를 시드로 되돌렸다. 글쇠마다 6번, 표의 값은 가운데 값(ms)이다.
- 값은 글쇠를 누른 때부터 고름이 다음 박스로 옮겨질 때까지다. 재는 동안 다른 작업이 CPU를 나눠 써서 절대값은 어림이고, 앞뒤의 차이를 본다.
- 단계 이름 — **전**: v1.6.7(3a까지) / **큐 뒤**: `fix/assign-command-queue`(3b) / **덩어리 뒤**: `fix/assign-instant-motion`(3c) + `perf/assign-filter-chunks`(3d).

## 원인별 몫

- 저장 응답(서버 `POST groups/save` TTFB 66~133ms)과 그 뒤 다시 읽기를 기다리던 것이 거의 전부였다 — 큐 뒤에는 누르는 즉시 옮긴다. 서버 로그는 `app.timing` 로거의 `group save timed`(JSON 한 줄, 원문 · 이름 없음).
- 필터를 켰을 때 남던 몫은 용지 덩어리를 나누지 않던 것 — 접힌 목록도 덩어리로, 덩어리는 제 안의 값이 바뀔 때만 다시 그린다.
- 필터를 켠 채 위로 굴릴 때 보던 줄이 튀지 않는다(250px씩 76번, 어긋남 최대 0px. 필터를 끈 채로도 93번 0px).

## 아직 남은 것

- 큐가 비어 모델을 다시 받을 때는 전과 같이 모든 덩어리를 한 번 다시 그린다.
- 문서 전체를 화면 밖에서 빼는 진짜 가상화는 목표를 이뤄 열지 않았다.
- 운영(postgres · 사내망)은 재지 않았다. 큐는 응답을 기다리지 않으므로 느린 망에서 차이가 더 크다.
