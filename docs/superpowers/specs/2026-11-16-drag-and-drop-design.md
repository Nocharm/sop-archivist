# 끌어다 놓기 설계 — 상자 전체 끌기 · Order · Assign 잇기와 보내기 · Pair view

2026-11-16. 사용자가 정한 것은 날짜와 함께, 내가 정한 것은 "내 판단"으로 적는다. 직접 끌어 보는 시안은 비공개 디자인 세션 산출물이라 저장소에 두지 않는다. 번호·이름 예시는 모두 지어낸 값이다. 조사 기준은 dev `794ed49`(v1.0.37)다. 1b걸음(Order 다른 칸으로)을 더한 고침의 조사 기준은 dev `19afc05`(v1.1.4)다.

같은 날 정한 세 설계 가운데 첫째다. **Documents 화면 고치기**(목록 두 줄 정리, WI를 SOP에 끌어 부모 정하기, 올리기 창의 Old/New 묶음, N/A 칸 상태 표)와 **참조 지도**는 따로 쓴다. 이 문서의 1번(끌기 층)을 둘째 설계가 그대로 쓴다.

## 1. 왜

- **Order**: 문장을 다섯 줄 올리려면 Move up을 다섯 번 누른다. 줄마다 단추 일곱 개가 늘 보이고, 글이 줄 폭을 채우면 단추 묶음이 글 아래로 내려가 줄마다 한 줄을 더 차지한다.
- **Assign**: Old 줄을 고르고, New 문장을 누르고, Confirm을 누른다. 아직 쓰지 않은 문서의 칸은 옆 패널의 나무를 펼쳐 찾고, 그 칸 안의 자리는 나중에 Order에서 따로 잡는다. New 칸에 보이는 빈 칸과 문장은 미리 보기라 누를 수 없다.
- **한/영 짝**: `ko_en_separate` 문서는 두 언어가 멀리 떨어져 있어 "Pair with another sentence…" → 스크롤 → 클릭 → Pair n의 다섯 걸음이고, 그동안 출발 문장이 화면에서 사라진다.

사용자 요청(2026-11-16): 끌어다 놓기를 쓰고, 사용성은 bpm을 참고한다.

## 2. 목표 · 비목표 · 반목표

**목표**

1. 공통 끌기 층 하나. 새 의존성 없이 포인터 이벤트로 만든다(bpm `plan-editor.tsx`와 같은 방식. 서버 빌드가 PyPI·npm만 받는 제약과 무관하게 늘릴 이유가 없다).
2. Order: 줄을 끌어 순서와 깊이를 바꾸고, 같은 New 문서의 다른 칸(WI는 다른 step)으로도 옮긴다(10절 1b걸음). 줄 끝 단추는 호버·포커스 때만 보인다.
3. Assign: Old 조각을 끌어 (가) 이미 쓴 문서의 문장에 **잇거나** (나) 아직 쓰지 않은 문서의 문장 사이·빈 칸·옆 패널의 칸에 문장째 **보낸다**.
4. Pair view: `ko_en_separate` 문서를 KO | EN 두 칸으로 펴고 끌어 짝을 맺는다(짝 없는 조각끼리, 그리고 제안 확정). 가까운 줄은 Pair view 없이 Old 칸 안에서 맞은편 언어 조각에 놓는다.

**비목표** (이번에 하지 않는다)

- Documents 화면의 끌기와 참조 지도(다른 설계).
- Order에서 줄을 **다른 New 문서**로 옮기기 — 문서를 바꾸는 일은 Assign에서 한다(1b걸음, 사용자 요청 2026-11-16의 범위는 같은 문서 안이다). 여러 줄을 Deleted/Moved 선반에 놓기, Unit 경계 옮기기(`move_boundary`), New 문서·WI step 순서.
- Shift로 고른 여러 줄을 한 번에 끌기. 1차는 한 줄(한/영 짝이면 그 짝 전체)만 끈다.
- 터치 화면의 끌기. 터치에서는 지금 경로(단추·메뉴)만 쓴다. 누른 채 움직이면 스크롤이어야 한다.
- 끌어서 합치기(Join). 같은 언어 조각에 놓는 것은 거절한다.
- 이미 짝인 조각에 끌어 더하기(1:2)와 다른 짝으로 옮기기, 짝 맺기를 Assign 되돌리기(Ctrl+Z)에 기록하기. 서버에 원자적 동작과 되돌리기 단계가 없다 — 필요해지면 따로 정한다(사용자 결정 2026-11-16).

**반목표** (되면 실패)

- 끌어 놓은 것이 Assign에서 곧바로 저장·확정이 된다. 놓는 것은 고르는 것까지다.
- AI 제안 여러 개를 한 번에 확정하는 길이 생긴다(제품 명세 §7.7).
- 지금의 클릭·단축키 경로가 하나라도 사라지거나 뜻이 달라진다.
- 끌기를 넣은 뒤 바깥을 눌러도 메뉴가 닫히지 않거나, 포커스가 옮겨 가지 않거나, 놓자마자 놓인 자리의 문장이 골라진다.
- Unit이 수천 개인 문서에서 끄는 동안 화면이 끊긴다.

## 3. 조사로 확인한 것

- **두 앱 모두 끌기 라이브러리가 없다.** frontend 의존성은 lucide-react·next·oidc-client-ts·react·react-dom·react-oidc-context뿐이다. 포인터 끌기는 이미 셋 있다 — 나누는 선(`components/paper/paper.tsx`, `components/assign/new-pane.tsx`), 두 문서 사이 세로선(`pane-divider.tsx`), Documents 화면 파일 놓기.
- **고르기는 지금도 뗄 때 일어난다.** Old 조각 고르기와 Shift 여러 줄은 `.pg`에 위임한 `onClick`(`paper.tsx` `handleClick`), New 문장 고르기는 줄 전체를 덮는 `button.new-hit`의 `onClick`이다. 두 번 눌러 나눌 자리 정하기도 `dblclick`이다. 상자 끌기와 부딪치지 않는다.
- **부딪치는 것은 글자 긁기 하나다.** Old 조각의 글자를 긁으면 `mouseup`에서 선택을 읽어 "New unit from selection" 띠가 뜬다(`paper.tsx` `handleMouseUp`). Order 줄의 글자도 지금은 긁힌다.
- **누를 때 움직이는 것들.** 메뉴·고르기 목록·EQUIS 창·AI 작업 창은 document `mousedown`으로 닫히고(`ui/menu.tsx`, `ui/combobox.tsx`, `equis/equis-status.tsx`, `ai-jobs-popover.tsx`), 그 자리 메뉴는 document `pointerdown`으로 닫힌다(`assign/link-menu.tsx`). Order 줄은 누를 때 네이티브 포커스를 받는다(`outputs/output-c.tsx`, 들일 수 있는 줄만 `tabIndex={-1}`). `pointerdown`에서 `preventDefault`를 부르면 뒤따르는 `mousedown`·`mouseup`이 사라져 이 모두가 깨지고 글자 긁기도 죽는다.
- **끈 뒤의 클릭을 삼키는 본보기**가 있다 — `new-pane.tsx`의 나누는 선 끌기가 `pointerup` 뒤 `click` 한 번을 capture로 삼킨다.
- **호버로 움직이는 것.** 조각 사이 틈은 300ms 머물면 벌어지고 Join 단추가 뜬다(`components.css` `--gap-open-delay`). 툴팁은 150ms(`ui/delegated-tip.tsx`), 이음 선과 짝 강조는 `pointerover`로 붙는다(`assign/link-lines.tsx`, `data-link-hover`·`data-mate-hover`).
- **Order 저장은 문서의 줄 전부를 새 순서로 보낸다** — `PUT /api/bundles/{id}/targets/order` `{revision, target_doc_id, items[]}`. 화면은 `lib/c-edit-model.ts`로 먼저 얹고 `lib/c-save-queue.ts`로 한 번에 하나씩 보낸다. 같은 칸 안에서만 움직인다(`lib/target-order.ts` `canMoveTarget` — 단추·글쇠는 지금도 그렇다. 끌기는 1b걸음부터 다른 칸으로도, 5절). **순서는 모든 줄이 바꿀 수 있다** — 줄마다 Move 단추가 있고(`outputs/output-c.tsx`) 서버 `reorder_targets`도 순서를 막지 않는다. 막히는 것은 깊이와 번호 표시다: AI 번역 줄(원문 줄의 칸·step·깊이에 묶인다, 422 `translation_locked`)과 이미 쓴 문서의 줄.
- **Assign 저장에는 "몇 번째 자리"가 없다.** `POST /api/bundles/{id}/groups/save`는 문서·칸·step까지 받는다. 새 문장의 순서는 문서가 `manual_order`가 아니면 출처 위치로 정렬되고, `manual_order`면 끝에 붙는다(`sop/decisions.py`). 번역을 출처 바로 뒤에 끼우는 `target_placement.insert_after`가 이미 있다.
- **이미 쓴 문서(entrance `match`)는 새 문장을 받지 않는다** — 422 `match_doc_new_target`. 잇기만 된다.
- **짝의 규칙은 서버와 화면에 나뉘어 있다.** 서버(`sop/pairs.py`): 한 문서 안에서만, 한쪽 최대 3개(`MAX_PAIR_SIDE`), 이미 확정 짝에 든 Unit은 다시 짝이 안 되고(409 `unit_already_paired`), 운명이 다르면 거절(409 `pair_fates_differ`). 화면(`lib/assign-context-menu-model.ts`): 배정을 결정한 Unit과 REF 줄은 짝 메뉴가 꺼진다 — 이 둘은 서버 거절 코드가 없다.
- **짝 맺기·풀기는 Assign 되돌리기 줄에 서지 않는다.** 짝 라우트(`routers/sop_documents.py`)는 되돌리기 단계를 기록하지 않는다. 짝에 Unit을 더하거나 다른 짝으로 옮기는 API도 없다(풀고 다시 맺어야 한다).
- **bpm에서 배운 것.** 4px 문턱으로 클릭과 끌기를 가른다. FLIP 변형 중에는 `getBoundingClientRect`가 어긋나므로 놓을 자리는 중간선 비교로 정한다. 끄는 프레임마다 React 상태를 바꾸면 마디 전부가 다시 그려진다(bpm `docs/lessons/canvas-react-flow.md` §7) — 작은 바깥 저장소와 DOM 속성으로 한다. bpm에는 Esc 취소와 자동 스크롤이 없다.

| G9 | 올리면 상자가 살짝 들린다(그림자와 테두리). 커서는 화살표 그대로 둔다 — 조각 안에서 두 번 눌러 나눌 글자를 정확히 찍어야 한다(내 판단) |
| G10 | 끄는 동안에는 다른 호버 효과를 모두 끈다 — 틈 벌어짐과 Join, 툴팁, 이음 선·짝 강조, 줄 끝 단추. 표시 하나(예: 끌기 중 속성)를 CSS와 JS가 같이 본다 |

## 5. Order

- **끄는 것**: 줄. 같은 의미에서 나온 이웃 줄(결과물 C의 굵은 선이 묶는 줄)은 **함께 옮긴다**(사용자 결정 2026-11-16). 그 아래 더 깊은 줄도 함께 간다. 줄 끝 단추와 글쇠는 지금처럼 한 줄씩 움직인다.
- **놓는 곳**: 같은 New 문서 안의 줄 사이 — 자기 칸이든 **다른 칸**(SOP의 다른 칸·하위 칸, WI의 다른 step)이든(사용자 요청 2026-11-16: "6.1을 5의 어딘가로 옮기면 5.x.x.x"). 다른 의미 묶음의 한가운데에는 끼우지 않고 그 묶음의 앞이나 뒤로 붙는다. 줄이 없는 칸(지금 "–"로 그리는 칸)에도 놓이고, 덩어리가 그 칸의 첫 줄들이 된다(내 판단). 다른 New 문서 위에서는 "문서를 바꾸는 일은 Assign에서 한다"는 이유를 보이고 놓이지 않는다(내 판단).
- **다른 칸으로 가면 줄의 자리가 정말 바뀐다**(내 판단): SOP는 새 문장의 `slot_key`, WI는 `wi_step`. 결과물 A의 Destination·B·C·Excel은 저장된 자리에서 읽을 때마다 다시 짓는 값이라 따로 고칠 것이 없다(`outputs.py`·`sheet_model.py`가 스냅숏에서 센다). Assign Old 조각의 간 곳 표시(`strip-note`)는 아직 쓰지 않은 문서의 문장이면 칸 없이 "Assigned"만 적고 이미 쓴 문서의 문장이면 절 경로를 적으므로 이 옮기기와 무관하다.
- **WI는 같은 부분끼리만**(내 판단): Instruction 줄은 다른 step의 Instruction으로, Why는 Why로. 순서 저장은 `wi_part`를 바꾸지 않는다 — Instruction·Why를 바꾸는 일은 Assign에서 한다는 이유를 보이고 놓이지 않는다. 단계 없는 칸(`unstepped:…`, 줄이 있을 때만 그려진다)은 같은 부분이면 놓인다(`wi_step`이 null이 된다).
- **다른 칸으로 못 가는 것**(사용자 요청 2026-11-16의 거절 규칙, 이유는 G7대로): N/A 칸(상위 칸이 N/A면 하위 칸도 — 저장 경로의 `na_slot`과 같은 규칙), 이미 쓴 문서의 줄이 든 덩어리, AI 번역 줄이 원문과 갈라지는 덩어리. 마지막 것은 화면이 번역의 원문을 id로 알지 못해 보수적으로 막는다 — 덩어리 안의 의미 묶음에 칸 안의 AI 번역 줄이 하나라도 있으면 그 묶음의 줄이 칸 안에서 **모두** 덩어리에 들어 있어야 하고 원문(번역이 아닌 줄)이 함께 있어야 한다(내 판단 — 번역만 떠나면 서버가 422 `translation_locked`, 원문만 떠나면 서버가 남은 번역을 지우거나 보류하므로 둘 다 막는다). 그런 덩어리도 자기 칸 안에서는 지금처럼 움직인다.
- **깊이**: 끄는 동안 좌우로 24px 움직일 때마다 한 단. 0부터 "넣을 자리 위의 가장 가까운 번호 줄 깊이 + 1"(상한 `MAX_INDENT_LEVEL`)까지, 덩어리의 아래 줄들은 단 차이를 지킨다. 다른 칸에서도 같은 규칙이고, 줄이 없는 칸에서는 0이다. 깊이가 잠긴 덩어리(아래)는 다른 칸에서도 저장된 깊이를 그대로 지니고, 번호는 세는 규칙대로 눌러 읽힌다(내 판단).
- **미리 보기**: 넣을 자리에 그 깊이의 줄이 시작하는 곳(글의 들여쓰기와 같은 폭)부터 선을 긋고, 그 자리에 놓았을 때의 새 번호를 끌리는 표에 "→ 5.2"로 적는다(`section-number.ts` `numberLines`로 센다 — 서버 `outputs.number_lines`의 사본이라 저장 응답이 이긴다). 다른 칸이면 그 칸에서 받을 번호("→ 5.1.3")를 같은 `previewEdit` + 번호 세기로 적고, 깊이 낱말(indent · outdent)은 붙이지 않는다. 그 칸에 번호가 없으면(단계 없는 WI, 번호 생략·주석 줄) "→ 칸 이름"을 적는다(내 판단). 줄이 없는 칸이면 "–" 자리 위에 선을 긋는다. 올린 다른 칸은 테두리로 보인다(놓을 수 있으면 진하게, 못 놓으면 끊긴 테두리 — G7).
- **끄는 동안 흐리게 하는 것**(내 판단): 출발 칸 밖의 모든 칸을 흐리던 것을 바꿔 N/A 칸, 다른 New 문서, 그리고 덩어리가 다른 칸으로 못 가면 출발 칸 밖의 모든 칸만 흐리게 한다.
- **놓은 뒤**: 다른 칸에 놓은 줄은 멀리 갈 수 있어 잠깐 강조한다(Assign의 `[data-flash]` 테두리를 함께 쓴다). 움직임 줄이기에서는 미끄러짐 없이 같은 시간 동안 정지한 테두리만 보인다(내 판단). 같은 칸 안의 놓기는 지금처럼 미끄러짐만.
- **번호는 표에만**(브랜치 전체 리뷰 2026-11-16): 선 위 번호 알약은 아래 줄 위를 7px 덮었고, 용지 왼쪽 여백(용지 안 30px + 틀 여백 16px)에는 긴 번호("10.12.3 · indent")가 들어가지 않아 여백에도 두지 않는다. 첫 칸 위·마지막 칸 아래는 놓을 자리 밖이다(표에 이유 없음). 칸 사이 틈에서는 출발 칸의 띠(위 10px·아래 28px)가 먼저이고, 그 밖에서 두 칸의 띠가 겹치면 아래 칸이 이긴다(내 판단 — 칸 머리 바로 위는 그 칸이다).
- **칸 안에서는 끌기가 단추가 하는 만큼만 한다.** 모든 줄을 위아래로 끌 수 있다(Move 단추와 같다). 좌우로 깊이를 바꾸는 것은 Indent·Outdent가 있는 줄만 된다 — AI 번역 줄과 이미 쓴 문서의 줄은 깊이가 잠겨 있어 위아래로만 움직이고, 덩어리에 그런 줄이 하나라도 있으면 그 덩어리는 깊이를 바꾸지 않는다(내 판단). 원문과 떨어져 놓인 번역 줄은 원문을 끌어도 따라오지 않는다(단추와 같다). **칸을 넘는 것은 끌기만 한다**(내 판단 2026-11-16) — Move up·down과 `Alt`+`↑`·`↓`는 지금처럼 칸 끝에서 멈춘다. 사용 설명서에 적는다.
- **저장**: 지금과 같다 — `c-edit-model`로 화면에 먼저 얹고 `c-save-queue`가 `PUT /targets/order`를 한 번에 하나씩 보낸다(유일한 저장 길). 다른 칸으로 옮긴 줄은 요청에 새 자리(`slot_key` 또는 `wi_step`)와 깊이를 **늘** 싣는다 — 깊이를 빼면 서버가 자리가 바뀐 줄의 깊이를 0으로 돌린다(8절). 저장이 날아가는 동안 놓은 것은 응답 위에 다시 얹고, 더는 얹을 수 없으면(칸이 N/A가 됨, 줄이 사라짐) 조용히 버린다(G1~G13 그대로).
- **글쇠**: Tab·Shift+Tab은 그대로. `Alt`+`↑`·`↓`를 더한다(포커스 줄을 한 자리 옮긴다, 칸 끝에서 멈춘다).
- **줄 끝 단추**(사용자 결정 2026-11-16): 호버·포커스 때만 보인다. 용지 오른쪽 바깥에 띄워 글을 덮지도 자리를 비워 두지도 않는다. 줄 높이는 호버로 변하지 않고, 글이 길 때 단추 묶음이 다음 줄로 내려가던 배치는 없앤다. 한 번에 한 묶음만 보인다(다른 줄에 올리면 포커스 줄의 묶음은 물러난다). 넓은 틀에서는 묶음을 줄 옆에 펼치고, 좁은 틀에서는 줄 옆에 "⋯" 단추 하나를 두어 일곱 동작을 메뉴로 연다. 올리거나 포커스가 있는 줄은 옅게 칠한다(사용자 결정 2026-11-16). `(hover: none)`에서는 지금처럼 늘 보인다.
- 이 결정은 2026-11-12의 "줄 끝 단추는 늘 흐리게"(`docs/lessons/ui-review.md`, 디자인 기초 11절)를 **Order와 Documents에서만** 바꾼다. 결과물 C와 관리 화면의 표는 그대로 둔다. 두 문서에 예외를 적는다.

## 6. Assign — 잇기와 보내기

- **끄는 것**: Old 칸의 조각 한 줄. 한/영 짝이면 짝 전체가 한 장으로 들린다(줄 단위는 `classify-model` `buildRows`와 같다).
- **이미 확정한 줄을 끌면** 지금 클릭으로 보낼 곳을 다시 고르는 것과 같다(같은 새 문장을 다시 쓴다). 다른 칸·문서의 두 문장 사이에 놓으면 그 자리로 옮긴다(8절). 그 문장이 이미 들어 있는 칸에 놓는 것은 거절한다 — 같은 칸 안의 순서는 Order에서 바꾼다(내 판단. Assign이 Order를 겸하지 않게 한다).
- **놓는 곳과 결과**

| 놓는 곳 | 결과 | 지금의 같은 길 |
|---|---|---|
| New · written 문서의 문장 | 그 문장을 고른 상태가 되고 그 자리 메뉴(Link / Confirm / Cancel)가 뜬다 | Old 줄 고르고 New 문장 클릭(`handleNewPick`) |
| New · from Assign 문서의 두 문장 사이 | 그 자리에 새 문장(As is) 초안이 점선으로 생긴다. 짝이면 두 언어 문장이 함께 | 옆 패널 All 나무에서 칸 고르기 + 나중에 Order |
| New · from Assign 문서의 빈 칸 | 그 칸의 초안. 자리를 보내지 않는다 | 나무에서 칸 클릭 |
| 옆 패널 All 나무의 칸·step | 그 칸의 초안. 자리를 보내지 않는다(지금 클릭과 같은 저장) | 나무에서 칸 클릭 |

- **자리를 보내는 것은 두 문장 사이에 놓았을 때뿐이다.** 그때만 그 문서가 순서를 사람이 정한 문서(`manual_order`)가 된다. 빈 칸과 옆 패널의 칸에 놓는 것은 지금 클릭과 똑같이 저장되어, `manual_order`가 아닌 문서에서는 출처 위치 순서로 들어간다(내 판단 — 자리를 고르지 않았는데 문서의 정렬 방식이 바뀌면 안 된다).

- **거절**: N/A 칸, 이미 쓴 문서의 문장 사이(`match_doc_new_target`), 같은 칸 안 다른 의미 묶음의 한가운데(묶음 앞뒤로 붙는다).
- **끄는 동안** 출발 조각에서 포인터까지 초안 이음 선(점선)이 따라온다. 지금 이음 선의 초안 모양을 쓴다.
- **놓은 뒤**는 지금의 "Not saved yet" 상태 그대로다. 오른쪽 칸의 판단 영역에 보낼 곳이 차고, Confirm(Enter)이 저장한다. Edit and confirm(E)로 글을 고쳐 확정하는 길도 그대로다. Cancel로 초안이 사라진다. 다른 줄을 고르면 점선 초안은 화면에서 사라지지만 초안은 그 줄에 남아, 그 줄로 돌아오면 다시 보인다(지금 코드의 초안은 줄마다 남고 나갈 때 묻는다 — 3걸음에서 확인했고 바꾸지 않았다. 아래 "3걸음에서 정한 것").
- **보낸 자리를 지킨다**(사용자 결정 2026-11-16). 저장이 자리까지 정한다(8절).
- **끌기가 꺼지는 때**: 클릭이 다른 뜻인 방식 — 짝 고르기(pair pick), "New without source"에서 출처 고르기, 한 단 보기에서 New 칸이 없을 때는 놓을 곳이 옆 패널뿐이다.
- New · from Assign 문서의 미리 보기 줄은 지금 눌러 고르지 못한다. 놓을 자리로만 쓰고 누르기는 그대로 둔다.
- **2걸음(잇기)에서 정한 것** — 설계에 없던 빈칸을 계획(`docs/superpowers/plans/2026-11-16-assign-drag-link-plan.md`)이 채운 것이다.
  - 지금 고른 줄이 아닌 Old 조각을 끌어 놓아도 된다. 그 줄이 골라지고(클릭과 같은 줄 고르기) 그 줄의 관계 묶음이 온 뒤 잇기가 적용된다. 그 사이 다른 줄을 고르면 버린다(내 판단).
  - 놓은 뒤 놓인 문장이 번쩍이고, 그 자리 메뉴는 그 문장을 클릭했을 때 뜨는 자리(이음 선 끝, v1.1.1)에 뜬다. 그러려고 놓은 자리를 메뉴까지 들고 간다(내 판단).
  - 이미 그 문장에 확정해 이은 줄을 그 문장에 놓으면 클릭과 같이 고름을 바꾸지 않고 끊기 메뉴가 뜬다(내 판단).
  - 한 단 보기에서도 끌기는 시작된다. 놓을 곳이 없어 표만 따라오고 아무 일도 없다 — 3걸음에서 옆 패널의 칸이 놓을 곳이 된다. 글자 긁기 규칙(Alt)을 두 보기에서 같게 둔다(내 판단).
  - 끌기가 꺼지는 때(조각에 끌기 표시도 없어 글자는 그냥 긁힌다): 읽기 전용, New without source, 짝 고르는 중, 한 단의 New 문서 원문 보기(내 판단).
  - 표 한 장: ID는 줄 첫 Unit의 번호, 글은 그 Unit의 글(한 줄로 줄인다), Unit이 둘 이상이면 개수. 놓을 수 있는 문장 위에서는 메모 "이 문장에 잇기"(내 판단).
  - Old 조각의 커서는 지금의 손가락 그대로 둔다 — G9의 "화살표 그대로"를 "끌기 커서(grab)를 더하지 않는다"로 읽었다(내 판단).
  - 한/영 짝 카드는 한 장으로 끌리니 어느 줄에 올려도 카드 전체가 고리 하나로 들린다. 상태 탭 밖이라 펼친 점선 조각은 들지 않는다 — 점선 테두리 바로 바깥에 실선 고리가 겹친다(내 판단).
- **3걸음(보내기)에서 정한 것** — 설계에 없던 빈칸을 계획(`docs/superpowers/plans/2026-11-17-assign-drag-send-plan.md`)이 채운 것이다. 서버 쪽은 8절.
  - 놓을 자리: 포인터 밑 New 칸 줄 상자가 든 **의미 묶음 상자**(같은 Old 줄에서 나온 이웃 줄들)의 중간선과 견준다 — 위 절반이면 묶음 앞, 아래 절반이면 묶음 뒤. 그래서 다른 의미 묶음의 한가운데에는 끼울 자리가 없다(거절하지 않고 앞뒤로 붙는다). 칸 머리 줄과 용지 여백은 놓을 자리가 아니다(내 판단).
  - 의미 묶음은 화면이 정한다: 엮은 문서 응답에 묶음 키가 없어, 문장의 첫 출처 Unit이 든 Old 줄이 같고 이웃한 줄을 한 묶음으로 본다(출처가 없으면 혼자). 서버 응답은 넓히지 않고, 서버는 묶음 한가운데를 거절하지 않는다(내 판단).
  - 놓을 자리 표시: 두 문서 틀에 붙인 명령형 선 하나(Order의 놓을 자리 선 모양). 표의 메모는 "→ 칸 머리 글"(예 "→ 6.1. Procedure"), 나무 위에서는 "→ 문서 번호 · 칸 이름". 빈 칸·나무 줄은 공통 테두리다. 끄는 동안 React 상태를 바꾸지 않는다(내 판단).
  - 점선 초안: 놓은 뒤 New 칸이 그리는 따로 선 줄이고 문장 줄이 아니다 — 이음 선·고르기·놓기 대상에 끼지 않는다. 글은 저장될 문장(고친 글이 있으면 그 글), 짝은 영어 먼저. 빈 칸에 놓았으면 줄 대신 그 칸의 자리 표시에 테두리만 단다(나무에서 그 칸을 눌러 골라도 같다 — 같은 초안 상태를 그린다)(내 판단).
  - 자리의 수명: 초안의 자리는 고쳐 쓰기(E)·글 고침·Remark를 지나도 남는다. 보낼 곳을 다시 고르면 지우고, 다른 길로 보낼 곳이 달라져 자리의 칸과 맞지 않으면 저장 요청에 싣지 않는다. 다시 읽은 문서에서 그 자리의 문장이 사라졌으면 자리만 버리고 칸 초안으로 남는다(내 판단).
  - 놓은 뒤 그 자리 메뉴: New 칸에 놓았으면 점선 초안(빈 칸이면 그 자리 표시)에 Confirm / Cancel 메뉴("Not saved yet")가 뜬다 — 칸 초안의 Cancel이 오른쪽 칸에 없어서다. 나무에 놓았으면 메뉴 없이 클릭과 같다(내 판단).
  - 다른 줄을 끌어 놓아도 된다(2걸음과 같다): 그 줄이 골라지고 관계 묶음이 온 뒤 초안이 적용된다. 그 사이 다른 줄을 고르면 버린다. New 칸에 놓았으면 New 칸은 놓은 문서에 둔다(내 판단).
  - "이미 그 칸에 있다"는 문장 사이에 놓을 때만 본다 — 열린 엮은 문서의 그 칸에 끄는 줄의 Unit을 출처로 둔 문장(AI 제안 문장 포함)이 하나라도 있으면 거절한다. 관계 묶음을 기다리지 않고 화면의 문서로 판단한다. 빈 칸과 나무는 클릭과 같아 이 거절이 없다(내 판단).
  - 나무: 놓이는 곳은 칸 줄과 step 줄뿐이다. 칸 제목 자리와 이미 쓴 문서의 문장 줄은 놓을 곳이 아니다. 접힌 문서·접힌 **All** 묶음은 끄는 동안 저절로 펼쳐지지 않는다 — 끌기 전에 펼쳐 둔다(끄는 동안 호버 효과를 끄는 G10과 맞추고, 펼침은 React 상태다)(내 판단).
  - 고른 줄이 아닌 줄을 나무에 놓으면 옆 패널이 그 줄의 것으로 바뀌고 **All** 의 펼침이 처음으로 돌아간다 — 펼침은 줄마다인 지금 클릭 길을 바꾸지 않으려고(G12) 그대로 두었다. 한 단 보기에서는 새로 끄는 줄마다 **All** 을 다시 펼쳐야 한다는 뜻이다. 결함이 아니라 사용자에게 물을 제품 질문으로 남긴다(내 판단).
  - 이미 쓴 문서의 "문장 사이"는 그 용지의 줄 상자 안에서 문장 줄과 표·그림 상자 밖 — 줄 사이 틈과 왼쪽 번호 칸이다(거절 `match_doc_new_target`)(내 판단).
  - 저장 직후의 미리 고침도 놓은 자리에 넣는다 — 끝에 넣으면 다시 읽을 때 줄이 뛴다(내 판단).
  - 초안은 줄에 남는다: 위 "놓은 뒤"의 고친 문장대로다(내 판단).
  - 끌려가는 표: 창 오른쪽을 넘으면 포인터 왼쪽으로 넘기고, 긴 메모(거절 이유)는 글 칸을 먼저 줄인 뒤 표 안에서 줄을 바꾼다 — 1120 폭에서 가장 긴 거절 이유(`match_doc_new_target`, 폭 482px)가 300px 표 밖 오른쪽으로 275px 삐져나왔다(극단 자료 검토에서 고침, 공통 끌기 층이라 Order에도 같다)(내 판단).

## 7. Pair view와 가까운 줄

- **Pair view**: Old 문서가 `ko_en_separate`일 때 Old 칸 머리에 켜는 단추를 둔다. 켜면 Assign의 두 칸 틀 그대로 왼쪽에 그 문서의 한국어 Unit, 오른쪽에 영어 Unit을 원문 순서대로 보인다(New 칸 자리를 빌린다. 끄면 원래 보기로 돌아간다). 언어가 없는 Unit(REF 줄, 그림 등)은 제 언어 쪽 흐름에 흐리게 남기고 끌리지 않는다(내 판단 — 실제 문서로 확인한다).
- **끄는 것과 놓는 곳**: 조각을 맞은편 언어의 조각에. 방향은 양쪽 다 된다.
- **끌기로 하는 것은 둘이다**(사용자 결정 2026-11-16, "화면만, 1:1부터"): 짝 없는 조각끼리 맺기와, 코드나 AI가 낸 제안(점선) 위에 놓아 그 제안을 확정하기. 맺기는 지금 "Pair with another sentence…"가 부르는 길(`POST …/documents/{doc}/pairs`)과 같다. 제안 확정(`POST …/pairs/{pair_id}/confirm`)은 처음 적은 것과 달리 "지금 길"이 아니었다 — 그 라우트는 서버에만 있었고 화면은 4걸음 전까지 한 번도 부르지 않았다(제안은 줄을 확정할 때 서버가 함께 확정한다, `pair_settle`). 4걸음이 화면에서 처음 부른다(`confirmPair`).
- **이미 확정 짝인 조각에는 놓이지 않는다.** 한 문장에 둘을 잇는 1:2와 다른 짝으로 옮기기는 지금처럼 "Pair with another sentence…"에서 Shift로 여러 개를 고르거나, 풀고 다시 맺는다. 서버에 짝에 더하기·옮기기가 없어서다(3절). 끄는 조각도 짝이 없어야 한다 — Old 칸에서 확정 짝 카드를 끌어 Old 조각에 놓는 것은 거절한다(그 카드를 New 칸으로 끄는 잇기·보내기는 6절대로 된다).
- **바로 저장하고, 알림의 Undo로 되돌린다.** 놓으면 짝이 바로 저장된다(지금과 같다). 알림에 Undo를 두고, 누르면 그 짝을 푼다(`DELETE …/pairs/{pair_id}`). 제안을 확정한 것이었으면 Undo는 확정 짝을 푸는 데까지다 — 제안 상태로 되돌리지는 않는다(내 판단. 풀린 뒤 제안이 다시 보이는지는 지금 풀기 동작을 따른다). Assign의 Ctrl+Z에는 서지 않는다 — 지금 짝 맺기가 그렇다.
- **거절과 이유**: 같은 언어, 이미 짝인 조각(`unit_already_paired`), 운명이 다른 Unit(`pair_fates_differ`), 그리고 화면 규칙 둘 — 배정을 결정한 Unit, REF 줄(지금 짝 메뉴가 꺼지는 조건과 문구를 쓴다).
- **선**: 사람이 이은 짝은 실선, 제안은 회색 점선(디자인 기초 2절 "제안은 연필로, 확정은 잉크로"). 4걸음 전의 화면은 제안 짝과 확정 짝을 똑같이 그렸다(`ClassifyRow.pairStatus`는 읽는 곳이 없고 Old 용지의 짝 카드는 상태를 가리지 않는다) — 이 구별은 Pair view에서 처음 생기고, Old 용지의 카드 모양은 그대로다.
- **가까운 줄**: `ko_en_interleaved` 문서에서는 Pair view 없이 Old 칸 안에서 조각을 맞은편 언어 조각에 놓는다. 같은 규칙, 같은 API다. Old 조각 하나를 끌 때 놓을 곳이 Old 칸의 조각이면 짝, New 칸이면 잇기·보내기다.
- Join 단추, 우클릭 메뉴, "Pair with another sentence…" 방식은 그대로 둔다.
- **4걸음에서 정한 것** — 설계에 없던 빈칸을 계획(`docs/superpowers/plans/2026-11-17-pair-view-plan.md`)이 채운 것과 설계·코드가 어긋난 곳의 판정이다. 서버 변경은 없다.
  - 단추: Old 칸 머리의 확대 단추 앞, 머리의 켜기 단추와 같은 모양에 라벨 **Pair view**(아이콘 `Languages`, `aria-pressed`). 칸 머리가 320px 이하면 라벨을 접고 툴팁이 이름부터 말한다. `ko_en_separate` Old 문서이고 한 단의 New 원문 보기·"New without source"가 아닐 때만 보인다. 글이 붙은 단추라 쉴 때도 흐리지 않는다(0.6이면 라벨이 2.75:1). 켜고 끌 때 눌린 단추는 사라지고 다른 칸 머리의 단추가 서므로, 단추로 바꿨으면 포커스를 새로 보이는 단추로 옮긴다(내 판단).
  - 기억하지 않는다 — 이 화면을 연 동안의 상태다. 한 단·양 단·확대·폭의 기억은 건드리지 않고, 한 단에서 켜도 두 칸으로 편다(내 판단).
  - 두 칸은 Old 용지를 두 번 그리지 않는 가벼운 조각 목록이다 — 용지의 도구(나눌 선·틈의 Join·필터 접기·부분 탭)는 한 언어만 남긴 칸에서 뜻이 달라진다. 세로선·확대(왼쪽 Old, 오른쪽 New 값)는 그대로 쓴다. 두 칸은 따로 스크롤하고, 짝의 두 끝을 한 화면에 들이는 길은 고르기다(누르거나 J·K — 칸마다 그 조각을 보이게)(내 판단).
  - 멀리 떨어진 조각을 보일 때는 바로 옮긴다: 조각 높이를 그리기 전에는 어림하므로(content-visibility) 부드럽게 멀리 굴리면 지나가며 그려진 조각이 자라 목표가 밀려 화면 밖에서 멈췄다(극단 자료에서 Pair view 칸 5,000px, Pair view를 끈 뒤 다시 그려진 Old 용지 11,000px 모자람). 한 화면 안이면 지금처럼 부드럽게, 더 멀면 바로 옮기고 몇 프레임 다시 맞춘다 — Pair view 칸과 Old 용지가 같은 길을 쓴다(Old 용지의 다른 이동도 이 길을 탄다)(내 판단).
  - 켜 있는 동안 고른 줄·옆 패널·글쇠는 그대로 산다(조각 클릭은 `handleOldClick`). 우클릭 메뉴·두 번 눌러 나누기·글자 긁어 새 Unit·Join은 없다(용지의 도구 — 끄고 쓴다). 상태 필터는 두 칸을 접지 않는다(내 판단).
  - Shape 줄의 나누기(단추·S)는 Pair view를 먼저 끄고 용지의 그 문장에 나눌 선을 놓는다 — 보이지 않는 자리에서 자르지 않는다. Pair view가 켜진 동안에는 아무것도 나누지 않는다(내 판단).
  - 끄는 길(단추·보기 단추·V·세로선 접기·New 쪽으로 보이기·"New without source"·나누기)은 모두 같은 자리로 돌아온다: 고른 줄이 있으면 Old 용지에 그 조각이 보이고, 없으면 켜기 전 스크롤 자리. 다시 그려진 용지는 몇 프레임에 걸쳐 자라 자리 맞추기를 되풀이하는데, 다시 켜기·화면 떠나기·사람의 굴림·누름·글쇠가 그 되풀이를 멈춘다(내 판단).
  - 짝 그리기: 두 끝이 모두 제 칸 화면 안인 짝만 선을 긋는다(KO 오른쪽 끝 → EN 왼쪽 끝, `buildLinkPath`). 확정은 강조색 실선, 제안은 `--ink-4` 점선, 고른 줄의 짝은 진하게. 조각마다 세로선 쪽 변에 같은 뜻의 막대(확정 실선·제안 점선, 막대 쪽 모서리 직각)(내 판단).
  - 언어가 없는 Unit은 원문 순서로 바로 앞 `ko`·`en` Unit의 칸에 선다(12절). 종이 카드 없이 회색 글로 흐리고(opacity로 흐리면 번호·REF 표시가 4.5:1에 못 미친다) 끌리지 않는다. 머리말·꼬리말도 원문 순서대로, 표에 묶인 칸 문장은 제 줄이 없다(내 판단).
  - 읽기 전용 묶음에서도 켜진다(읽는 일). 조각은 끌리지 않는다(G13)(내 판단).
  - 끄는 것은 조각 하나다. 제안 짝의 구성원도 따로 끌린다(제 짝에 놓아 확정하려고). 확정 짝의 조각도 끌리지만 어디에 올려도 거절과 이유다 — 끌리지 않으면 왜 안 되는지 알 길이 없다(내 판단).
  - 표의 메모: 맺기면 "Pair with OLD-3-011"(맞은편 번호), 확정이면 "Confirm this suggested pair", 못 놓으면 이유. 이유는 첫 번째로 걸리는 것 하나: 언어 없음(REF 줄·그 밖) → 같은 언어 → 확정 짝 → 다른 짝을 가리키는 제안 → 배정(끄는 쪽·놓는 쪽) → 저장 전 고름(끄는 쪽·놓는 쪽). 자기 자신·표·그림·행·표에 묶인 칸 문장 위는 놓을 자리 밖이라 조용하다 — G7("못 놓는 곳에는 이유")을 "맞은편 언어의 조각"에 좁혀 읽었다(내 판단).
  - 제안이 다른 짝을 가리키면 거절한다("One of them is already in a pair. Separate it first.") — 서버는 그 제안을 지우고 새로 맺어 주지만 그러면 놓기 한 번이 AI 제안을 버림으로 기록하고 Undo로도 돌아오지 않는다. 제안 확정은 그 제안 그대로다(1:2 제안이면 셋이 함께)(내 판단).
  - 여러 Unit의 줄(짝 카드)은 끌기로 맺지 않는다 — 한 Unit이라도 짝에 들었으면 거절과 이유, 짝이 없으면 조용하다. 첫 Unit만으로 맺지 않는다(내 판단).
  - 화면에만 있는 규칙은 넷이다(배정·REF 줄·저장 전 고름·글이 아닌 Unit) — 지금 짝 메뉴가 막는 것(`getPairPickBlocker`)을 끌기가 하지 않도록 넷을 모두 쓴다. `pair_fates_differ`는 표에 뜨지 않는다("배정" 규칙이 먼저 걸린다) — 그사이 다른 사람이 배정해 서버가 거절할 때의 알림으로만 보인다(내 판단).
  - **배정이 결정된 Unit에는 AI 분류 제안만 붙은 문장도 든다** — 지금 메뉴의 규칙(`isUnitDecided`)을 그대로 따랐다. 그래서 첫 진입 미리 분류가 켜진 묶음에서는 거의 모든 줄에 제안이 붙어 끌어서 짝 맺기가 대부분 "먼저 배정을 지우세요"로 거절된다(v1.1.3이 AI 나누기에서 푼 것과 같은 모양). 규칙을 바꿀지는 **사용자 확인 필요**(내 판단).
  - 바로 저장하고 알림의 **Undo** 로 푼다(Ctrl+Z 밖). 알림 글에 번호를 적는다("Paired OLD-3-004 + OLD-3-011") — 같은 글의 알림은 앞의 것을 지우므로 번호가 없으면 잇달아 맺을 때 앞 짝의 Undo가 사라진다. Undo는 다시 읽어 그 짝이 같은 Unit들로 확정된 채이고 판단이 없을 때만 풀고, 아니면 아무것도 쓰지 않고 "The pair changed after that. Nothing was undone."(배정된 문장의 짝을 풀지 않게). 다른 화면으로 가도 10초 안이면 같은 길로 푼다(내 판단).
  - 알림의 행동 단추(공용): `showToast(text, tone, { action })`. 행동이 있는 알림은 10초 머물고 포인터·포커스가 있는 동안 멈춘다. 진짜 단추라 Tab·Enter로 누르고, 포커스를 알림으로 옮기지 않는다(내 판단).
  - 가까운 줄은 `ko_en_interleaved` 문서에서만 켠다 — 그 밖의 배치에서 Old 조각을 Old 조각에 놓는 것은 지금처럼 아무 일도 없다(한 언어 문서에서 New 칸으로 끄는 내내 "같은 언어" 거절이 표에 번쩍이지 않게). 끄는 것은 줄이라(2걸음과 같다) 평소 Old 칸에서는 제안 짝 카드를 제 짝에 놓아 확정할 수 없다. 판단 순서는 나무 → 잇기 → 짝 → 보내기(내 판단).
  - 연달아 배치 문서에서 Old 조각 위를 지나는 동안 표의 메모는 조각마다 바뀐다(이유 · "Pair with …" · 빈 메모) — 줄이지 않았다. 거기서는 Old 조각마다 진짜 놓을 자리라 표가 지금 놓으면 무슨 일인지 말해야 한다(G6·G7). 표의 폭과 포인터와의 거리는 그대로이고 높이만 메모 줄 수대로 바뀐다(내 판단).
  - 놓은 뒤 저장이 끝나면 다시 받아 그 짝의 줄을 고른다(New 문장을 그 자리에서 다듬던 중이었으면 다듬기를 닫고). 놓은 자리의 click은 끌기 층이 삼킨다. 한 번에 한 저장이다(`busy` 동안 놓은 것은 버린다)(내 판단).

## 8. 서버

바뀌는 것은 둘이다 — Assign 보내기의 자리 받기(3걸음)와 Order의 칸 옮기기(1b걸음). 모양은 내 판단으로 정했다.

**Order — `PUT /targets/order`의 `slot_key`(1b걸음).** 새 엔드포인트를 만들지 않고 지금 순서 저장에 넓힌다(내 판단).

- 줄마다 선택 필드 `slot_key`를 받는다. 이미 있는 `wi_step`과 똑같이 **보냈고 지금 값과 다를 때만** 바꾼다(`model_fields_set`). `wi_step`(WI 줄을 다른 step으로)은 v1.0 전부터 서버가 받았고 화면이 보내지 않았을 뿐이다 — 1b걸음부터 화면이 WI에서는 `wi_step`을 보낸다.
- 검사는 모두 쓰기 전에, 거절마다 규칙 코드와 시험을 둔다. (1) SOP 문서의 입구 1 줄만 — 문서가 WI이거나 이미 쓴 문서(`entrance` match)이거나 줄이 새 문서 원문(`origin` new_doc)이면 422 `slot_not_allowed`(새 코드, `wi_step_not_allowed`와 같은 원칙). (2) `SLOT_KEYS`에 없는 값(null 포함)은 422 `unknown_slot`(To-Be가 쓰는 코드를 그대로). (3) 그 문서에서 N/A인 칸이거나 N/A 상위 칸 아래면 422 `na_slot`(새 최상위 코드 — 저장 경로의 `invalid_group.na_slot`과 같은 규칙 `is_within_slot`). (4) AI 번역 줄은 원문과 함께 같은 칸으로만 — 422 `translation_locked`(지금 step 검사와 같은 코드·같은 규칙). 칸 새 문장과 칸 제목은 목록에 없다(보내면 `order_mismatch`). 화면에서 닿는 새 코드 둘(`slot_not_allowed`·`na_slot`)은 `rule.<code>` en·ko를 둔다.
- 쓰기는 step 옮기기가 하는 것과 똑같다: 줄과 그 표의 칸 새 문장의 자리를 바꾸고 revision을 올려 낡은 저장을 막는다. 자리가 바뀐 줄은 깊이를 보내지 않았으면 0으로 돌린다(`_check_indents`가 step·칸 옮긴 줄을 함께 본다 — 저장 경로 `decisions._apply_plan`의 규칙과 같다). 함께 옮긴 번역은 사람이 정한 자리이고, 원문만 옮기면 `sweep_translations`가 번역을 지우거나(ai_suggested) 보류하고 원문 자리로 옮긴다. 작업 기록은 지금처럼 `targets.reorder` 하나, 묶음 revision은 한 번 오른다. 응답 줄(`OrderItemOut`)에 `slot_key`를 더한다.
- 자리에 걸린 다른 것: 절 경로(`section_path`)는 이미 쓴 문서의 줄에만 있어 무관하다. AI 작업의 낡음 판정은 새 문장 revision을 보므로 올린 revision으로 충분하다. Assign 되돌리기는 저장 뒤 바뀐 열을 어긋남으로 보므로 칸을 옮긴 뒤 그 저장을 되돌리면 지금 step·순서를 바꾼 뒤와 같이 409 `undo_conflict`다(바꾸지 않는다). 스키마(Alembic) 변경은 없다.

**Assign 보내기 — 자리 받기(3걸음).** 모양은 내 판단, 이름은 구현에 맡긴다.

- `POST /groups/save`의 새 문장 항목에 자리를 하나 받는다: "이 새 문장 뒤"(같은 문서·같은 칸·같은 step의 새 문장 ID) 또는 "칸의 맨 앞". **새로 만드는 새 문장**과 **다른 칸·문서로 옮기는 기존 새 문장**에 쓴다. 보내지 않으면 지금과 똑같이 동작한다. 칸이 바뀌지 않는 저장에 자리가 오면 422로 거절한다(화면이 먼저 막는다 — 6절).
- 자리를 받으면 한 저장 안에서 (1) 그 문서가 `manual_order`가 아니면 지금 보이는 순서를 `order_index`로 굳히고 `manual_order`를 켠 뒤(`PUT /targets/order`가 하는 일과 같다) (2) 그 자리에 끼운다(`insert_after`와 같은 밀기). 짝이라 두 문장을 만들면 영어 먼저, 번역은 출처 바로 뒤로 이어 놓는다 — 서버가 새 문장을 놓는 순서(`arrange_new_targets`)다. 처음엔 "받은 순서대로"라고 적었는데, 화면은 원문 순서(한국어 먼저)로 보내고 번호 표시 기본값은 영어를 첫 줄로 매기므로(`target_placement._arrange_meaning`) 받은 순서대로 두면 번호가 둘째 줄에 붙는다. 순서를 사람이 정한 문서 끝에 짝이 붙는 지금 모습과 같게 했다(내 판단, 3걸음 — 받은 순서를 원하면 이 규칙을 바꾼다).
- 거절: 가리킨 새 문장이 다른 문서·칸·step이거나 없으면 422. 이미 쓴 문서는 지금처럼 `match_doc_new_target`.
- **3걸음에서 정한 것**(계획 `docs/superpowers/plans/2026-11-17-assign-drag-send-plan.md`):
  - 필드는 새 문장 항목의 `position: {"after_target_id": <새 문장 id> | null}` — 키가 있는 객체라 "자리 없음(필드 생략)"과 "칸의 맨 앞(`null`)"이 섞이지 않는다. `{}`는 형식 오류(422 검증)다(내 판단).
  - 자리를 받는 항목은 최상위이고 칸 제목이 아니며, 새로 만들거나 줄에서 만든 기존 문장인데 (문서, 칸, step, part)가 바뀌는 것이다. WI의 Instruction ↔ Why만 바뀌어도 칸이 바뀐 것이다(결과물 C의 칸이 다르다). 그 밖에는 사유 넷으로 거절한다 — `position_not_allowed`·`position_same_place`·`unknown_position_target`·`position_target_elsewhere`(내 판단).
  - 굳히기는 `PUT /targets/order`와 같은 일을 한다: 결과물 C가 보이는 순서로 `order_index`를 0부터 매기고 `manual_order`를 켜고 작업 기록 `targets.reorder`를 남긴다. 자리를 받은 저장은 묶음 `revision`을 1 올린다(굳혔든 아니든) — 낡은 Order 화면의 순서 저장이 409가 되게(내 판단).
  - 자리를 받아 옮긴 문장의 남은 번역은 그 문장 바로 뒤로 옮긴다 — 떼어 내기는 남긴 번역의 칸만 출처에 맞추고 순번은 두므로, 옮긴 문장만 새 순번을 받으면 번역이 그 칸의 엉뚱한 자리에 선다(내 판단).
  - 한 저장 안의 검사는 모두 쓰기 전이고, 굳히기는 검사가 끝난 뒤에만 한다 — 거절된 저장은 아무것도 쓰지 않는다.
- **되돌리기**: Assign 되돌리기(`2026-11-13-assign-undo-design.md`)로 그 저장을 되돌리면 새 문장이 사라진다. 문서가 `manual_order`가 된 것은 되돌리지 않는다(Order에서 순서를 한 번 바꾼 뒤와 같다 — 내 판단). 굳히기는 그 저장의 되돌리기 단계 **밖**에서 한다(검사 → 굳히기 → 단계의 앞 모습 찍기 → 쓰기) — 단계 안에서 굳히면 되돌릴 때 순번만 굳히기 전 값(대개 모두 0)으로 돌아가는데 `manual_order`는 켜진 채라 문서가 만든 순서로 뒤섞인다. 그래서 되돌리기는 새 문장을 지우고 민 줄을 되돌릴 뿐 굳힌 순서는 남는다. 그 값으로, 굳히며 순번이 바뀐 문장을 건드린 **그 전 단계**는 되돌릴 때 409 `undo_conflict`가 된다 — Order에서 순서를 바꾼 뒤와 같고, 문서마다 처음 한 번 문장 사이에 놓고 확정했을 때만 생긴다(내 판단, 사용자 확인 필요. `test_an_earlier_undo_step_on_a_frozen_document_conflicts`).
- Pair view는 서버 변경이 없다. Order는 위의 `slot_key` 하나다. 스키마(Alembic) 변경은 어디에도 없다.

## 9. 검증

- **순수 모델을 먼저 시험한다**(화면 규칙은 순수 모델에 두는 이 저장소의 방식): 놓을 자리 정하기(중간선, 의미 묶음 경계로 붙이기, 깊이 범위), 덩어리 정하기(같은 의미 + 더 깊은 줄), 짝 놓기의 거절 사유, Assign 놓을 곳의 종류와 거절 사유.
- **서버**: 자리 받기 — 맨 앞·가운데·끝, 짝 두 문장, `manual_order` 아닌 문서가 굳는 것, 다른 칸의 ID 거절, 자리 없이 보낸 저장이 예전과 같은 것.
- **브라우저**: 스모크에 끌기 네 장면을 더한다(Order 순서·깊이, Assign 잇기, 보내기, Pair view). 끌기 뒤 클릭이 삼켜지는지, Alt로 글자가 긁히는지, 끌기 시작 뒤에도 열린 메뉴가 바깥 누름으로 닫히는지 본다.
- **극단 자료**(`seed_sop_worst`, 1120과 2560 폭): 1,800자 문단을 끌 때 표 한 장이 한 줄로 줄어드는지, Unit 수천 개 문서에서 끄는 동안 React 커밋이 없는지, 긴 문서에서 자동 스크롤이 되는지, Order의 줄 끝 단추가 좁은 창에서 글을 가리지 않는지.
- 움직임 줄이기(`prefers-reduced-motion`)에서 자리 바꿈과 들림이 바로 끝나는지.
- **Order 다른 칸으로(1b걸음)**: 순수 모델 — 포인터 아래 칸 고르기(출발 칸 우선, 겹치면 아래 칸), 다른 칸의 넣을 자리·깊이(빈 칸 0, 위 번호 줄 + 1, 덩어리 단 차이), 거절 사유(N/A·상위 N/A, 이미 쓴 문서, 번역 갈라짐, WI 다른 부분), 칸을 넘는 `place` 편집의 미리 보기·저장 줄(새 자리와 깊이를 늘 싣는다)·응답 뒤 다시 얹기와 조용히 버리기, 칸 안 편집이 예전과 똑같은 것. 서버 — `slot_key` 옮기기와 표 칸 새 문장이 따라가는 것, 깊이를 보내지 않으면 0·보내면 그 값, 거절 넷(`slot_not_allowed`·`unknown_slot`·`na_slot`(상위 N/A 포함)·`translation_locked`)이 아무것도 쓰지 않는 것, 번역을 원문과 함께 옮기기와 원문만 옮겼을 때의 쓸기, 보내지 않거나 같은 값이면 예전과 같은 것. 브라우저 — SOP 칸 → 다른 칸(하위 칸 하나, 빈 칸 하나 — 다시 읽어 확인), WI step → 다른 step, N/A 칸 거절, 잠긴 덩어리 거절, Esc, 저장이 날아가는 동안 다른 칸에 놓기, 다른 칸 위를 지나는 동안 React 커밋이 없는 것, 단추·`Alt`+`↑`·`↓`는 칸 끝에서 멈추는 것. 극단 자료에서 긴 문서의 먼 칸까지 끌 때 자동 스크롤과 표 한 줄.

## 12. 열린 것

- Pair view에서 언어가 없는 Unit이 서는 곳은 합성 자료로 정했다(앞 Unit의 칸) — 실제 `ko_en_separate` 문서로 확인 필요. 원문 순서로 바로 앞 `ko`·`en` Unit의 칸, 앞에 없으면 바로 뒤 Unit의 칸, 둘 다 없으면 KO 칸이다. 합성 시드의 따로 배치 문서(OLD-3)에는 언어 없는 Unit이 없어, 응답을 바꿔 그린 스모크와 연달아 문서를 따로 배치로 바꾼 극단 자료(OLD-1의 그림·표가 앞 영어 문장의 EN 칸에 섰다)로만 봤다. REF 줄의 원래 언어는 서버에만 있어(`unit_ref_marks.prev_lang`) 화면은 흐름의 자리로 읽는다. 그림·표가 두 언어 사이(한글 본문 끝과 영어 본문 처음 사이의 공용 부록)에 있을 때 KO 칸 끝에 서는 것이 맞는지 본다(7절 "4걸음에서 정한 것").
- Assign 되돌리기의 스냅숏과 `order_index` — 확인했다, 사용자 확인 대기. 스냅숏은 묶음의 새 문장 모든 열(`order_index` 포함)을 찍고 `target_docs`(`manual_order`)는 찍지 않는다. 굳히기를 저장 단계 안에서 하면 8절과 어긋나(되돌리면 순번만 돌아가 문서가 뒤섞인다) 굳히기를 단계 밖에서 하기로 했다(8절 "되돌리기"). 그 값: 굳히며 순번이 바뀐 문장을 건드린 그 전 단계는 되돌릴 때 409 `undo_conflict`(Order에서 순서를 바꾼 뒤와 같다). 이것이 싫으면 `manual_order`도 스냅숏에 넣어 되돌리기가 굳히기까지 무르게 하는 길이 있는데, 8절을 바꾸는 일이라 고르지 않았다.
- 고른 줄이 아닌 줄을 나무에 놓으면 옆 패널이 그 줄의 것으로 바뀌고 **All** 의 펼침이 처음으로 돌아간다(6절 "3걸음에서 정한 것") — 놓은 뒤에도 펼침을 지킬지 사용자에게 묻는다.
- 터치 화면의 끌기(길게 눌러 시작)는 요구가 생기면 따로 정한다.
