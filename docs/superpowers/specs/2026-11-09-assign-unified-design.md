# 3단계 Assign 통합 화면 설계

- 날짜: 2026-11-09 · 대상 버전: v0.10.0 (MINOR, 화면 동작이 바뀐다)
- 목업(사용자 확인본, 단계별 따라가기): https://claude.ai/artifact/KWf4qXJBqKrV5YsdHiLdPx (비공개 Artifact. 저장소 사본 `docs/design/2026-11-09-assign-mock.html`은 main 머지 뒤 지웠다 — git history)
- 판단 기준: 제품 명세 `docs/superpowers/specs/2026-11-05-sop-restructuring-e2e-design.md` §5(두 입구)·§7.10(입구 2 짝 맞추기)

## 1. 왜

3단계 "배정"에는 입구가 둘이다. 아직 안 쓴 To-Be 문서는 **분류**(Old Unit → 칸)로 채우고, 이미 써서 업로드한 New 문서는 **짝 맞추기**(New 문장 → Old 출처)로 잇는다. 지금은 두 화면이 따로 있고 레일에서 둘 다 3번이다(v0.9.0에서 한 칸으로만 묶었다).

사용자가 실제 작업을 그려 보니 **Old 문장을 한 줄씩 처리하는 것이 자연스럽다**(사용자 판단). 한 Bundle에 쓴 문서와 안 쓴 문서가 섞이면 Old 문장의 행선지가 문장마다 갈리는데, 사람이 입구를 의식할 필요는 없다. To-Be에서 문서마다 정한 입구가 보낼 곳의 종류를 정한다.

성공 기준: 목업의 따라가기 시나리오(카드로 짝 고르기 → 원문에서 직접 고르기 → 나눔 → 합침 → 아직 안 쓴 문서의 칸 → 추천이 틀렸을 때 전체에서 고르기 → 삭제 → 출처 없는 New를 신규로)를 실제 데이터로 막힘 없이 끝내고, 결과물 A·B·C와 검토 조건이 지금과 같은 값을 낸다.

## 2. 범위

**하는 것**: 분류 화면과 짝 맞추기 화면을 Assign 화면 하나로 합친다(§3~§6). 이를 위한 Old Unit → New 문장 후보 API 하나(§7).

**하지 않는 것**
- 저장 규칙·데이터 모델·결과물 계산 변경. 두 화면이 이미 같은 저장 API(`/groups/save`)와 같은 표(`TargetSentence`·`TargetSource`)를 쓴다. 이 설계는 화면을 합치는 일이다.
- To-Be 화면 개편(업로드한 New 문서를 반은 목록·반은 미리보기로, 짝 맞춘 내용을 To-Be에 반영 — 사용자가 "나중에"로 미룬 생각).
- 이미 쓴 New 문서 안의 **표(칸 문장)를 사람이 Old 표에 잇는 길**(사용자 결정: 이번엔 그대로). 지금처럼 AI 짝 작업이 잇거나 "신규로 표시"한다. 실제 출처가 있는 New 표가 신규로 남을 수 있는 것은 알려진 빈틈으로 남긴다. New 원문에는 표를 보이되 고를 수 없게 하고, 출처 없는 New 칩은 문장만 센다(표는 검토 조건에서 지금처럼 막는다 — 빌더가 칩 숫자와 검토 조건의 차이를 툴팁으로 알린다).
- AI 정확도 주장. 후보 API의 임계값·순위는 합성 자료로만 맞춘다(CLAUDE.md "임계값은 합성 자료로만 잡은 값").

**실패로 보는 것**: 화면은 합쳤는데 지금 두 화면에서 되던 일이 안 되는 것 — 표 단위 배정, 한/영 짝 같이 배정, 일괄 삭제·이동, 똑같은 문장 한꺼번에 확정, 신규 표시, AI 제안 받아들이기, 보류·사유, 미저장 이탈 가드, 라이트·다크, 대비 4.5:1, 좁은 화면(1366).

## 3. 화면 구성 (목업)

```
레일 | [막대: 거르기 칩 · 진행 · 똑같은 문장 일괄 · AI 요청 · New 원문 열기/닫기]                     | 오른쪽 칸
     | Old 원문(Unit 조각) ‖ 세로선 ‖ New 원문(이미 쓴 문서)                                           | 고른 Old · 고른 곳 · 확정/보류/비우기 · 아코디언 4단
```

### 3.1 레일·주소
- 레일 3단계는 **Assign 한 항목**(사용자 결정). 화면 이름 영어 "Assign", 한국어 "배정"(내 판단). v0.9.0의 번호 한 칸 묶음(`groupStages`)은 필요 없어져 지운다.
- 주소 `/bundles/[id]/assign`. 옛 `/classify`·`/match`는 이 주소로 넘긴다(즐겨찾기·설명서 링크, 내 판단). 개요 "다음 할 일"(`NEXT_ACTION_STAGE`·`pickNextStage`)은 모두 assign으로 간다.
- 분류 화면의 "원문 3단 / 목록+상세" 레이아웃 설정(`classifyLayout`)은 없앤다. 원문 자체가 목록이라 목록 보기가 따로 필요 없다(내 판단 — §11 확인 항목).

### 3.2 Old 원문 = 목록 (사용자 결정)
- 따로 된 Old 문장 목록을 두지 않는다. **Split 화면의 Unit 조각 보기**(`components/paper/paper.tsx`의 조각 모드)를 그대로 쓴다: 문단 앞 KO/EN·H 태그, 종이 오른쪽 끝 상태 표시(확정 ✓ · AI 제안 ✦ · 미배정 ○), 확정한 조각 아래 간 곳(`→ WI-04 1.1`, `→ SOP-CF 일반 요구사항 › 안전`, `→ 삭제`).
- 조각을 누르거나 ↑↓·J/K로 옮긴다. 고른 조각은 바깥 윤곽(Split과 같은 표시)이고 화면 가운데로 스크롤한다.
- 표는 Split처럼 표 모양으로 보이고, 지금 분류처럼 표 전체·행 단위로 고른다.
- Old 문서가 여럿이면 Old 원문 머리의 드롭다운(`Select`)으로 바꾼다. ↑↓가 문서 끝에 닿으면 다음 문서로 넘어간다(내 판단).
- **거르기 칩**(막대): 미배정 · 보류 · 확정 · 전체(지금 분류와 같은 값) + **출처 없는 New**. Old 거르기는 조각을 숨기지 않고 ↑↓가 그 상태만 밟게 하며, 나머지 조각은 흐리게 둔다(내 판단 — 원문 흐름이 끊기지 않게).
- **일괄**: Old 조각을 Shift+클릭으로 여러 개 고르면 지금 분류의 일괄 삭제·외부 이동 막대가 나온다(내 판단, Ctrl+클릭은 New 쪽 나눔 고르기와 겹치지 않게 Shift로).

### 3.3 New 원문
- 이미 쓴 New 문서(To-Be 입구 `match`)를 연다. 문장 번호·절 머리·KO/EN 태그. 표시: 점선 = AI 후보, 채움 = 지금 고른 문장, `← 1-012` = 붙은 Old 출처(둘 이상이면 합침), 빨간 테두리 = 출처 없음, `신규`.
- **자동으로 열고 닫는다**(내 판단, 목업): 고른 Old 조각의 맨 위 후보나 고른 곳이 이미 쓴 문서의 문장이면 열고, 아니면 닫힌다(Old 원문만 가운데). 막대의 "New 원문 열기/닫기"로 언제든 바꾼다. 이미 쓴 문서가 여럿이면 머리 드롭다운으로 바꾸고, 후보가 있는 문서로 자동으로 맞춘다.
- 이미 쓴 문서가 하나도 없는 Bundle에서는 New 원문 단추가 없다.

### 3.4 두 문서 나란히 (사용자 결정)
- 겹치지 않고 나란히. **사이 세로선을 끌어 폭을 나눈다**: 30~70%, 더블클릭 = 반반, 선에 포커스 두고 ←→(3%씩). `role="separator"`, `aria-valuenow`.
- **문서마다 따로 확대**: 70~160%, 10%씩. 마우스를 올린 문서에서 Ctrl+휠, 또는 Ctrl +/−(Ctrl 0 = 100%). 문서 머리 −/+ 단추(평소 흐림, 호버 때 진함). 마우스가 문서 위에 없을 때는 브라우저 확대를 가로채지 않는다. 트랙패드 핀치(작은 Ctrl+휠이 잦다)는 모아서 한 칸씩.
- 확대·폭은 사람마다 기억한다(`ui-prefs`, `sopa.` 접두, 내 판단). 확대·폭을 바꿔도 각 문서의 스크롤 자리는 지킨다.

### 3.5 오른쪽 칸
- **아무 조각도 고르지 않았을 때**: "Old 조각을 고르세요" 안내 + **범례 전체**(Old 조각 표시 · New 원문 표시 · 키) (사용자 결정).
- **조각을 골랐을 때**: 머리(Unit ID · 상태 칩 · 원문 한 줄) + 오른쪽 위 **(i) 범례**(호버·포커스 때 같은 범례가 뜬다, 사용자 결정). 그 아래:
  1. **고른 곳 상자** — 비었으면 점선 안내. 이미 쓴 문서의 문장이면 문장과 변경 종류(그대로·말투·고쳐 씀, 나눔·합침은 자동 표시), 아직 안 쓴 문서의 칸이면 새 문장 KO/EN 입력(지금 분류와 같은 편집·번역 제안), 삭제면 사유(필수).
  2. **확정 ↵ · 보류 H · 비우기 U** (+ 지금 분류의 고쳐 확정 E, 사유·검사·확정한 사람 줄은 그대로).
  3. **아코디언 4단**(사용자 결정, 우선순위 순서로 한 단계씩 펼친다):
     - ① **추천**(처음부터 열림): 이 Unit에 대한 AI 제안(분류 제안의 칸 + 짝 제안의 New 문장)과 후보 API의 비슷한 New 문장을 한 목록으로. 카드 한 번 누르면 고른 곳이 된다. AI가 낸 것은 ✦와 이유, 비슷한 문장은 "비슷한 문장"(유사도를 확률로 보이지 않는다 — 명세 §7.10).
     - ② **가까운 곳**: 맨 위 후보 문장의 앞뒤 문장, 또는 같은 To-Be 문서의 다른 칸.
     - ③ **전체**: 이미 쓴 문서(문서 → 절 → 문장) · 아직 안 쓴 문서(문서 → 칸·단계)를 한 단계씩 펼친다. N/A 칸은 고를 수 없다.
     - ④ **삭제·외부 이동**.
- 출처 없는 New 모드에서는 New 문장 머리 + "신규로 표시" + "Old 조각을 눌러 출처로" 안내.

## 4. 동작

- **이미 쓴 문서의 문장에 붙이기**: 카드나 New 원문의 문장을 누른다. Ctrl+클릭은 여러 문장 고르기(= **나눔**, Old 하나 → New 여럿). 다른 Old 조각이 이미 붙은 New 문장을 고르면 **합침**으로 표시하고 "OLD-…와 한 문장으로 합쳐집니다"를 보인다. 나눔·합침 판정은 지금처럼 서버가 한다(`decisions.py` 703-707).
- **아직 안 쓴 문서의 칸**: 지금 분류와 같다(새 문장 만들기, AI 고쳐 쓰기·번역 제안).
- **보낼 곳은 바꾸기가 기본**(사용자 결정): 이미 갈 곳이 있는 조각에 다른 곳을 고르면 이전 연결을 떼고 바꾼다 — New 문장에서 출처를 빼고(그 New 문장은 다른 출처가 없으면 출처 없음으로 돌아간다), 칸에 만들었던 새 문장(과 그 번역)은 지운다(지금 분류에서 보낼 곳을 바꿀 때와 같은 떼어 내기, `detach`). 더하기는 두 경우뿐: 같은 New 문서 안에서 Ctrl+클릭(나눔), 그리고 고른 곳 상자의 "다른 곳에도 추가"로 두 문서에 보내기(지금 서버 규칙대로 사유 필수 — `duplicate_without_reason`). 분류 제안과 짝 제안이 둘 다 있을 때 하나를 받으면 나머지 제안은 고르지 않은 것으로 남는다(밀린 제안 처리는 지금 서버 그대로).
- **함께 확정되는 것을 보여 준다**(사용자 결정): 서버는 닫힌 관계 묶음 전체를 받아야 저장하고, 받은 묶음의 판단을 모두 사람 확정으로 바꾼다. 그래서 고른 곳 상자 아래에 "함께 확정되는 것"(합쳐진 다른 Old 조각, 같은 Old의 다른 New 문서 연결, 짝 조각)을 줄로 보이고, 확정·보류 한 번이 이 전부에 적용된다. 서버 저장 규칙은 바꾸지 않는다.
- **다른 언어 만들기**(사용자 추가 요청): 한 언어만 있는 조각(Old 문서가 한국어만이거나 짝이 없는 조각)을 아직 안 쓴 문서의 칸에 확정하면, 고른 곳 상자의 새 문장에 "영어 만들기"(KO만 있을 때) · "한국어 만들기"(EN만 있을 때) 단추가 보인다. AI가 켜져 있으면 지금 분류의 번역 요청(`translate`, 이 조각 하나, `ko_to_en`/`en_to_ko`)을 보내 번역 제안을 받고, 꺼져 있으면 빈 다른 언어 칸을 열어 직접 쓴다. 번역 새 문장은 지금처럼 출처 새 문장을 따른다(CLAUDE.md "번역은 출처 새 문장을 따른다"). 이미 쓴 New 문서의 문장은 글이 잠겨 있어 이 단추가 없다(내 판단 — 사용자 확인 필요).
- **확정하면 다음 미완 조각으로** 넘어간다(지금 분류의 `findNextOpen`과 같은 순서).
- **출처 없는 New**: 칩을 누르면 New 원문이 열리고 출처 없는 문장만 차례로 밟는다. "신규로 표시"는 지금 `/match/bulk-confirm`의 `new`. Old 조각을 누르면(Ctrl로 여럿) 그 문장의 출처가 된다. 칩 숫자는 남아 있으면 위험색(검토 요청의 `targets_unassigned`를 막는 값).
- **똑같은 문장 한꺼번에 확정**: 지금 짝 맞추기의 배너 기능을 막대로 옮긴다(`list_identical_candidates`, 개수가 있을 때만).
- **AI 요청**: 지금 두 화면의 AI 요청 메뉴(분류·번역·짝)를 막대 하나로.
- **삭제 후보**: AI가 Bundle에 입구 1 문서가 없을 때 표시하는 삭제 제안(`delete_candidate`)은 ① 추천에 삭제 카드로 나온다.

## 5. 한/영 짝 (내 판단 — §11 확인 항목)

지금 분류는 한/영 짝 Unit 둘을 한 줄로 같이 배정하고, 짝 맞추기는 같은 언어끼리만 잇는다(명세 §7.10).
- Assign에서도 조각 하나를 고르면 그 짝까지 같이 골라진다(Old 원문에 두 조각이 함께 윤곽).
- 이미 쓴 문서의 문장에 붙일 때: 한 언어 문장을 고르면 **그 New 문장의 한/영 짝**(New 문서도 업로드 때 짝을 만든다, `units._create_code_pairs`)을 다른 언어 Old 조각에 자동으로 붙인다. New 쪽에 짝이 없으면 고른 곳 상자에 언어별 칸 두 개(KO·EN)를 두고 빈 쪽을 직접 고르게 한다.
- 변경 종류는 기본으로 두 언어에 같은 값을 쓰고, 고른 곳 상자에서 언어별로 바꿀 수 있다(서버가 글자가 다른 target마다 `change_type`을 요구한다 — `change_type_required`, 내 판단).
- 한쪽만 짝인 경우(Old는 짝인데 New는 한 언어뿐, 또는 반대): 있는 언어만 저장하고, 남은 언어 조각은 미배정으로 남아 Old 남음에 계속 보인다(내 판단 — 확정을 막지 않는다).
- 아직 안 쓴 문서의 칸: 지금 분류와 같다(KO·EN 새 문장).

## 6. 추천 순서

① 추천 목록은 이 순서로 섞는다(내 판단).
1. 사람이 아직 손대지 않은 AI 제안(짝 제안 `kind=match`의 그룹 중 이 Unit이 든 것, 분류 제안 `kind=classify`의 칸·삭제). 지금 화면처럼 Unit ID로 찾는다(`content.unit_ids`).
2. 똑같은 문장 후보(`list_identical_candidates`에 이 Unit이 있으면).
3. 후보 API의 비슷한 New 문장(§7), 이미 위에 나온 문장은 뺀다.
4. 분류 칸 후보(`rank_candidates`의 상위 칸, AI가 꺼져 있어도 글자 유사도로 나온다면) — 빌더가 지금 분류 화면이 AI 없이 칸 후보를 보이는지 확인하고 같은 동작을 유지한다.
- 최대 5장, 나머지는 ② ③으로.

## 7. 서버 변경

- **새 엔드포인트** `GET /api/bundles/{id}/units/{unit_id}/new-candidates` (멤버면 읽기, 기존 단위 읽기와 같은 권한): 이 Old Unit과 **같은 언어**의 이미 쓴 문서 문장(`origin=new_doc`, 최상위 문장, 표·그림 제외) 중 비슷한 것 최대 5개. 각 항목 `{target_id, target_doc_id, doc_code, section_path, text, basis: "embedding" | "text"}`. 임베딩 캐시에 두 문장이 다 있으면 그 코사인, 하나라도 없으면 글자 2-gram(`similarity.py`)으로 떨어진다 — 이 GET은 임베딩·LLM을 부르지 않는다(내 판단: 응답이 빠르고 사용량 행·세션 규칙 문제가 없다. 임베딩은 짝 맞추기 AI 작업이 이미 캐시를 채운다). 이미 다른 Old Unit이 붙은 문장도 내보낸다(합침이 될 수 있어서).
- **저장**은 지금 `/groups/save` 그대로. 단 프런트는 **늘 닫힌 관계 묶음 전체를 보낸다**: 고른 Unit(과 짝)의 묶음(`getGroupByUnit`)과 새로 붙일 New 문장의 묶음(`getGroupByTarget`)을 합쳐, 손대지 않는 target도 그대로 되돌려 보낸다(지금 분류의 `buildGroupSave`가 `new_doc` target을 되돌려 보내는 방식). 그래야 나눔(Old 하나가 New 둘의 출처)·합침이 `not_closed`로 거절되지 않는다. 지금 짝 맞추기 화면은 고른 New 문장 하나만 보내서 실제로 거절된다(시험으로 확인: 사람이 두 번째 문장에 붙일 때와 AI 나눔 제안을 받아들일 때 모두 422 `invalid_group`/`not_closed`). 같은 Old Unit이 다른 New 문서의 문장에도 붙어 있는 경우도 같은 규칙에 걸리므로 묶음 전체를 보내는 방식으로 함께 풀린다.
- 그 밖의 엔드포인트(일괄, 지우기, 신규 표시, 똑같은 문장, AI 요청·적용)는 그대로 쓴다.

## 8. 함께 옮기는 것

- `lib/stages.ts`(assign 하나, 잠금 목록·다음 할 일), `app-shell`의 넓은 화면 목록, 개요의 단계 링크.
- 순수 모델: 지금 `classify-model`·`match-model`의 규칙을 `assign-model`로 모으고 시험한다(저장 묶음 만들기, 추천 섞기, 짝 자동 붙이기, 다음 미완, 확대·폭 범위).
- i18n: `classify.*`·`match.*` 중 쓰는 것을 `assign.*`로, 안 쓰는 키는 지운다(en·ko 한 쌍 규칙).
- 스모크(`pw-smoke-sop`)의 분류·짝 맞추기 단계, 대비 감사 화면 목록, 설명서 그림(`pw-manual-shots`)과 `docs/manual/system-walkthrough.html`의 분류·짝 맞추기 장.
- 목업 HTML은 개발 동안 `docs/design/`에 두었다가 머지 뒤 지웠다(설계 스냅샷 폐기 정책).

## 9. 검증

- 단위: `assign-model`(위 §8), 확대 단계·폭 범위, 저장 묶음에 되돌려 보내는 target이 빠지지 않는지(나눔·합침·짝 자동).
- backend: 후보 API(같은 언어만, 표 제외, 임베딩 꺼짐 → 글자 유사도, 권한), 닫힌 묶음 저장으로 나눔·합침이 저장되는 경로.
