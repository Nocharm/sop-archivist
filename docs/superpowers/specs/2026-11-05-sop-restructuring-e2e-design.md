## 1. 의도

옛 SOP를 넣으면 **쪼개기 → 분류(+고쳐 쓰기·번역 제안) → 변경 추적 결과물**까지 한 앱 안에서 이어지는 도구다. 누가 하든 같은 단계를 거쳐 같은 모양의 결과물이 나오게 해서, SOP 오너마다 제각각이던 재구성 작업 방식을 하나로 통일한다. **[결정]** 이 도구가 내는 결과물이 곧 재구성 추적표의 표준이 된다.

**배경.** 회사 GMP 문서(SOP)가 공장·캠퍼스·모달리티가 늘 때마다 덧붙여져 길어지고 중복됐다. 전사 TF가 모든 SOP를 두 층으로 다시 짜고 있다.
- **SOP(부모)**: 무엇을 지켜야 하나. 정책·요구사항·역할과 책임. 7칸 고정 구조(Purpose / Scope / Definitions / Responsibilities / General Requirements / Procedures / Document Relationships).
- **WI(자식, Work Instruction)**: 어떻게 하나. 단위 작업별 단계(Instruction)와 필요한 단계에만 Why.

지금은 오너가 옛 SOP(Word)를 문장 단위로 엑셀에 옮기고, 문장마다 갈 곳을 정하고, 추적표를 손으로 만든다. 엑셀 양식·쪼개는 단위·추적표 모양이 사람마다 다르다.

**왜 이렇게 만드나.** 사내 AI를 써 본 오너들은 번역·문장 다듬기에서는 효과를 봤지만, 구조 검토나 As-Is/To-Be 매핑 같은 복잡한 일에서는 결과를 검증하는 데 시간이 다 들어가 아낀 시간이 거의 없었다. Excel로 받지 못하고, 표와 그림이 옮겨지지 않고, 조건을 매번 다시 설명해야 했다. 그래서 이 도구는 일을 셋으로 가른다.
- **코드가 셀 수 있는 것은 코드가 한다**: 추출, 누락·중복 계산, 결과물. 사람이 세지 않는다.
- **AI는 정해진 칸 중에서 고르는 제안만 한다**: 근거와 규칙 ID를 붙인다. 확정하지 않는다.
- **사람은 판단하고 확정한다**: "AI 제안" 상태인 줄만 보면 된다.

이전에 같은 팀이 이 일을 서비스 세 개로 나눠 만들었는데, 사람이 JSON을 내려받아 다음 서비스에 올려야 이어져서 흐름이 끊겼다. **[결정]** 이번에는 하나의 앱이다.

**사용자.** 부서별 SOP 오너(작성자)와 QA 검토자. **[추천 채택]** Word와 Excel에는 익숙하지만 프롬프트는 다루지 않는다고 본다. 그래서 프롬프트와 지침은 앱이 버전으로 관리하고, 오너는 프롬프트를 쓰지 않는다. 만드는 쪽은 AX팀이다.

## 2. 이번 단계의 범위와 순서

- **(사용자 결정 2026-11-05) 설계와 백엔드를 먼저 구현한다.** 프런트엔드 테마·디자인 토큰이 아직 정해지지 않았으므로, 프런트는 구현 계획 이후 사용자가 Claude Design으로 1차 작업한다.
- 그래서 백엔드는 **모든 단계를 API만으로 끝까지 수행**할 수 있어야 하고, 합성 데이터로 API 수준의 처음부터 끝까지 흐름을 테스트로 증명한다(§13).
- 화면은 이 문서 §12에서 "무엇을 보여 주고 무엇을 할 수 있는가"(상태·행동·데이터) 수준으로만 정한다. 모양·배치·시안은 Claude Design 단계의 몫이다. **[결정]** 킥오프의 "큰 화면은 시안 2–4개를 보여 주고 사용자가 고르게 한다"는 그 단계에서 지킨다.
- 기존 프런트(로그인·홈·관리 화면)는 깨지지 않게 유지한다. 새 권한 키를 추가할 때의 프런트 미러(CLAUDE.md 체크리스트) 정도만 건드린다.
- 구현 계획은 둘로 나눈다(§14). 계획 1은 AI 없이 사람이 끝까지 할 수 있는 결정적 코어, 계획 2는 그 위의 AI 층이다.

## 3. 목표 · 비목표 · 실패로 보는 것

**목표 [결정]**
1. 한 앱 안에서 끝난다. 단계 사이에 파일을 내려받아 다시 올리지 않는다.
2. 옛 문장이 하나도 빠지지 않았다는 것을 **코드가 계산해서** 보여 준다. 사람이 세지 않는다.
3. AI는 제안만 하고 확정은 사람이 한다. 사람은 "AI 제안" 상태인 줄만 보면 된다.
4. 오너가 "끝났다" 할 때 손에 쥐는 것은 결과물 A·B·C(§7.13)와 그 Excel 파일이다.

**비목표 (이번 범위 밖)**
- EQUIS(이퀴즈 — Veeva 기반 사내 문서관리시스템)에서 새 문서를 Active로, 옛 문서를 Obsolete로 바꾸는 일. **[결정]**
- 새 SOP/WI 문서 생성. 고친 문장을 모아 Word로 조립하는 일과 사내 양식에 맞춘 완성본 생성은 다음 단계이고, 결과물 C가 그 단계에 넘길 재료다. **[결정]**
- 사내 SOP DB 전체 검색. 오너가 문서를 직접 올린다.
- 모델 배포, 토큰 한도, 응답 속도 같은 인프라.
- 옛 SOP를 참조하던 다른 문서(Form, QRA, 교육 등)의 참조 갱신. **[추천 채택]**
- 사용자가 비교표의 칸 순서를 바꾸는 기능. **[결정]**
- 그림 내용 읽기와 그림 변경 추적. 그림은 바뀌지 않는다고 가정한다. **[결정]**
- 비교표를 Excel에서 고쳐 다시 가져오기. Excel로 가져오는 것은 To-Be 목록뿐이다. **[추천 채택]**
- 이전 추출의 판단을 새 추출로 자동으로 옮겨 오기(§6.3). (내 판단)

**실패로 보는 것 (기능이 돌아가도 이러면 실패다) [결정]**
- AI가 추적표를 쓴다. 추적표는 사람이 확정한 결과로 시스템이 계산해야 한다.
- AI가 원문을 고쳐 저장한다. 원문은 그대로 두고, 고친 문장은 따로 저장한다.
- AI 제안이 사람 확인 없이 확정된다.
- 배정되지 않은 옛 문장이 남아 있는데 화면에 "완료"가 뜬다.
- 원문이 사내 모델 밖으로 나간다.
- 오너가 화면 여러 개를 오가거나, 같은 조건을 매번 다시 입력한다.

## 4. 용어

| 용어 | 뜻 |
|---|---|
| 묶음(bundle) | 재구성 한 건. 옛 SOP 여러 개를 새 SOP와 WI로 바꾸는 작업 하나. 작업 상태는 묶음 단위로 서버에 저장한다. **[결정]** |
| 옛 문서 / 새 문서 | 옛 문서 = 재구성 대상인 기존 SOP. 새 문서 = To-Be 목록의 새 SOP·WI. 입구 2에서는 새 문서 파일도 올린다 |
| 원문 블록 | 추출기가 원본에서 읽은 문단·표 칸·그림 하나. 원문 글자 그대로이고 바뀌지 않는다 |
| 단위(unit) | 원문 블록 위의 글자 범위. 문장, 그림, 표, 표의 행, 표 칸 안의 문장이 있다(§6.4) |
| 커버 단위 | 누락 계산의 기본 원소. 문장 단위(표 칸 안의 문장 포함), 제목 단위, 그림 단위. 표·행 단위는 칸 문장들의 보낸 곳을 담는 묶음일 뿐 따로 세지 않는다 |
| 처분(disposition) | 단위가 어디로 가는가: 미배정 / 배정(새 문서의 위치) / 삭제 / 다른 문서로 이동 |
| 새 문장(target sentence) | 새 문서의 한 위치에 들어갈 문장(또는 표·그림 항목). 출처 옛 단위 0개 이상과 이어진다 |
| 위치(location) | 새 문서 안 자리. SOP는 칸 키(`procedures.maintenance` 등), WI는 (몇 번째 단계, Instruction 또는 Why), 입구 2 문서는 그 문서의 실제 절 위치 |
| 관계 묶음 | 나뉘거나(1→N) 합쳐진(N→1) 단위·새 문장끼리의 묶음 |
| 짝(pair) | 같은 내용의 한글 단위와 영어 단위를 잇는 것 |
| 입구 1 / 입구 2 | 입구 1 = To-Be를 아직 쓰지 않음(칸에 배정). 입구 2 = To-Be를 이미 씀(옛·새 단위 짝 맞추기). 새 문서마다 고른다 |
| 상태 | 커버 단위와 새 문장의 확인 상태: 미배정 / AI 제안 / 확정 / 보류. 정확히 하나 |

## 5. 전체 흐름과 두 입구

```text
[옛 SOP 묶음 업로드] → ① 쪼개기 → ② To-Be 목록 → ③ 분류 + 제안 / 짝 맞추기 → ④ 결과물 A·B·C → Excel
                         (코드)       (사람)        (임베딩 + LLM 제안, 사람 확정)       (코드)
```

- 입구는 두 개이고, 어느 입구로 들어와도 같은 모양의 결과물이 나온다. **[결정]**
- **입구 1 (To-Be를 아직 쓰지 않았을 때)**: 옛 SOP를 쪼갠다. 미리 넣은 To-Be 목록의 칸에 단위를 하나씩 배정한다. AI가 배정·고쳐 쓰기·번역을 제안하고 사람이 확정한다.
- **입구 2 (To-Be를 이미 썼을 때)**: 옛 SOP와 새 SOP·WI를 둘 다 올려 둘 다 쪼갠다. 임베딩으로 옛 단위와 새 단위의 짝을 제안한다(1:1, 1:N 나눔, N:1 합침). 사람은 짝이 맞는지만 확인한다. 짝이 없는 옛 단위는 삭제 후보, 짝이 없는 새 단위는 신규로 표시한다.
- 한 묶음 안에서 새 문서별로 입구를 고른다. 어떤 WI는 써 두었고 어떤 WI는 아직이면 두 입구를 섞어 쓴다.
- AI가 느리거나 멈춰도 ①과 ④는 돌아가고, 사람이 손으로 배정·짝 맞추기를 할 수 있다. **[추천 채택]**

## 6. 데이터 모델 (개념)

표 이름·컬럼 이름은 빌더 재량이다. 여기서는 개념, 꼭 있어야 하는 필드, 코드가 지켜야 하는 불변식을 정한다. 시각은 기반 규칙대로 `DateTime(timezone=True)`와 `app.clock.now()`(KST), 스키마 변경은 Alembic 리비전이다.

### 6.1 묶음과 멤버

- **묶음**: 제목, 설명(선택), 상태(`in_progress` 작업 중 / `in_review` 검토 대기 / `done` 검토 완료), 만든 사람·시각, `revision`(동시 편집 검사용, §6.13). 묶음에 To-Be 목록과 문서별 언어 설정이 한 번 저장되고 이후 모든 AI 요청에 자동으로 들어간다. 오너가 조건을 다시 설명하지 않는다. **[추천 채택]**
- **멤버**: (묶음, `login_id`, 역할 `author` 작성자 | `reviewer` 검토자). 작성자는 한 명 이상, 검토자는 검토 요청 시점에 한 명 이상. 한 사람은 한 묶음에서 한 역할만 갖는다(작성자가 자기 묶음을 검토 완료하지 못하게, 내 판단). 권한 규칙은 §9.

### 6.2 문서·파일·추출

- **문서**: 묶음, 쪽(`old` 옛 문서 | `new` 입구 2의 새 문서), 원본 파일 이름, 형식(`docx` | `pdf`), 크기, SHA-256, 문서 번호·버전·제목, 언어 배치(§6.5), 상태(`ready` | `rejected` | `failed`)와 사유, 올린 사람·시각. `new` 문서는 To-Be 목록의 새 문서 하나와 1:1로 이어진다.
- **원본 파일**: 바이트를 DB에 저장한다(내 판단: 기존 일간 백업이 그대로 덮고, 서버에 파일 볼륨을 새로 두지 않는다. 용량이 커지면 재검토). 원본은 절대 바꾸지 않는다. 같은 묶음에 같은 해시의 파일은 다시 받지 않는다.
- **파일 이름 파싱**: 문서 코드(예: `SOP-QC-00005`), 버전, 제목을 파일 이름에서 자동으로 채운다. 이름에 없는 값은 지어내지 않고 빈 칸으로 두어 사람이 채울 칸으로 표시한다. **[추천 채택]**
  - 읽는 규칙: 확장자를 떼고 `_`를 공백으로 본 뒤 첫 문서 번호(`SOP-QC-00005`·`WI-01` 꼴), 그 번호를 뺀 나머지의 첫 버전(`v3`·`Rev. 2`·`Ver 1.1` 꼴)을 읽고 남은 글을 제목으로 다듬는다. 없거나 컬럼 길이(번호 100자·버전 50자)를 넘으면 빈 칸이다. (계획 1에서 정함)
- **추출(extraction)**: 문서 하나를 한 번 추출한 결과. 추출기 버전, 시각, 보조 대조 결과(§7.3), 경고 목록. 원문 블록과 단위는 추출에 속한다.

### 6.3 원문 블록

- 추출기가 읽은 순서대로의 블록 목록. 블록마다:
  - 부분(part): 본문 / 머리말 / 꼬리말 / 각주 / 미주 / 텍스트 상자. 본문과 구별하고, 반복되는 머리말도 임의로 지우지 않는다.
  - 종류: 문단 / 표 칸 / 그림(캡션 포함).
  - 위치: XML 경로(DOCX) 또는 쪽·문단 번호(PDF), 표라면 (표 번호, 행, 열, 병합 정보), 쪽 번호와 그 근거(`rendered` Word가 저장한 쪽 나눔 | `manual` 수동 쪽 나눔 | `estimated` 추정), 섹션 번호(원문 글자에 있는 조항 번호, 없으면 가장 가까운 제목 글), 제목 수준(제목 스타일일 때).
  - 글자: 원문 그대로. 자동 교정·정규화하지 않는다.
- **원문 불변 [결정]**: 블록은 만든 뒤 바뀌지 않는다. 다시 추출하면 새 추출이 생기고 이전 추출의 블록·단위·판단은 읽기 전용으로 남는다. 이전 판단을 새 추출로 옮겨 오는 기능은 이번 범위 밖이고(내 판단), 이번 범위에서는 다시 추출 화면을 두지 않는다(추출기 개선 후 관리 작업으로만).

### 6.4 단위

- 단위는 **원문 블록 위의 범위 목록**이다. 범위 = (블록, 시작, 끝) 글자 위치. 나눈 단위는 부모 범위의 분할, 합친 단위는 원문 순서를 지킨 범위 목록이다. 그래서 글자가 생기거나 사라지지 않았는지 코드로 검사할 수 있다. **[추천 채택]**
- 종류: 문장 / 제목 / 그림 / 표 / 표의 행 / 칸 문장.
  - **표**는 표 하나를 한 단위로 잡고, 그 안의 칸 글자도 문장 단위(칸 문장)로 추적한다. 기본값은 표 전체를 한 곳으로 보내는 것이고, 행마다 다른 곳으로 보내야 하면 표 단위를 행 단위로 나눈다. **[추천 채택]** 칸 문장은 표·행의 보낸 곳과 상태를 따른다.
  - **레이아웃 표**: 본문을 배치하려고 쓴 표(예: 한/영 두 열, 단계 | Instruction | Why 열)는 데이터 표와 달리 칸 글을 일반 문단처럼 다룬다. 칸 문장마다 따로 배정하고, 표 단위를 만들지 않는다. 칸은 행 순서, 행 안에서는 왼쪽부터 읽으므로 한/영 두 열 표는 "한/영 연달아"처럼 이웃 짝이 된다. **기본값은 데이터 표**이고, 작성자가 표마다 레이아웃 표로 바꾼다. **(사용자 결정 2026-11-05: 본문이 표 안에 들어 있는 경우는 있지만 많지 않다)** 코드가 레이아웃 표를 판별해 제안하지는 않는다(드물어서, 내 판단).
  - **그림**은 캡션까지 묶어 한 단위다. 내용은 읽지 않고 보낸 곳만 정한다. 변경 종류는 "그대로"로 고정(삭제는 가능). **[결정]** 그림 단위는 언어 중립이다. 진행 숫자와 검토 조건에서는 한 줄로 한 번 센다(§6.5 커버리지). (사용자 결정 2026-11-12, 언어 축) 결과물에 한 번만 나오는 것은 결과물 작업(언어 축 (4))에서 바꾸고, 그때까지 결과물 A·B·C와 요약은 한글판·영어판 모두에 그림을 싣는다.
  - **제목**(제목 스타일 문단, 조항 번호만 있는 줄)도 커버 단위다. 아무 글자도 조용히 빠지지 않게 하기 위해서다. 구조용 제목은 여러 개를 골라 한 번에 "삭제(사유: 구조 제목)"로 처분할 수 있다(§7.7). (내 판단)
- **불변식(코드 검사)**: 한 추출 안에서 커버 단위들의 범위는 서로 겹치지 않고, 모든 블록의 공백이 아닌 글자를 빠짐없이 덮는다. 단위의 앞뒤 공백·줄바꿈은 범위에서 빼고, 단위 사이의 공백은 어느 단위에도 속하지 않는다. **[추천 채택]**
- 같은 문장이라도 위치가 다르면 다른 단위다. **[결정]**
- **단위는 제자리에서 바뀌지 않는다**: 나누기·합치기·경계 옮기기는 옛 단위를 은퇴시키고 새 단위를 만든다(이력과 낡은 AI 결과 판별을 위해). 은퇴한 단위의 판단은 이력으로 남고, 새 단위는 미배정에서 시작한다.
- **단위 ID**: 시스템이 붙이는 고유 번호. 화면·결과물용 표시 ID는 문서 안에서 읽기 쉬운 형태(문서 약칭 + 순번)로 빌더가 정한다.
  - 표시 ID 꼴: `<문서 번호, 없으면 D<문서 id>>-<순번 3자리>`(예: `SOP-QC-00005-012`). 편집으로 생긴 새 단위는 그 추출의 다음 순번을 받는다. (계획 1에서 정함)
- **경계 확인**: 단위마다 "경계 확인됨" 표시가 있다(①의 Enter). **검토 요청 조건이다**(§7.15) — 결과물과 Excel이 단위가 잘린 자리를 그대로 따르기 때문이다(사용자 결정, 2026-11-10. 그전에는 "판단 확정이 대신한다"고 보고 조건에 넣지 않았다). 세는 것은 글 범위가 있는 단위(문장·제목·그림·칸 문장)이고 표·행 묶음 단위는 세지 않는다. 판단 확정은 경계 확인을 대신하지 않으며, 편집(나누기·합치기·AI 나눔 확정)으로 새로 생긴 단위는 확인 안 된 상태로 시작한다. 한 문서의 남은 단위는 한 번에 확인할 수 있고(작성자, 작업 중) 작업 기록에 `unit.check_all`(문서 id·건수)로 남는다 — 하나씩 누른 확인은 기록하지 않는다. 경계 확인·확인 취소·모두 확인은 편집과 같은 되돌리기 기록에 한 줄 순서로 들어간다(바뀐 단위만, 문서 revision은 그대로 — 사용자 결정 2026-11-13). 되돌리기 응답은 무엇을 거꾸로 했는지(`op`)와 표시가 바뀐 단위를 실어 화면이 알리고 그 Unit으로 돌아간다.

### 6.5 언어와 짝

- **[결정]** 옛 문서와 새 문서 모두 기본적으로 한글과 영어가 함께 적혀 있다. 한글판과 영어판이 따로 파일로 오지는 않는다. **(사용자 결정 2026-11-05)** 그래서 짝은 언제나 한 문서 안에서 맺는다.
- 문서마다 **언어 배치**를 고른다: `ko_en_interleaved` "한/영 연달아", `ko_en_separate` "한/영 따로", `en_only` "영어만", `ko_only` "한글만". 이름은 임시다. **[결정]**
- 단위마다 **언어 속성**(KO | EN, 그림·표는 중립)이 있다. 기본값은 글자를 보고 코드가 판정하고(§7.4), 틀린 단위는 사람이 단위별로 바꾼다(쪼개기 그 자리 메뉴, §7.5). **[결정]** 언어는 구조·규칙의 축이 아니라 시스템이 뒤에서 쓰는 속성이다(짝 제안, 번역 판정, 글꼴). 용지·목록 어디에도 언어 표시(KO·EN 글자와 색 막대)를 붙이지 않는다 — 한글인지 영어인지는 글자를 보면 안다. (사용자 결정 2026-11-12, 언어 축)
- **짝**: 한글 단위 집합 ↔ 영어 단위 집합(보통 1:1, 한 문장이 다른 언어로 두 문장이 되는 경우를 위해 작은 다대다를 허용한다, 내 판단). 한 단위는 짝 하나에만 속한다. 상태는 제안(코드 또는 AI) / 확정.
  - 한/영 연달아: 코드가 이웃한 한글·영어 단위를 짝으로 제안한다. **[추천 채택]**
    - 한글 묶음은 바로 뒤에 오는 영어 묶음과만 짝을 짓고, 짝은 부분(본문·머리말·꼬리말·각주)이나 표 경계를 넘지 않는다. (계획 1에서 정함)
  - 한/영 따로: 임베딩으로 짝을 제안하고 사람이 확인한다(계획 2). 임베딩이 없으면 사람이 손으로 잇는다.
- 짝은 같은 일을 두 번 하지 않게 하는 장치다. 한쪽을 배정하면 짝에도 같은 배정을 제안하고, 짝은 한 화면에 함께 보이고 한 번에 확정할 수 있다. 확정 기록은 언어별(단위별)로 남는다. **[추천 채택]**
  - **짝은 한 곳으로 간다 — 한 줄의 처분은 늘 하나다.** 판단을 쓰는 길(관계 묶음 저장, 여러 개 한 번에 삭제·이동, 입구 2 한 번에 확정, 짝 만들기·AI 짝·이웃 짝 제안) 끝에 서버가 그 짝을 본다(`pair_settle.settle_pairs`). 미배정이 아닌 구성 단위들의 운명(처분, 이동 대상 문서 번호, 새 문장이 놓인 **새 문서의 집합**)이 다르면 짝을 풀고(`pair.delete`, 판단은 그대로), 제안 짝의 구성 단위가 모두 같은 운명으로 확정이면 짝도 확정한다(`pair.confirm`, AI 짝 제안이면 채택 기록 §6.11). 따로 누르는 짝 확인 단추는 없다 — 줄을 확정하면 짝도 확정이다. 갈림의 기준은 새 문서까지이고, 같은 새 문서 안에서 칸·단계·절이 다른 것은 갈린 것이 아니다(한/영 따로인 새 문서에서는 두 언어가 다른 절에 놓이는 것이 정상). (사용자 결정 2026-11-12, 언어 축)
  - 이미 서로 다른 운명으로 판단된 단위들을 사람이 짝으로 묶으면 409 `pair_fates_differ`로 거절하고(한쪽 배정을 먼저 바꾼다), AI 짝·이웃 짝 제안은 그런 쌍을 제안하지 않는다. 짝을 맺은 결과 구성 단위가 모두 같은 곳으로 확정돼 있으면 그 자리에서 확정 짝이 된다. (내 판단 2026-11-13, 언어 축)
  - **한 언어만 이을 때 (사용자 결정 2026-11-10)**: 정상 흐름은 두 언어가 함께 이어지는 것이고, 이것은 그렇지 않은 경우의 대응이다. 옛 단위는 짝인데 이미 쓴 새 문장이 한 언어로만 있으면(입구 2) 있는 언어만 이어 확정하고 그 짝을 푼다. 판단이 없던 다른 언어 단위는 미배정인 제 줄로 남아 사람이 삭제(사유)나 보류로 끝낸다. 짝 풀기는 서버가 그 저장 안에서 한다 — 화면이 남는 단위를 저장 요청의 `release_unit_ids`에 실어 보낸다(이 묶음 옛 문서의 단위만 받는다). 한쪽만 저장하고 다른 쪽이 아직 미배정인 것만으로는 풀지 않는다. 이미 판단이 있는 다른 언어 단위는 판단을 그대로 두고, 운명이 갈리면 위 규칙대로 짝만 푼다. 짝 풀기는 기록에 `pair.delete`로 남는다. (사용자 결정 2026-11-12, 언어 축)
- **커버리지는 줄로 한 벌 센다.** (사용자 결정 2026-11-12, 언어 축 — 킥오프의 "언어별로 따로 센다 [결정]"을 대체) 줄은 짝 하나 전체, 또는 짝이 없는 "판단을 받는 단위" 하나다(배정 화면의 줄과 같다). 판단을 받는 단위는 문장·제목·그림·레이아웃 표의 칸 문장, 그리고 데이터 표(행으로 나눴으면 행)이고, 데이터 표에 묶인 칸 문장은 따로 세지 않는다. 제안 상태 짝도 한 줄이라 짝을 맺거나 풀면 전체 줄 수가 바뀐다.
  - 줄의 상태는 구성 단위 중 가장 덜 끝난 것이다: 미배정 → AI 제안 → 보류 → 확정 순으로 앞선 것. 서버(`status.pick_row_status`, 진행 숫자 SQL)와 배정 화면(`STATUS_RANK`)이 같은 순서를 쓴다. (내 판단 2026-11-12, 언어 축)
  - 진행 숫자(묶음 목록·개요·관리 화면)는 `{total, unassigned, ai_suggested, confirmed, on_hold, single_language}` 한 벌이다. 묶음 목록의 확정 열도 하나다.
  - **보조 표시 "한 언어만 있는 줄"**(`single_language`): 언어 배치가 한/영 연달아 또는 한/영 따로인 옛 문서에서 짝도 다른 언어 새 문장도 없는 글 단위(문장·제목) 수다. 개요 Coverage 아래 작은 글 한 줄이고 검토 요청 조건이 아니다. "한/영 따로" 문서는 `AI pair`를 누르기 전까지 이 숫자가 크다. (사용자 결정 2026-11-12, 세는 법은 내 판단)
  - 결과물 요약 숫자(`/summary`)는 결과물 작업(언어 축 (4))까지 언어별로 남는다. 그 사이 개요·목록의 줄 숫자와 결과물 요약 숫자는 다르게 보이고, 이 상태는 개발 스택에만 둔다.
- 짝이 없는 단위는 배정 화면과 숫자에서 한 줄이다. 결과물에서 한 줄로 놓는 것은 결과물 작업(언어 축 (4))이고, 그때까지 결과물은 자기 언어 표에만 싣는다. 고쳐 쓰기도 그 언어로만 제안한다. **[추천 채택]**
- 한 언어로만 된 원문이나 짝이 없는 단위가 있어도, 반대 언어를 채워야 완료되는 것은 아니다. 번역은 오너가 요청할 때만 만든다(§7.9). **[결정]** (킥오프 원문의 이 문장 뒷부분은 촬영 누락이라, §6③4 "번역 제안은 오너가 방향을 골라 요청한다"에 맞춰 읽었다. 내 판단)

### 6.6 To-Be 목록

- 입구 1에서 분류를 시작하기 전에 묶음의 To-Be 목록을 넣는다. **[결정]** 분류가 "새로 판단하기"에서 "정해진 칸 중에서 고르기"로 바뀌어 AI가 틀릴 여지가 크게 준다.
- **새 문서 한 줄**: 문서 번호(없으면 임시 코드, 묶음 안에서 유일), 제목, 종류 SOP | WI, WI라면 부모 SOP(같은 묶음의 SOP, 필수), 입구(`assign` 입구 1 | `match` 입구 2), 장비 SOP 여부(SOP만), 순서. 입구 2 문서는 올린 새 문서 파일과 이어진다.
- **SOP 칸**: 도메인 문서 §2의 일곱 칸과 권장 하위 칸(칸 키 고정, 사용자 정의 칸 없음, 내 판단). 칸마다 N/A 표시를 사람이 사유와 함께 남길 수 있다. AI는 N/A를 정하지 않는다. 장비 SOP에서 Procedures 아래 세 하위 칸이 비어 있고 N/A도 아니면 경고한다(완료를 막지는 않는다, 내 판단). **[결정: 회의 자료의 구조]**
- **WI**: 정해진 칸이 없다. 위치는 "몇 번째 단계의 Instruction" 또는 "몇 번째 단계의 Why"다. 오너가 단계(번호, 선택적 제목)를 미리 적어 두면 그 단계에 배정하고, 적지 않았으면 WI에 배정하고 단계 순서는 결과물 C에서 정한다. 옛 문장 중 이유를 설명하는 문장은 해당 단계의 Why 후보다. **[결정·추천 채택]**
- **고정 처분**: "삭제"(사유 필수)와 "다른 문서로 이동"(이번 묶음 밖 SOP, 대상 문서 번호와 사유 필수). 이동은 대상 문서 번호만 기록하고 다른 묶음의 결과물에 자동으로 넣지 않는다. **[추천 채택]**
- 목록은 API로 입력하거나 Excel 템플릿으로 가져온다(§7.6). **[추천 채택]** 입구 2에서는 올린 새 문서로 목록 줄이 만들어진다.
- 이미 새 문장이 들어간 새 문서를 목록에서 지우거나 SOP↔WI 종류를 바꾸는 변경은 거절한다(먼저 옮기거나 비운다, 내 판단).
  - AI 제안 상태의 새 문장과 번역 새 문장도 "들어간 새 문장"으로 센다. 문서 하나를 AI로 분류한 뒤에는 그 문서를 지우기 전에 줄마다 비워야 하고, 번역이 든 입구 2 새 문서를 지우는 것도 거절(409 `doc_has_targets`)한다. (계획 2에서 정함)

### 6.7 처분·새 문장·출처

결과물 A·B·C는 모두 아래 세 가지에서 계산된다.

- **단위 판단(unit decision)**: 커버 단위(그리고 칸 문장의 보낸 곳을 담는 표·행 단위)마다 하나. 처분, 이동 대상 문서 번호, **Remark**(삭제·이동·중복 배정·표 구성 변경 시 필수, 그 밖의 배정에서는 선택 — 예전의 "사유"를 넓힌 것이고 열은 하나다, 저장 칸 이름은 `reason` 그대로. 짝인 줄은 같은 글을 구성 단위의 판단마다 싣는다. 사용자 결정 2026-11-12, 언어 축), 상태(§6.8), 보류 사유, 근거가 된 AI 제안, 확정한 사람·시각, `revision`.
- **새 문장**: 새 문서, 위치, 순서, 언어, 종류(문장 | 표 | 그림), **확정 문장**, **AI 제안 문장**(확정 문장으로 덮어쓰지 않고 따로 보관 **[결정]**), 변경 종류, 기원(`units` 옛 단위에서 / `translation` 번역 / `new_doc` 입구 2 새 문서에서), 번역 출처 단위, 입구 2 새 단위, 상태, **Remark**(`remark`, 선택 — 단위 판단이 없는 출처 없는 새 문장, 곧 입구 2의 신규에도 글을 적게 하려는 칸, Alembic `0013`. 사용자 결정 2026-11-12, 언어 축), `revision`.
  - 문장 새 문장의 언어: 입구 2와 번역 새 문장은 행의 언어로 잠겨 있다. 입구 1 새 문장은 요청이 실어 보낸 언어, 비웠으면 기존 새 문장의 지금 언어(되돌리면 사람이 쓴 번역이 조용히 출처 언어가 된다), 새로 만드는 새 문장은 출처가 한 언어면 그 언어, 섞였으면 글자로 판정한다. 문장에는 `neutral`을 두지 않는다 — 보낸 `neutral`은 보내지 않은 것으로 본다(중립 문장은 번역이 될 수 없고 결과물 두 판에 다 나간다). 표·그림은 중립이다. (내 판단 2026-11-13, 언어 축)
- **출처 연결**: (새 문장, 옛 단위, 순서) 다대다. 나눔은 한 단위 → 여러 새 문장, 합침은 여러 단위 → 한 새 문장이다. **[결정]** "한 단위가 여러 문장으로 나뉘거나 여러 단위가 한 문장으로 합쳐지면 관련된 줄을 관계 묶음 ID로 묶는다."
- **문장 이력**: 확정 문장이 바뀔 때마다 이전 글자와 누가·언제를 남긴다(작업 기록 §6.12와 "누가 무엇을 왜 바꿨는지"를 위해).
- **표와 그림의 새 문장 (내 판단)**: 표(또는 행) 단위의 보낸 곳에는 "표" 종류 새 문장 하나가 생기고, 칸 문장마다 그 아래에 칸 좌표를 가진 일반 새 문장이 붙는다. 칸 문장의 새 문장은 일반 문장과 똑같이 고쳐 쓰기·번역·문장 검사 대상이고, 언어는 칸 문장의 언어다. "표" 종류 새 문장 자체는 언어 중립이고 글자 대신 칸 구성(행·열)을 가지며, 변경 종류는 "그대로" 또는 "표 구성 변경"(이유 필수)이다. 그림의 새 문장은 언어 중립 "그림" 종류이고 글자를 고치지 않는다.

**입구 2의 모양**: 새 문서를 추출하면 시스템이 새 커버 단위마다 새 문장을 하나씩 만든다(확정 문장 = 새 문서의 원문 그대로, 기원 `new_doc`, 위치 = 새 문서의 실제 절 위치, 즉 그 단위 앞에 있는 제목들의 경로와 문서 안 순서). 새 문서의 머리말·꼬리말은 양식 반복이라 새 문장을 만들지 않고, 제목은 새 문장이 아니라 위치(절)를 정하는 데 쓴다(내 판단). 짝 맞추기는 이 새 문장들에 출처 연결을 붙이는 일이다. 그래서 두 입구가 같은 표를 채우고 결과물 계산이 하나다. 고쳐 쓰기는 이미 끝났으므로 새 문서의 문장이 확정 문장이 되고, AI는 변경 종류만 제안한다. **[결정]**

입구 2 새 문장은 쪼개기 편집이 있을 때마다 그 새 문서 전체를 다시 맞춘다(절 경로·언어·칸 부모·좌표·순서). `revision`은 절 경로·언어·칸 부모·좌표가 바뀐 새 문장만 오르고 순서만 바뀐 새 문장은 오르지 않는다. (계획 1에서 정함)

**변경 종류 [결정: 목록]**: 그대로 / 말투 / 고쳐 씀 / 나눔 / 합침 / 번역 / 삭제 / 신규 / 표 구성 변경. 누가 정하나(내 판단):
- 구조에서 나오는 종류는 코드가 계산하고 사람이 바꾸지 않는다: 나눔(한 단위가 같은 새 문서 안 **자기와 같은 언어의** 새 문장 둘 이상으로), 합침(출처가 둘 이상), 번역(기원 번역이거나, 출처 하나인 문장 새 문장의 언어가 출처 단위 언어와 다를 때 — 어느 쪽이든 중립이면 아니다), 신규(출처 없음, 입구 2), 삭제(처분 삭제). 순서는 번역 기원 → 신규 → 표·그림 → 합침 → 언어가 다름(번역) → 나눔 → 글자 비교 종류다. 그래서 영어 옛 문장 하나를 새 문서의 한/영 짝에 이으면 영어 새 문장은 글자 비교 종류, 한글 새 문장은 "번역"이다. (사용자 결정 2026-11-12, 언어 축 — 언어로 막지 않고 이은 대로 적는다)
- 글자 비교 종류는 사람이 정하고 AI가 제안한다: 그대로 / 말투 / 고쳐 씀. 확정 문장이 출처 원문과 글자까지 같으면 코드가 "그대로"로 둔다.
- 표 구성 변경은 표 종류 새 문장에 사람이 정하고 이유를 남긴다. 칸 단위 재구성의 세부 모형은 이번 범위 밖이고 이유 글로 기록한다.
- 표의 "그대로"는 원문 격자와 칸 자리가 같을 때만 쓸 수 있고, 아니면 "표 구성 변경"과 이유가 필요하다. 글이 출처 하나와 다른 문장은 "그대로"가 될 수 없다. "그대로"인 표는 칸 문장마다 칸 새 문장이 있어야 한다. (계획 1에서 정함)
- 다른 문서로 이동한 줄은 변경 종류를 비우고 "보낸 곳 종류" 칸에 이동으로 적는다.

### 6.8 상태 규칙

- 커버 단위와 새 문장은 **정확히 하나의 상태**를 갖는다: `unassigned` 미배정 / `ai_suggested` AI 제안 / `confirmed` 확정 / `on_hold` 보류. 칸 문장은 자기 표·행 단위의 상태를 따른다. **[결정]** "옛 단위마다 상태가 정확히 하나"를 테스트로 보인다.
- **사람의 저장 단위는 관계 묶음이다**: 사람이 판단을 저장할 때는 서로 이어진 단위·새 문장 전체(관계 묶음)를 한 번에 보낸다. 서버는 묶음이 닫혀 있는지(보낸 새 문장의 모든 출처가 보낸 단위 안에 있고, 보낸 단위의 모든 새 문장이 보낸 묶음 안에 있는지) 검사하고, 통과하면 전체를 `confirmed` 또는 `on_hold`로 둔다. 합침을 반만 확정하는 상태가 생기지 않는다. (내 판단)
  - 닫힘은 묶음 읽기와 같은 그래프(출처 연결 + 표↔칸 새 문장 연결)로 본다. (계획 1에서 정함)
- 전이:
  - 미배정 → AI 제안(AI) | 확정(사람) | 보류(사람, 사유)
  - AI 제안 → 확정 | 보류(사람) | AI 제안(더 새로운 AI 제안이 덮음)
  - 확정 → 확정(사람이 고침, 이력 남음) | 보류(사람)
  - 보류 → 확정(사람)
  - 어느 상태든 → 미배정: 사람이 "배정 지우기"를 하거나, 쪼개기 편집으로 단위가 은퇴해 새 단위가 생길 때
- **AI는 사람의 것을 덮지 않는다**: AI 결과는 미배정 단위에, 또는 **같은 종류** AI 작업의 이전 제안 위에만 들어간다(입구 2 짝 제안이 분류 제안을 덮거나 그 반대가 되지 않는다). 확정·보류 단위에 새 제안을 받으려면 사람이 먼저 배정을 지운다. (내 판단)
- 확정 버튼은 일반 버튼이다. 전자서명이나 재인증은 없다(§10). **[결정]**

### 6.9 관계 묶음과 중복 배정

- **관계 묶음** = 단위–새 문장 연결 그래프의 연결 요소 중 단위가 둘 이상이거나 새 문장이 둘 이상인 것. ID는 구성원에서 결정적으로 만든다(예: 구성 단위 중 가장 앞선 표시 ID 기준). 따로 저장해 어긋날 상태를 만들지 않는다. (내 판단)
- **중복 배정** = 한 옛 단위의 새 문장들이 **서로 다른 새 문서 둘 이상**에 있는 경우. 같은 새 문서 안에서 여러 문장으로 간 것은 나눔이다. 중복 배정은 이유를 적어야 저장된다. **[추천 채택: 이유 필수]** (정의는 내 판단)

### 6.10 지침·프롬프트 버전

- 앱이 지침(도메인 문서의 규칙 ID 체계)과 프롬프트를 **버전으로** 관리한다. 키별(예: `rules`, `prompt.classify`, `prompt.translate`, `prompt.match`, `prompt.split`) 버전 번호·내용·메모·만든 사람·시각, 키마다 활성 버전 하나. **[추천 채택]**
- `prompt.pair` 키는 만들지 않는다. 한/영 짝(§7.11)은 임베딩만 쓰고 LLM을 부르지 않기 때문이다. LLM을 붙이면 그때 키를 더한다. (계획 2에서 정함)
- 처음 기동 때 저장소의 시드 파일에서 첫 버전을 만든다. 이후 버전은 `guideline.manage` 권한자가 올리고 활성화한다(화면은 프런트 단계).
  - 같은 키의 활성화는 키를 잠가 한 번에 하나씩 일어나고, 이미 활성인 버전을 다시 활성화하면 활성화한 사람·시각을 덮지 않고 성공한다. 동시 활성화가 활성 버전 둘을 만들지 않게 한다. (계획 2에서 정함)
- 모든 AI 제안은 사용한 지침·프롬프트 버전을 기록한다. 버전을 바꿔도 이전 제안 기록은 그대로다.

### 6.11 AI 작업과 제안 (계획 2)

- **AI 작업(job)**: 묶음, 종류(분류 `classify` / 번역 `translate` / 입구 2 계획 `match_plan` / 입구 2 짝 맞추기 `match` / 한·영 짝 `pair` / 복합 문장 나누기 `split`), 대상 단위·문장, 입력 스냅샷(대상의 `revision`과 해시), 상태(`queued` | `running` | `done` | `failed` | `stale` | `cancelled`), 시도 횟수, 정제된 오류(주소·토큰 없이), 요청한 사람.
  - 입구 2는 작업 둘로 돈다. `match_plan`은 LLM을 부르지 않고 묶음의 옛 단위와 새 문장을 코드로 묶어(임베딩이 켜져 있으면 임베딩, 아니면 글자 유사도) 표·그림·짝 없는 항목의 제안을 바로 쓰고, 문장 그룹마다 `match` 작업을 쌓는다. `match`가 LLM에 변경 종류만 묻는다(§7.10). (계획 2에서 정함)
- **AI 제안**: 작업 결과 하나. 내용(보낸 곳, 이유, 규칙 ID, 근거 위치, 고쳐 쓴 문장, 변경 종류 등), 검사 결과와 경고, **기록 필드**: 입력 문서 버전(파일 해시와 추출 ID), 지침·프롬프트 버전, 모델, 시각, 결과, 이후 확정한 사람과 채택 여부(`as_is` 그대로 채택 / `edited` 고쳐서 / `rejected` 버림). **[추천 채택]** 채택률(§13)은 여기서 계산한다.
  - 내용에는 분류의 고쳐 쓴 문장 `rewrites`(`ko`·`en` 목록)와 번역한 글 `text`가 들어간다. 새 제안이 이전 제안을 밀어내거나 단위가 은퇴하면 그 글이 남는 곳이 제안 기록뿐이다. 경고는 문장 검사(§7.12)와 같은 모양(`kind`·`source`·`target`)이라 Excel 내보내기가 그대로 읽는다. 무효 제안은 응답 원문을 보관하지 않고 경고에 종류 코드와 정리한 값만 둔다. (계획 2에서 정함)
  - 같은 종류의 새 제안이 이전 제안을 덮으면 이전 제안의 `result`가 `stale`이 된다(채택이 이미 남은 제안은 `applied` 그대로 둔다). 안 그러면 밀린 제안이 `applied`로 남아 채택률의 `pending`이 줄지 않는다. 그래서 제안 목록의 `applied`는 지금 살아 있는 제안만 뜻한다. (계획 2에서 정함)
  - **채택은 사람의 저장이 제안과 어떻게 다른지로 코드가 정하고, 처음 정한 판정이 남는다**(뒤의 저장은 제안이 아니라 사람의 글을 고친다). 보류는 결정이 아니라 기록하지 않는다. 종류별 규칙(계획 2에서 정함):
    - 분류: 제안한 처분이 저장에 없거나 새 문장이 모두 사라졌거나 모두 다른 자리면 버림, 처분·자리·글·출처가 같으면 그대로, 그 밖은 고쳐서. 짝 하나를 한 제안이 맡으므로 짝 한쪽만 배정을 지워도 그 제안은 버림이고, 나중에 다른 쪽을 그대로 확정해도 먼저 정한 판정이 남는다. 일괄 삭제·이동(§7.7)도 보류 중이던 제안 단위의 채택을 남긴다(제안과 같은 처분이면 그대로, 아니면 버림). (계획 2에서 정함)
    - 번역: 확정한 글이 제안 글 그대로면 그대로, 고쳤으면 고쳐서, 번역을 지우면 버림. (계획 2에서 정함)
    - 입구 2(`match`): 새 문장의 글·자리가 잠겨 있어 출처만 견준다. 같으면 그대로, 출처가 모두 비면 버림, 그 밖은 고쳐서. 짝 하나(1:1)와 표는 변경 종류까지 견주므로 같은 출처에 다른 종류를 고르면 고쳐서다. 삭제 후보는 처분만 견준다. 표는 제안 기록에 칸 연결이 없어 표 새 문장만 견주므로, 표 구성 변경 제안에서 칸 연결만 고친 저장은 그대로로 센다(표 채택률이 조금 높게 잡힌다). (계획 2에서 정함)
    - 한/영 짝: 확정하면 그대로, 풀면 버림. 사람이 만든 짝이 AI 짝을 대신하면 단위 집합이 같을 때 그대로, 다르면 버림. (계획 2에서 정함)
    - 나누기: 자동 판정이 없다. 제안이 단위·판단·새 문장을 만들지 않아서, 사람이 `POST /suggestions/{id}/adoption`으로 직접 남긴다(§7.11). (계획 2에서 정함)
  - 작업이 끝난 뒤 은퇴한 단위의 제안은 `applied`에 채택이 빈 채로 남고 `pending`에 세지 않는다(결정할 주체가 없다). `as_is`·`edited`·`rejected`는 제안의 `result`와 상관없이 세므로 `applied`는 나머지 숫자의 합이 아니다. (계획 2에서 정함)
- **임베딩 캐시**: (모델, 글자 해시) → 벡터. 같은 글을 다시 보내지 않는다.

### 6.12 작업 기록

- 묶음마다 추가만 하는 사건 기록: 누가·언제(KST)·무엇(단위 나누기·합치기, 판단 확정·보류·지우기, 문장 고침, To-Be 변경, 멤버 변경, 상태 전이, AI 작업 요청·취소·다시 시도, Excel 내보내기)·대상 ID·사유. 글자 내용은 문장 이력(§6.7)이 갖고 사건 기록은 ID로 가리킨다.
- AI 결과 적용과 채택은 사건 기록에 쓰지 않는다. `ai.request`·`ai.cancel`·`ai.retry`만 남기고 적용·채택 내역은 AI 제안 기록(§6.11)이 맡는다. 기록 조회 상한이 500이라, 큰 분류 한 번의 적용이 사람의 기록을 밀어내지 않게 하려는 것이다. (계획 2에서 정함)
- 묶음 삭제는 묶음 밖의 전역 기록에 남긴다(누가·언제·어떤 제목의 묶음을). (내 판단)
- **애플리케이션 로그**(stdout)에는 원문 글자와 인증값을 남기지 않는다. ID·건수·상태 코드만 남긴다. **[추천 채택]**

### 6.13 동시 편집

- 여러 작성자가 한 묶음을 함께 고친다. 다른 사람이 먼저 바꾼 내용을 덮어쓰지 않도록, 바뀌는 대상마다 `revision`을 두고 변경 요청은 기대 `revision`을 싣는다. 다르면 409와 현재 상태를 돌려준다. **[추천 채택]**
- 범위(내 판단): 문서의 단위 집합(쪼개기 편집) = 문서 `revision`, 판단·새 문장 = 각자의 `revision`, 묶음 설정·To-Be 목록 = 묶음 `revision`.
- 409 응답은 충돌한 대상마다 `current_revision`을 싣고, 화면은 그 대상을 다시 읽는다. (계획 1에서 정함)
- 늦게 온 AI 응답은 요청 대상 ID와 `revision`을 확인한 뒤에만 적용한다(§8.3).

## 7. 단계별 동작

### 7.1 업로드와 거절

- 기본 입력은 DRM이 없는 DOCX다. 추출 품질은 DOCX에 집중한다. **[결정]** 텍스트 PDF도 받되 보조로 지원한다. **[추천 채택]**
- 다음은 이유를 알리고 거절한다. 빈 추출을 성공으로 처리하지 않는다. **[추천 채택]**
  - 암호나 DRM이 걸린 파일(ZIP이 아닌 DOCX 포함), 스캔 이미지 PDF, 암호화 PDF
  - 변경 추적(`w:ins`, `w:del`)이 남은 DOCX: "변경 내용을 모두 수락하거나 거부한 뒤 다시 올려 주세요"(어느 쪽을 기준으로 할지 정하기 전에는 진행하지 않는 쪽이 안전하다는 이전 시도의 결론, 내 판단)
  - altChunk(다른 문서를 끼워 넣은 것)가 있는 DOCX
  - 아래 제한을 넘는 파일, 형식이 맞지 않는 파일
- **제한(부하 검증 전의 추천값, env로 조정 가능)**: 파일 하나 25 MiB, DOCX 압축 해제 합계 200 MiB, PDF 500쪽, 문서 하나 200만 자, 파싱 한 번 60초. **[추천 채택]** ZIP 항목 수와 압축 비율 상한은 빌더가 정한다.
- 파싱은 **별도 프로세스**에서 시간 제한을 걸고 돌려, 이상한 파일이 백엔드 프로세스를 멈추거나 메모리를 다 쓰지 못하게 한다(내 판단). 업로드 요청이 추출 결과까지 기다렸다가 돌려준다(보통 몇 초, 내 판단).
- 메인 추출과 MarkItDown은 시간 제한을 따로 가진 두 자식 프로세스에서 차례로 돌고, 동시에 도는 파싱은 최대 2개다(메모리). (계획 1에서 정함)
- 파서가 예상 밖 예외를 내면 그 문서는 `failed`(사유 `parse_error`)이고 예외 클래스 이름만 남긴다. (계획 1에서 정함)
- 업로드는 묶음 상태가 작업 중일 때만 된다. 문서를 지우면 그 단위·판단·출처 연결이 함께 지워지고, 확정된 판단이 있으면 명시적 확인 플래그가 있어야 지운다(내 판단).

### 7.2 메인 추출기

**[결정]** 메인은 원문 위치와 원문 글자를 그대로 보존하는 자체 추출기다. 단위·ID·커버리지 계산은 모두 메인 결과로 한다.

**DOCX**: XML을 직접 읽는다. 이전 시도에서 확인한 함정을 처음부터 반영한다.
- ZIP 안전 검사를 먼저 한다: 파일 크기, 압축 해제 크기, 항목 수, 압축 비율, 경로 이상(`..` 등). XML은 DTD와 외부 엔티티를 금지하고 파싱한다.
  - ZIP 항목은 선언한 크기까지만 읽고, 크기를 속인 파일은 `unsafe_zip`으로 거절한다. (계획 1에서 정함)
- 본문(`word/document.xml`) 외에 머리말·꼬리말·각주·미주를 별도 부분으로 추출하고 본문과 구별한다.
- 텍스트 상자 글(`w:txbxContent`)은 따로 추출해, 상자가 들어 있는 문단에 같은 글이 두 번 들어가지 않게 한다. `mc:AlternateContent`의 Choice와 Fallback은 같은 내용을 두 번 담으므로 하나만 읽는다.
- 필드 코드(`w:instrText`)는 원문 글이 아니므로 읽지 않고 필드 결과만 읽는다.
- 병합 셀(`w:gridSpan`, `w:vMerge`)은 같은 글이 여러 칸에 중복으로 만들어지지 않게 하고 경고를 붙인다. 표 안의 표도 경로를 남겨 읽는다.
  - 세로 병합(`w:vMerge`)으로 이어지는 칸에 글이 있으면 버리지 않고 제자리 칸 블록으로 내며 경고 `merged_cell_content`를 붙인다. 비어 있는 이어지는 칸은 블록을 만들지 않는다. (계획 1에서 정함)
- 자동 번호(`w:numPr`, 스타일에 걸린 번호 포함)는 목록 정의(`numbering.xml`)로 표시 번호를 계산해 **문단 글 앞에 써 넣는다**(`1.` `1.1` `a)` `가.` `•` — 본문·표 칸 문단 모두). 카운터는 문서 순서로 세고 위 수준이 나아가면 아래 수준은 처음부터 다시 센다. 글머리표는 글꼴에 매인 기호 대신 `•`로 쓴다. 번호를 풀지 못한 문단(목록 정의가 없거나 깨짐)만 번호 없이 두고 경고 `auto_numbering`을 붙인다. 위치는 항상 XML 경로로 남긴다. 섹션 번호는 글에 적힌(또는 써 넣은) 조항 번호를 쓰고, 없으면 가장 가까운 제목 글을 쓴다. (사용자 피드백 2026-11-10: 번호가 화면·결과물에 보이지 않아 원문과 대조하기 어려웠다 — 처음에는 계산하지 않고 경고만 붙였다)
- 머리말·꼬리말 블록에는 그 부분을 쓰는 구역과 종류(기본·첫 쪽·짝수 쪽)를 표시 `section_ref:<구역>:<종류>`로 남긴다. 쪼개기 화면이 부분 파일마다 묶어 보여 주고, 내용이 같은 머리말은 한 번만 보여 준다(블록·단위는 그대로 둔다).
- 쪽 번호는 Word가 마지막으로 저장한 쪽 나눔(`w:lastRenderedPageBreak`)을 우선 쓰고, 없으면 수동 쪽 나눔, 둘 다 없으면 추정 쪽임을 표시한다. 근거 위치에는 쪽 번호보다 XML 경로를 쓴다.
- 블록의 XML 경로는 500자까지만 싣는다. 넘으면 첫 마디 + `/…/` + 끝부분으로 줄인다. (계획 1에서 정함)
- 그림·도형(`w:drawing`, `w:pict`, `w:object`)은 그림 블록으로 만들고, 캡션(캡션 스타일 또는 "그림/Figure n" 꼴의 이웃 문단)을 묶는다. 표시용으로만 이미지 바이트를 꺼내 줄 수 있다(내용은 읽지 않는다).
  - 표 칸 안의 그림은 표에 묶지 않고 칸 블록 바로 뒤에 그림마다 그림 블록(캡션은 묶지 않는다)으로 내며, 독립 그림 단위가 된다. (계획 1에서 정함)

**PDF (보조 지원)**: 텍스트 PDF만. 쪽마다 빈 줄(공백만 있는 줄 포함)을 기준으로 문단 블록을 나눈다. 줄을 조용히 이어 붙이지 않는다(블록 안 줄바꿈 보존). 다단·표·읽기 순서는 실제 배치와 다를 수 있다는 경고를 문서에 붙인다. 표 구조는 만들지 않는다. **[추천 채택]**

PDF의 폼 객체 안 글자도 글자 배치를 분석해 읽어, 줄·낱말이 붙지 않게 한다. (계획 1에서 정함)

### 7.3 보조 추출기 (MarkItDown) 대조

**[결정]** 두 추출기를 함께 쓴다. 보조는 MarkItDown(Microsoft, MIT)이다.
- **추출 누락 검사 [추천 채택]**: 같은 파일을 MarkItDown으로도 변환해, 그 글자가 메인 단위에 모두 들어 있는지 코드로 대조한다. 메인에 없는 글자가 있으면 가장 가까운 메인 블록 위치에 "추출 누락 의심" 경고를 띄운다. 메인 결과를 자동으로 고치지는 않는다. 정규화·비교 단위·경고 기준은 빌더가 정하고 합성 데이터로 검증한다.
- 경고는 사람이 하나씩 "확인함(메모)"으로 닫는다. 닫지 않은 경고가 있으면 검토 요청을 할 수 없다(§7.15). 기계적 커버리지와 사람의 의미 검토를 따로 보이라는 이전 시도의 교훈 때문이다(내 판단).
- 한 문서의 "추출 누락 의심" 경고는 200개까지만 만들고, 넘으면 닫을 필요 없는 경고 `missing_text_truncated` 하나로 알린다. (계획 1에서 정함)
- 보조 추출이 실패해도 작업은 계속하고 "보조 검사 못 함"으로 표시한다. **[추천 채택]**
- **표 표현 (추천 변경 제안, 내 판단)**: 킥오프는 표를 MarkItDown으로 Markdown 표로 바꿔 화면 미리보기와 LLM 입력에 쓰라고 추천했다. 이 설계는 **메인 추출기의 칸 격자에서 Markdown 표를 직접 만든다**. 근거: 메인 격자는 칸마다 단위 ID·위치가 붙어 있어 AI가 인용한 칸을 정확히 되짚을 수 있고, MarkItDown은 병합 셀을 펼쳐 같은 글을 여러 칸에 복제하므로 커버리지·근거 위치와 어긋난다. 목적("AI가 행과 열을 이해한 채로 분류")은 그대로 지킨다. MarkItDown의 표 출력은 누락 대조에만 쓴다.
- MarkItDown은 DOCX·PDF 변환기만 쓰고, 외부 서비스를 부르는 기능(LLM 이미지 설명, 클라우드 문서 인식, URL 가져오기)은 켜지 않는다. 메인으로 쓰지 않는 이유(위치 정보 없음, 병합 셀 펼침, PDF는 표 구조 없이 글자만, 공백·기호 변경)는 **설치하는 버전으로 직접 확인**한다. 설치 시 딸려 오는 의존성(파일 형식 판별 모델 등)과 메모리 사용량도 확인해 기록한다. **[결정·추천 채택]**

### 7.4 규칙 기반 쪼개기와 언어 판정

- 코드가 문단, 조항 번호, 표 구조, 문장 끝 규칙으로 먼저 자른다. 한글(`~다.`, `~음.`, `~함.` 등)·영어 문장 끝 규칙을 쓰되, 소수점·약어(`e.g.`, `i.e.`, `No.`, `Fig.`)·단위 뒤 마침표·문서 번호를 잘못 자르지 않는다. 예외 목록은 빌더가 테스트 케이스로 굳힌다. **[추천 채택]**
- `Rev. 2`·`Ver. 3`, 점 이니셜(`U.S.`), 줄 첫머리의 목록 번호(`1. …`·`5.1. …`·`a. …`·`iv. …`·`가. …`)에서도 문장을 자르지 않는다. (계획 1에서 정함, 글자·가나다 번호는 2026-11-10)
- **DOCX는 블록 안 줄바꿈(Shift+Enter, 칸 안의 문단 경계)에서도 단위를 나눈다** — 글쓴이가 넣은 경계다. 제목 블록도 줄마다 제목 단위가 된다(`목적`/`Purpose` 두 줄 제목). 블록은 하나로 남으므로 줄 단위들을 합치면 줄바꿈을 품은 한 단위로 돌아간다. PDF 블록의 줄바꿈은 폭에 따라 접힌 줄이라 나누지 않는다. (사용자 피드백 2026-11-10)
- 언어 판정: **한글이 하나라도 있으면 KO, 없고 라틴 문자가 있으면 EN**, 숫자·기호뿐인 단위는 이웃 단위나 문서 설정을 따른다. (사용자 피드백 2026-11-10 — 처음에는 한글 비율 0.2로 정해, 영어 낱말이 많은 한글 문장이 EN이 됐다) 판정 결과는 짝 제안·번역 판정에 쓰이고 화면에는 표시하지 않는다(§6.5). 판정이 틀렸을 때 고치는 길은 쪼개기 그 자리 메뉴의 언어 바꾸기와 묶기 전환(§7.5)이다. (사용자 결정 2026-11-12, 언어 축)
- 한/영 연달아 문서는 이웃한 한글 묶음과 영어 묶음을 짝으로 제안한다. 제안은 보수적이다 — 두 쪽 머리의 숫자 번호가 다르거나, 숫자가 한쪽에만 있거나 서로 다르거나, 길이가 번역으로 보기 어렵게 다르면 잇지 않는다. 문장 수가 다른 묶음(1:2 등)은 머리 번호가 같거나 숫자가 완전히 같을 때만 잇는다. 헷갈리면 잇지 않고 사람에게 맡긴다. 기준값은 합성 자료로만 잡았다. (사용자 피드백 2026-11-10)
- 한 문장에 여러 행동이 든 복합 문장은 AI가 나누기를 제안할 수 있다(계획 2, §7.11). 사람이 받아들이면 나누기 편집이 된다.

### 7.5 쪼개기 편집

- 편집 동작(모두 문서 단위, 묶음이 작업 중일 때만):
  - 나누기: 단위 안의 글자 위치에서 둘로
  - 합치기: 고른 단위들을 원문 순서대로 하나로(떨어진 문장도 가능). **언어가 달라도 합친다** — 예전의 422 `mixed_language`는 없다. 섞어 합친 단위의 언어는 글자로 판정하고(한글이 있으면 KO), 합치기 풀기는 각 단위를 제 언어로 되살린다. 짝의 구성 단위를 모두 합치면 그 짝은 없어진다. (사용자 결정 2026-11-12, 언어 축)
  - 경계 옮기기: 이웃한 두 단위 사이 경계를 글자 위치로 이동
  - 골라 만들기: 글자 범위를 골라 새 단위로(이웃 단위가 필요한 만큼 잘린다)
  - 표를 행 단위로 나누기 / 다시 합치기
  - 언어 바꾸기(화면에서는 그 자리 메뉴에만 — 옆 칸의 `Language` 칸은 없다), 경계 확인 표시·취소
- **묶기(`Join`) 하나 (사용자 결정 2026-11-12, 언어 축)**: 화면에서 조각을 한 덩어리로 만드는 동작은 `Join` 하나다(조각 사이 틈 단추, 그 자리 메뉴, 떨어진 조각을 고르는 `Join with…`). 결과는 시스템이 고른다 — 묶는 조각의 언어가 모두 같으면 합치기, 한글과 영어가 섞여 있으면 짝(§6.5)이다. 따로 누르는 짝 확인(`Confirm pair`)은 없다(줄 확정이 짝 확정, §6.5).
  - 묶인 결과의 옆 칸에 `One sentence | KO/EN pair` 전환이 있다. 짝 → 한 문장은 짝을 풀고 구성 단위를 합친다. 한 문장 → 짝은 합치기를 풀고 되살린 단위들을 짝으로 맺는다 — 되살린 단위의 언어가 같으면 라틴 글자 비율이 높은 쪽을 EN으로 바꿔 맺는다. 전환은 편집과 짝 API 두 번이라 둘째가 실패하면 화면이 어디까지 됐는지 알린다. (사용자 결정 2026-11-12, 세부는 내 판단)
  - 전환은 합친 단위(`can_unmerge`)마다 보이고, 글에 한글과 라틴 글자가 함께 있지 않으면 `KO/EN pair`를 끄고 이유를 보인다. `One sentence`는 짝 구성 단위가 문서 순서로 끊김 없이 이어질 때만 켠다(한/영 따로 문서의 떨어진 짝은 흐리고 이유). (내 판단 2026-11-13, 언어 축)
  - `Join`이 꺼지는 틈: 표·그림처럼 글 단위가 아닌 조각, 같은 언어인데 떨어진 조각(`notAdjacent` — 서버는 받지만 화면에서는 이웃한 조각만 합친다), 이미 다른 짝에 든 조각을 짝으로 묶을 때(`alreadyPaired` — 먼저 `Separate`), 한쪽이 중립이라 합치기도 짝도 안 될 때. 같은 짝 안의 틈에는 `Join`을 두지 않는다(묶을 것이 없고 전환이 그 길이다, 내 판단 2026-11-13, 언어 축).
  - 용지에는 언어 표시가 없다. 이웃한 짝은 구성 단위 수와 상관없이(1:2 포함) 한 카드(옅은 바탕, 안쪽 점선)로 그리고, 떨어진 짝은 고리 아이콘과 고른 때의 강조 테두리로 보인다. (사용자 결정 2026-11-12, 1:N 카드는 내 판단) 배정 New 칸의 카드는 1:1 짝만이다 — 이미 쓴 문장의 응답에 짝 id가 없고 둘짜리 짝 상대(`partner_target_id`)만 있어서다(내 판단 2026-11-13, 언어 축).
- 표 행 나누기·합치기와 레이아웃 표 바꾸기도 쪼개기 편집이다. 같은 편집 길을 타서 서버 편집 기록에 남고, 되돌리기·다시 하기가 같은 ID로 뒤집으며, 다시 묶이는 칸의 판단도 확인 플래그 대상이다. (계획 1에서 정함)
- 새 문서의 표를 다시 묶을 때 판단이 끝난 칸·표 새 문장이 있으면 확인을 받고, 그 새 문장들을 먼저 미배정(같은 묶음의 나머지는 보류)으로 돌린 뒤 다시 맞춘다. (계획 1에서 정함)
- 이미 판단이 있는 단위(옛 문서는 단위·묶인 표의 판단, 새 문서는 미배정이 아닌 새 문장)는 언어를 바꿀 수 없다. 먼저 배정을 지운다. (계획 1에서 정함)
- 같은 범위를 다시 만들 뿐인 경계 편집은 아무것도 하지 않는다(새 ID도 되돌리기 기록도 만들지 않는다). (계획 1에서 정함)
- **되돌리기·다시 하기**: 문서마다 서버에 편집 기록을 남기고 선형으로 되돌린다(되돌린 뒤 새 편집을 하면 다시 하기 기록은 사라진다). 되돌리면 확인했던 판단이 사라질 때(은퇴하는 단위에 판단이 있을 때)는 서버가 거절하고 화면이 먼저 묻는다(확인 플래그를 붙여 다시 보냄). **[추천 채택]** 서버 쪽 기록으로 둔 것은 여러 작성자가 같은 문서를 볼 때 기록이 하나여야 해서다(내 판단).
- **판단이 있는 단위를 은퇴시키는 편집 (내 판단)**: 되돌리기뿐 아니라 앞으로 가는 편집(나누기·합치기·경계 옮기기·골라 만들기)도, 은퇴하는 단위에 미배정이 아닌 판단이 있으면 확인 플래그가 있어야 한다. 적용하면:
  - 은퇴한 단위의 판단은 이력으로 가고, 새 단위는 미배정에서 시작한다. 그 단위에 걸린 AI 결과는 낡은 것으로 처리된다.
  - 은퇴한 단위의 출처 연결을 뗀다. 출처가 하나도 남지 않은 새 문장은 기원이 옛 단위면 지우고, 입구 2 새 문서에서 온 것이면 미배정으로 돌린다.
  - 같은 관계 묶음의 나머지(다른 단위와 새 문장)는 지우거나 미배정으로 돌리지 않고, 내용을 그대로 둔 채 **보류**(시스템 사유 "관련 단위가 바뀜")로 바꾼다. 다른 작성자가 확정한 것을 조용히 날리지 않고, 사람이 다시 보게 하기 위해서다.
- **번역은 출처 새 문장을 따른다 (계획 2에서 정함)**: 출처 새 문장의 글이나 자리(칸 좌표·부모·출처 단위 집합 포함)가 바뀌거나 출처가 사라지면, 사람이 다시 보게 하려고 그 번역을 쓸어 낸다. AI 번역은 지우고(제안은 `stale`), 확정한 번역은 내용을 둔 채 **보류**(시스템 사유 "관련 단위가 바뀜")로 바꾼다. 그대로 두면 옛 글의 번역이 확정으로 결과물에 나가기 때문이다. 결과물 C에서 출처의 단계를 바꿀 때도 같다. 표의 다른 칸이 바뀌어 표가 보류돼도 자기 출처가 그대로인 AI 번역은 제안으로 남는다. 보류하면 확정 글이 빈 보류가 되어 결과물에 빈 줄로 나가고 다시 번역도 못 받기 때문이다. 표를 다시 저장할 때 닫힘이 함께 담아 사람이 정한다.
  - 같은 저장에서 사람이 그 번역 글도 고쳤으면 쓸어 내지 않는다. 화면이 되돌려 보낸 줄(에코)은 사람의 결정이 아니라서 글을 고친 것만 면제다. 표를 저장하면 닫힘 검사가 칸 번역을 같은 저장에 싣게 하므로, 표를 고친 사람은 되돌려 온 칸 번역을 다시 확정하게 된다. (계획 2에서 정함)
  - 같은 순서 바꾸기 요청에서 번역 줄을 출처의 새 단계로 함께 옮겼으면 쓸어 내지 않는다. 글이 그대로이고 자리만 따라간 것이라, AI 번역은 새 단계에서 `ai_suggested` 그대로다. (계획 2에서 정함)
- **되돌리기는 은퇴한 단위를 원래 ID 그대로 되살린다.** 되살린 단위는 미배정이고, 예전 판단은 이력에서 볼 수 있지만 자동으로 복원하지 않는다. 그래서 결과물 A의 단위 ID는 편집과 되돌리기를 거쳐도 같은 범위에 같은 ID다.

### 7.6 To-Be 목록 입력

- API로 전체 목록(새 문서·SOP 칸 N/A·WI 단계)을 읽고 쓴다. 묶음 `revision`으로 동시 편집을 막는다.
- **Excel 가져오기**: 앱이 내려 주는 템플릿(시트 "새 문서": 문서 번호/임시 코드, 제목, 종류, 부모 SOP 번호, 장비 SOP 여부. 시트 "WI 단계": WI 번호, 단계 번호, 단계 제목)을 받는다. 값만 읽고 수식은 무시한다. 번호 중복, 부모가 없는 WI, SOP가 아닌 부모를 거절한다. 문서 번호를 기준으로 기존 목록과 합치고, 새 문장이 들어 있는 문서를 빼는 가져오기는 거절한다. 크기 상한은 빌더가 정한다. (세부 내 판단)
- 입구 2 문서는 새 문서 파일을 올릴 때 목록 줄을 함께 만든다(번호·제목은 파일 이름 파싱, 종류와 부모는 사람이 고른다).

- 새 문서(`side=new`)는 추출에 성공했을 때만 목록 줄이 생기고(거절·실패한 파일이 번호를 붙잡지 않는다), 새 문서의 문서 번호를 고치면 목록 줄의 번호도 함께 바뀐다. (계획 1에서 정함)

### 7.7 배정과 확정 (사람의 경로, AI 없이도 끝까지)

- 사람은 관계 묶음 단위로 판단을 저장한다(§6.8): 단위별 처분과 Remark, 새 문장들(새 문서, 위치, 순서, 언어, 글자, 출처 단위, Remark). 저장 동작은 "확정" 또는 "보류(사유)"다.
- 서버 검사: 묶음이 닫혀 있는가, 위치가 To-Be 목록에 있는가(N/A 칸 금지, 선언된 WI 단계라면 존재하는가), 글자가 비어 있지 않은가, 필수 Remark가 있는가, `revision`이 맞는가. 새 문장 언어가 출처 단위 언어와 같은지는 보지 않는다 — 다르면 변경 종류가 "번역"이 된다(§6.7, 예전의 422 `invalid_group`/`lang_mismatch`는 없다). (사용자 결정 2026-11-12, 언어 축)
- **배정은 언어로 막지 않는다 (사용자 결정 2026-11-12, 언어 축)**: 배정 화면 New 칸에서 다른 언어의 새 문장도 고를 수 있다(잠금 없음). 이미 쓴 새 문장을 고르면 그 새 문장의 새 문서 짝(`partner_target_id`)도 늘 함께 고른다 — 옛 줄에 두 언어가 다 있으면 한글은 한글에, 영어는 영어에 붙고, 옛 줄에 없는 언어의 새 문장은 옛 줄의 단위를 모두 출처로 붙여 "번역"이 된다. 사람이 Ctrl-누르기로 함께 고른 짝 문장을 떼면 그 새 문장은 "신규(Added)"로 남는다(내 판단 2026-11-13, 언어 축).
  - 칸에 확정한 한 언어 줄에는 `Write Korean`·`Write English`가 있어 사람이 빠진 언어의 새 문장을 직접 써 넣는다(AI와 무관, 기원 `units`라 관계 묶음에 들고 종류는 번역). 줄에 그 언어 문장(직접 쓴 것·쓰는 중인 칸·AI 번역)이 이미 있으면 `Make …`(AI 번역 요청, §7.9)와 함께 숨긴다. 제목과 묶이지 않은 칸 문장 줄에도 나온다. (내 판단, 2026-11-12·13, 언어 축)
  - 판단 칸의 Remark는 줄마다 하나다(필수 조건은 §6.7). 출처 없는 새 문장의 "Mark as new"도 Remark를 실을 수 있게 관계 묶음 저장으로 확정한다(그래서 작업 기록은 `group.confirm`, 내 판단 2026-11-13, 언어 축).
- 상위 SOP 칸(예: Procedures)이 N/A면 그 아래 하위 칸에도 배정할 수 없다. (계획 1에서 정함)
- **"그대로 보내기"**: 보낸 곳만 고르면 새 문장 = 원문 글자 그대로, 변경 종류 그대로.
- **보낼 곳 없는 보류**: 보낼 곳을 아직 못 정한 단위는 사유(`hold_reason`)를 남기고 보류할 수 있다. 처분은 `unassigned` 그대로, 새 문장은 없고 상태만 `on_hold`다. 보류 저장에서만 되고 확정 저장은 `hold_required`, 그 단위를 출처로 갖는 새 문장이 함께 오면 `disposed_with_targets`로 거절한다. 나중에 배정·확정하거나 배정 지우기로 미배정으로 돌린다. (프런트 요청 2026-11-07)
- **배정 초기화**: `POST /bundles/{id}/decisions/reset` `{revision(묶음), document_id?, dry_run?}` — 문서 하나(없으면 묶음 전체)의 배정된 단위를 `detach_units(cause="cleared")` 한 번으로 미배정으로 돌리고, 대기 중 AI 제안은 거절로 남긴다. 다른 문서와 묶여 있던 문장은 보류로 간다. `dry_run`은 같은 길을 돌린 뒤 되돌려 `{unassigned_units, deleted_targets, held_units, held_targets}` 건수만 준다(기록 없음). 그 묶음에 대기·실행 중 AI 작업이 있으면 409 `ai_job_active`. 기록은 `decision.reset` 이벤트 하나(건수만).
- **짝**: 한쪽을 저장할 때 짝 단위도 같은 요청에 담아 한 번에 확정할 수 있다. 서버가 짝 단위의 판단을 몰래 같이 바꾸지는 않는다(명시적으로 담긴 것만). 짝 자체는 서버가 저장 끝에 풀거나 확정한다(§6.5 "짝은 한 곳으로 간다") — 저장 응답은 그 저장에서 확정·푼 짝(`pairs_confirmed`·`pairs_dissolved`)을 돌려주고 화면은 푼 짝의 줄을 나눈다. (사용자 결정 2026-11-12, 언어 축)
- **여러 개 한 번에**: 여러 단위를 같은 "삭제" 또는 "다른 문서로 이동"과 같은 사유로 한 번에 확정할 수 있다(머리말·구조 제목 정리용). AI 제안을 여러 개 한 번에 확정하는 기능은 두지 않는다. 사람이 줄마다 보게 하려는 목표 3 때문이다(내 판단).
  - 계획 2에서 이 거절을 서버가 지킨다. 고른 단위에 AI 제안 상태(`ai_suggested`) 단위가 하나라도 섞이면 409 `ai_suggested_units`와 그 단위 목록으로 통째 거절한다(그 줄은 하나씩 처리하거나 먼저 배정을 지운다). 머리말 정리 전에 AI를 돌리면 그 줄은 하나씩 처리하게 되는 비용을 받아들였다. 보류 상태의 제안 단위는 받아서 채택을 남긴다(§6.11). (계획 2에서 정함)
- **AI 제안 받아들이기 (계획 2에서 정함)**: 사람의 확정은 위의 관계 묶음 저장 그대로이고, 제안을 그대로 받으려면 글(`text`)과 변경 종류(`change_type`)를 비워 보낸다.
  - 입구 1은 AI 제안 문장이 든 새 문장에 `text`를 비우면 그 제안 문장이 확정 문장이 된다. 입구 2는 새 문장의 글·자리가 새 문서 원문으로 잠겨 있어, 제안이 있고 출처가 제안과 같을 때만 비워 보낼 수 있다. 손으로 맞춘 짝이나 출처를 바꾼 저장은 종류를 직접 골라야 하고 아니면 422다. (계획 2에서 정함)
  - `change_type`은 글자 비교 종류(그대로·말투·고쳐 씀)를 다르게 고를 때만 보낸다. 구조에서 나오는 종류(나눔·합침·신규)는 보내지 않는다(§6.7). 출처를 바꾸면 종류를 다시 골라야 한다. (계획 2에서 정함)
  - 표 구성 변경 제안은 §6.7대로 사람이 정하는 종류라서, 비워 보내도 받아지지 않고 `change_type: "table_restructured"`와 사유를 함께 보내야 한다. (계획 2에서 정함)
- **순서**: 새 문서 안 새 문장의 기본 순서는 옛 문서 순서다. 결과물 C에서 사람이 순서를 바꾸고 WI 단계 번호를 정한다.
- **입구 2 수동 짝 맞추기**: 새 문장(새 문서 단위)에 옛 단위를 출처로 붙이거나 떼고, 변경 종류를 고르고 확정한다. 짝이 없는 새 문장은 "신규"로 확정하고, 짝이 없는 옛 단위는 "삭제"(사유) 등으로 처분한다.
- **입구 2의 한 번에 확정 (내 판단)**: 코드가 확인할 수 있는 경우만 여러 개를 한 번에 확정한다. 옛 단위와 새 단위의 글자가 같은 1:1 짝(변경 종류 "그대로")과, 사람이 골라 표시한 짝 없는 새 문장의 "신규"다. AI가 제안한 짝은 하나씩 본다. 새 문서 하나에 수백 번 확정하는 일을 줄이면서 목표 3(AI 제안은 사람이 줄마다 본다)을 지키기 위해서다.

### 7.8 AI 분류와 고쳐 쓰기 제안 (입구 1, 계획 2)

작성자가 대상(문서 전체의 미배정 단위, 또는 고른 단위)을 골라 요청한다. 단위별로(짝이 있으면 짝 하나를 한 작업으로) 나눠 처리하고, 끝난 단위부터 화면에 보인다. 문서를 통째로 한 번에 보내지 않는다. **[추천 채택]**

- **요청 범위 (계획 2에서 정함)**:
  - 문서 범위 요청은 그 문서의 **미배정** 단위만 받는다. 이미 AI 제안이 있는 단위를 다시 받으려면 `unit_ids`로 고른다. 문서 범위가 제안 상태 단위까지 다시 받으면, 요청 상한을 넘는 문서의 뒤쪽 단위는 영영 처리되지 않는다. (계획 2에서 정함)
  - `unit_ids`로 고른 단위의 짝도 같은 작업에 담는다. 짝이 미배정이거나 같은 종류의 AI 제안 상태일 때만이고, 확정·보류된 짝은 건드리지 않는다. §7.7의 "짝을 몰래 바꾸지 않는다"는 사람의 저장 이야기이고 제안은 확정이 아니라서, 고르지 않은 짝의 제안이 함께 바뀔 수 있다. (계획 2에서 정함)
  - 요청 한 번이 쌓는 작업은 상한(2000건)이 있고, 넘은 단위는 건너뛴 목록에 사유 `limit_reached`로 알린다. 조용히 빠지면 사람이 전부 요청됐다고 믿는다. 고르는 단위 목록은 2만 개까지 받는다. (계획 2에서 정함)

1. **후보 추리기**: 임베딩으로 입구 1 새 문서들의 칸 중 후보를 3개 추린다(`K=3`, 비즈니스 상수). 칸의 임베딩 글은 "새 문서 제목 / 칸 이름: 도메인 문서 §2의 넣는 것" 꼴, WI는 "WI 제목(부모 SOP) / 단계 n 제목 / Instruction 또는 Why". "삭제"는 항상 후보에 넣고, "다른 문서로 이동"은 AI가 제안하지 않는다(묶음 밖 대상을 모르므로, 내 판단). 임베딩이 꺼져 있으면 목록의 모든 칸을 후보로 주고, 너무 많으면 글자 유사도로 줄인다(내 판단). 하위 칸 이름은 상위 칸 이름을 달아(`Procedures > Troubleshooting`) 임베딩과 LLM이 서로 구분하게 하고, 넣는 것이 비어 있으면 `: ` 꼬리를 뗀다. (계획 2에서 정함)
2. **LLM 고르기**: 지침(활성 버전), 출력 형식, 대상 단위(와 짝), 맥락(앞뒤 단위, 소속 절 제목, 표 단위면 Markdown 표), 후보 목록(ID 포함), 묶음의 To-Be 요약을 보낸다. 표 행 단위도 표 전체의 Markdown을 맥락으로 받는데, 빈 행·열을 접고 행 200·열 50·글자 2만을 넘는 뒤쪽은 표시 없이 자른다. 조작된 병합·격자 값이 메모리와 프롬프트 크기를 정하지 못하게 하려는 것이다. (계획 2에서 정함) LLM은 후보 중 하나를 고르고 이유, 인용한 규칙 ID, 근거 위치(단위 글자 안의 인용), 변경 종류(그대로/말투/고쳐 씀), 필요하면 나눔 제안을 낸다. 후보 밖을 고른 응답은 버린다. **[결정·추천 채택]**
3. **고쳐 쓰기 제안**: 같은 요청에서 한글과 영어로 함께 낸다. SOP로 보내는 문장은 SOP 문체, WI로 보내는 문장은 WI 문체(R02, RW06). 짝이 없는 단위는 그 언어로만. **[결정]** 표 단위의 AI 제안은 보낼 곳만 고르고 칸 문장은 원문 그대로(변경 종류 "그대로") 둔다. 칸 고쳐 쓰기까지 하면 응답 모양과 검증이 크게 늘어서, 칸은 사람이 고치거나 칸 번역을 쓴다. (계획 2에서 정함)
4. **검사**: 형식, 단위 ID, 후보 소속, 규칙 ID가 활성 지침에 있는지(없는 ID는 빼고 경고), 근거 인용이 실제 단위 글자 안에 있는지, 숫자·단위·부정 차이(§7.12). 형식이 틀렸거나 후보 밖이면 그 단위만 **보류**(사유 "AI 응답 무효")로 두고 나머지는 진행한다. **[결정]**
   - 응답의 모든 글자는 저장 전에 저장 못 하는 글자(NUL·짝 없는 서로게이트)를 같은 길이의 대체 문자로 바꾸고, 글자 한 칸이 사람이 저장하는 문장과 같은 상한(2만 자)을 넘으면 그 단위만 무효다. 상한이 같아야 제안을 그대로 확정할 수 있다. 규칙 ID와 후보도 같은 처리를 거친다. (계획 2에서 정함)
   - 다시 돌린 응답이 무효면 이전 제안도 걷고(제안 `stale`) 단위를 보류한다. 보류 단위 밑에 AI 제안 새 문장이 남지 않게 하려는 것이고, 이전 제안 글은 제안 기록에서만 본다. (계획 2에서 정함)
5. **적용**: 대상이 여전히 미배정 또는 AI 제안 상태이고 `revision`이 스냅샷과 같을 때만, 단위를 AI 제안 상태로 두고 AI 제안 문장을 가진 새 문장을 만든다(확정 문장은 비어 있음). 아니면 그 결과는 낡은 것(`stale`)으로 남기고 적용하지 않는다.
6. **사람**: 확정하거나, 고쳐서 확정하거나, 보류한다. 확정할 때 채택 여부(그대로 / 고쳐서 / 버림)를 기록한다.

### 7.9 번역 제안 (계획 2)

- 오너가 방향(한→영 또는 영→한)을 골라 단위 또는 문서 단위로 요청한다. **[결정]**
- 대상은 이미 배정된 단위의 새 문장이다(미배정 단위는 "먼저 배정"으로 건너뛰고 알린다). 번역할 글은 그 새 문장의 현재 글(확정 문장, 없으면 AI 제안 문장)이다. 반대 언어 짝이 이미 있으면 건너뛰고 알린다. (내 판단) 단위가 도착 언어의 새 문장(사람이 쓴 `Write …`, 입구 2 짝)을 이미 출처로 두고 있어도 건너뛴다 — 번역은 빠진 언어를 채우는 것이라서다. (내 판단 2026-11-13, 언어 축)
- 번역은 "빠진 언어를 채워 넣는 것"이고 변경 종류의 하나다. 번역으로 생긴 문장은 출처 줄의 빈 언어 자리를 채운다(배정 화면에서는 그 줄에 붙는다): 위치는 출처 새 문장과 같고, 기원 번역, 번역 출처 단위 ID, 변경 종류 "번역", 상태 AI 제안. **[추천 채택]** (사용자 결정 2026-11-12, 언어 축) 결과물 A에서 출처 줄과 한 묶음으로 놓는 것은 결과물 작업(언어 축 (4))이고, 그때까지 결과물은 번역 문장을 대상 언어 판에 새 줄로 싣는다.
- AI 번역 말고도 사람이 빠진 언어를 직접 써 넣을 수 있다(§7.7 `Write …`). 그 문장은 일반 새 문장(기원 `units`)이라 관계 묶음에 들고, 아래 번역 줄의 규칙은 기원 `translation`에만 해당한다. AI가 꺼져 있어도 빠진 언어를 채울 수 있어야 해서다. (내 판단 2026-11-12, 언어 축)
- **짝이 확정되면 묶인 단위의 번역을 쓸어 낸다**: 짝을 맺기 전에 번역이 있던 단위가 짝이 되면, 그 짝이 확정되는 순간(줄 확정·짝을 맺으며 바로 확정 — `pairs.mark_pair_confirmed` 한 곳) §7.5의 "출처가 바뀜"과 같이 쓸어 낸다(AI 번역은 지우고 확정 번역은 보류). 제안 짝인 동안은 둔다 — 풀면 다시 필요하다. 쓸리는 것은 기원 `translation` 행뿐이라 사람이 쓴 다른 언어 문장은 남는다. (내 판단 2026-11-13, 언어 축)
- 숫자·단위·부정 검사는 언어를 넘어 비교한다.
- **번역 출처는 출처 연결이 아니라 새 문장의 번역 출처 단위 필드로 둔다 (계획 2에서 정함)**: 그래서 번역 줄은 관계 묶음·나눔 판정·닫힘 검사에 끼지 않고, 표 칸 번역 말고는 자기 혼자 저장된다(표 칸 번역은 표 전체와 함께 저장). 번역은 단위의 판단을 건드리지 않는다.
- **번역의 자리는 출처를 따른다 (계획 2에서 정함)**: 저장에서 번역의 자리는 비우거나, 지금 자리나 출처의 저장 뒤 자리를 보낸다. 그 밖의 자리는 422 `invalid_group`(`translation_locked`)이다. 출처가 있으면 최종 자리는 늘 출처의 자리다. 순서 바꾸기(C)는 번역 줄도 목록에 담아야 하고, 번역 줄의 단계는 출처의 새 단계로만 바꿀 수 있다. 번역만 따로 옮기는 길은 어느 쓰기 경로에도 없다.
- **무효 응답 (계획 2에서 정함)**: 번역 응답이 형식 오류·초장문이면 단위를 보류로 바꾸지 않고 제안에 `invalid`만 남긴다. 출처 단위는 이미 배정돼 있어 보류할 대상이 없고, 이미 있던 AI 번역은 그대로 둔다(분류의 §7.8과 달리 보류가 없다). 화면은 무효 건수를 보여 준다.

### 7.10 입구 2 짝 맞추기 제안 (계획 2)

- 옛 단위와 새 단위를 **같은 언어끼리** 임베딩으로 비교해 짝을 제안한다. 1:1, 1:N(나눔), N:1(합침)을 만든다. 기준값·묶는 방법은 빌더가 정한다. **[결정]**
- 이미 입구 1 문서에 배정된 옛 단위는 대상에서 뺀다.
- **두 입구를 섞은 묶음 (내 판단)**: 짝 맞추기를 먼저 돌리고, 남은 미배정 단위에 분류를 돌린다. 짝이 없는 옛 단위를 삭제 후보로 표시하는 것은 묶음에 입구 1 문서가 없을 때만이다. 입구 1 문서가 있으면 그 단위는 미배정으로 남아 분류 대상이 된다(입구 1 쪽으로 갈 문장이 삭제 후보로 쏟아지지 않게).
- LLM은 짝마다 **변경 종류만** 제안한다(그대로 / 말투 / 고쳐 씀 / 나눔 / 합침 / 표 구성 변경, 이유 포함). **[결정]**
- 짝이 없는 옛 단위는 "삭제 후보"(AI 제안 처분 삭제, 사람이 확정할 때 사유 필수), 짝이 없는 새 단위는 "신규".
- 임베딩이 꺼져 있으면 같은 언어 글자 유사도로 후보를 만들고, 그것도 없으면 사람이 손으로 맞춘다(§7.7). 유사도는 정답 확률로 보여 주지 않는다. **[추천 채택]**
- 계획 2의 세부:
  - **같은 글자 반복**: 글이 똑같은 항목(같은 언어·종류, 보이는 글자가 있을 때만)은 점수 계산 전에 먼저 id 순으로 1:1로 잇는다(적은 쪽 수까지). 같은 문장이 되풀이되면 점수가 모두 같아, 그냥 묶으면 거짓 나눔과 거짓 삭제 후보가 나오기 때문이다(§13). 반복 문장의 어느 자리끼리 이어졌는지는 달라질 수 있다. (계획 2에서 정함)
  - **한 번에 확정 후보는 뺀다**: 같은 글자가 양쪽에 딱 하나씩인 1:1(§7.7 한 번에 확정)은 코드로 확인되는 짝이라 AI 짝 대상에서 뺀다. (계획 2에서 정함)
  - **표·그림은 코드가 낸다(1:1만)**: 그림은 변경 종류 "그대로"로 고정이다. 표는 격자와 칸 글자로 판정해, 격자가 같고 옛 칸이 모두 이어지면 "그대로", 아니면 "표 구성 변경"을 제안한다(표의 말투 변경은 가려내지 못한다). 묶는 방법은 문장과 같다(각 옛 단위의 최고 새 문장과 각 새 문장의 최고 옛 단위를 이은 묶음). 표·그림은 묶음마다 가장 높은 쌍 하나만 남기고, 서로 최고인 쌍만 남기는 거름은 두지 않는다. 그 거름은 한쪽 최고로만 이어진 문장 짝을 잃게 한다. (계획 2에서 정함)
  - **글자 없는 단위**(캡션 없는 그림 등)는 삭제 후보·신규로 표시하지 않고 미배정으로 둔다. 비교할 글이 없어, 사람이 손으로 맞춘다. (계획 2에서 정함)
  - **다른 새 문서에 걸친 짝**: 1:N이 새 문서 둘에 걸치면 모습(`shape`)은 나눔(`split`)이지만 변경 종류는 구조로 정하지 않고 LLM이 낸 종류를 새 문장마다 둔다. 나눔은 같은 새 문서 안에서만이고(§6.7), 문서가 다르면 §6.9 중복 배정이라서 사람이 저장할 때 사유를 적는다. 제안 기록의 `change_type`에는 그 그룹에서 가장 큰 변화를 한 값으로 남기고, 사실은 새 문장마다 가진 종류다. (계획 2에서 정함)
  - **말투와 낡음**: 띄어쓰기·문장부호만 다른 짝은 "말투"다. 지침 시드가 LLM에 말투로 답하게 하고, 글이 다른 "그대로" 답은 코드가 "고쳐 씀"으로 바꾼다(§6.7). 계획과 작업 사이에 문장 언어가 바뀌면 그 작업은 낡음이다. (계획 2에서 정함)
  - **계획에는 요청 상한이 없다**: `match_plan` 하나가 묶음 전체를 보므로 문장 그룹마다 `match` 작업이 상한(§7.8)을 넘어 쌓일 수 있다. 짝을 조용히 버리는 쪽이 더 나빠서다. 한 번 눌러 LLM 호출이 많이 쌓일 수 있다. (계획 2에서 정함)

### 7.11 한/영 짝 제안과 복합 문장 나누기 제안 (계획 2)

- 한/영 따로 배치 문서 안에서 다국어 임베딩으로 한글·영어 단위 짝을 제안한다. 사람이 확인한다. **[결정]**
  - **같은 부분 안에서만 맺는다**: AI 짝도 본문·머리말·꼬리말·각주 부분을 넘지 않는다(§6.5). 안 그러면 본문 문장이 머리말의 다른 언어 문장과 짝지어진다. 표 경계는 넘는다. 한글 표와 영어 표를 잇는 것이 목적이라서, 연달아 짝(§6.5)이 표 경계도 넘지 않는 것과 다르다. (계획 2에서 정함)
  - 임베딩만 쓰고 LLM을 부르지 않는다(§6.10). 짝 없는 활성 한글·영어 문장 중 서로 가장 가까우면서 기준값 이상인 1:1만 제안 짝(출처 `ai`)으로 쓰고, 표·행에 묶인 칸 문장은 코드 짝처럼 제외한다. 이미 짝인 단위는 후보가 아니라서 사람이나 코드가 맺은 짝을 덮지 않는다. 채팅 AI가 꺼져 있어도 돌아서 요청의 관문은 AI 사용이 아니라 임베딩 사용(꺼져 있으면 409 `embedding_disabled`)이다. 요청 뒤 임베딩이 꺼졌으면 `config`, 호출 실패는 `connection`으로 끝난다. (계획 2에서 정함)
  - AI 짝은 제안이라 문서 `revision`을 올리지 않는다(열어 둔 화면의 저장을 막지 않게). 낡음은 문서 `revision`이 아니라 쌍의 단위 내용을 견주어 본다. 사람이 짝을 확정하면 그대로, 풀면 버림, 만든 짝이 대신하면 §6.11 규칙대로 채택이 남는다. 짝 행을 지운 뒤에는 제안을 찾을 길이 없어 채택은 지우기 전에 남긴다. (계획 2에서 정함)
- 복합 문장 나누기: 길거나 여러 행동이 든 단위에 LLM이 나눌 글자 위치를 제안하고(R03), 사람이 받아들이면 §7.5 나누기가 된다.
  - 제안은 나눌 글자 위치(`offsets`)만 기록하고 단위·판단·새 문장은 건드리지 않는다. 나누기는 사람이 위치를 받아들여 §7.5 편집으로 한다. 그래서 무효 응답도 분류와 달리 단위를 보류하지 않는다. 응답 조각이 원문을 빈 글자만 빼고 순서대로 그대로 덮을 때만 위치로 바꾸고, 아니면 무효(경고 종류 `parts_mismatch`)이며 응답 글은 보관하지 않는다. 조각 하나가 문장 전체면(나눌 곳 없음) 제안을 쓰지 않는다. (계획 2에서 정함)
  - **범위 규칙**: 문서 범위 요청은 묶이지 않은 문장·칸 문장 중 미배정만 받고, 열린 나누기 제안이 있으면 `already_suggested`, 짧은 문장(30자 미만 — 처음 60자는 한글 복합 문장을 거의 다 걸렀다)이면 `too_short`로 건너뛴다. 응답은 건너뛴 단위 전체의 사유별 수(`skipped_by_reason`)를 함께 알린다(고른 단위는 둘 다 없이 다시 물을 수 있다). 제목·표·묶인 칸은 문서 범위에서는 알리지 않고 대상에서 뺀다. 고른 단위가 제목·그림·표면 요청 전체를 막지 않고 단위마다 `not_splittable`, 표 칸에 묶인 단위면 `bound_cell`로 건너뛴다. (계획 2에서 정함)
  - 새 답(나누라는 답도 나누지 말라는 답도)이 오면 같은 단위의 열린 이전 나누기 제안을 `stale`로 내린다. 채택이 있는 제안은 `applied` 그대로이고, 무효·낡은 새 답은 이전 제안을 내리지 못한다. 채택은 사람이 `POST /suggestions/{id}/adoption`으로 직접 남기며, 적용된 나누기 제안이고 아직 채택이 비어 있을 때만 받는다(아니면 409 `not_manual_adoption`). (계획 2에서 정함)

### 7.12 문장 검사

- 원문(출처 단위들)과 새 문장 사이의 숫자(소수·범위 포함), 단위(℃, mL, rpm, 분, min, % 등), 부정 표현(한글: 않/없/금지/말 것/불가 등, 영어: not/no/never/without/prohibited 등)이 다르면 코드가 경고를 붙인다. **[추천 채택]**
- 숫자는 부호와 위 첨자 지수를 지켜 비교하고(`-20`, `10⁶`) 문장 앞 조항 번호(`5.1 `)는 뺀다. 숫자와 단위의 짝이 서로 바뀐 문장도 경고하고, 단위는 숫자 바로 뒤에서만 센다. 한글 금지 표현(`마십시오`·`안 된다`·`못 한다` 등)도 부정으로 센다. (계획 1에서 정함)
- AI 제안 문장, 번역, 사람이 확정한 문장 모두에 적용하고 화면·결과물에 경고로 보인다. 완료를 막지는 않는다(내 판단). 사전과 규칙은 빌더가 정하고 테스트로 굳힌다.

- 줄 규칙(내 판단): (1) 그 언어의 옛 커버 단위마다 한 줄(옛 문서 순서). 나눔이면 여러 새 문장을 한 칸에 번호(①②)를 붙여 적고, 합침이면 합친 문장을 각 출처 줄에 같은 관계 묶음 ID로 적는다. 중복 배정이면 보낸 곳마다 줄을 나눈다. (2) 번역 줄은 출처 단위 위치 바로 뒤에 넣고 옛 문장 칸에 출처 단위 ID를 적는다. (3) 입구 2의 신규 줄은 옛 문장 칸이 빈 채로 새 문서별로 끝에 모은다. (4) 표는 칸 문장 줄들 앞에 "표" 줄 하나(원문 문장 칸에 `[표 n, 행×열]`, 변경 종류 "그대로" 또는 "표 구성 변경"과 이유)를 두고, 이 줄은 요약 숫자에서 세지 않는다. 칸 문장 줄의 확정·AI 제안 칸은 그 칸 문장의 새 문장 글이다. (5) 그림 줄은 두 언어 표에 모두 나온다.
- 입구 2에서는 "새 문서 안 위치"에 이미 쓰인 문서의 실제 위치가 들어간다.

**B. 맵핑 흐름도**: 옛 문서들(왼쪽, 단위 수)에서 새 SOP·WI·삭제·다른 문서로 이동(오른쪽)으로 단위가 몇 개씩 갔는지 선으로 보인다. 미배정 단위는 따로 눈에 띄게 둔다. 백엔드는 노드·간선·숫자를 계산해 돌려주고, 화면 그림은 프런트가, Excel 그림은 백엔드가 그린다(§7.14).

**C. 새 문서 기준 묶음**: 새 SOP와 그 아래 WI마다, 위치별로 어떤 옛 단위를 어떤 순서로 받았는지(`← OLD-1 §5.1, OLD-3 §5.1 (합침)` 꼴). SOP의 N/A 칸은 사유와 함께, 삭제와 다른 문서로 이동은 끝에 따로. 다음 단계인 문서 생성에 넘길 재료다. C에서 사람이 순서와 WI 단계 번호, 들여쓰기 깊이를 바꾼다.

**섹션 번호** (사용자 결정 2026-11-10, 세부는 내 판단): 새 문장마다 `칸 번호 + 들여쓰기 깊이`로 번호를 센다(예: `6.1.2.1`). 결과물 C 항목과 칸, 결과물 A의 "새 문서 안 번호", Excel A·C의 번호 열이 같은 값이다(Excel은 옮겨 쓰기만 한다).
- 칸 번호는 SLOT_KEYS의 고정 자리다 — 도메인 문서 §2의 S1–S7(Purpose 1 … Document Relationships 7), 하위 칸은 `5.1`·`6.1`처럼. N/A 칸도 자기 번호를 지켜 칸을 N/A로 바꿔도 다른 칸 번호가 그대로다.
- 칸 안 줄은 순서대로 깊이 0이면 `칸.1`, `칸.2`, 깊이 1이면 그 아래 `칸.2.1`. 깊이는 앞줄의 (눌러 읽은) 깊이 + 1을 넘지 못하고 첫 줄은 0이다 — 넘는 깊이는 셀 때 눌러 읽고, 저장한 깊이는 사람이 정한 값 그대로 둔다(0–9).
- 판(한글·영어)마다 그 판에 보이는 줄(그 언어와 중립)만 센다. 번역 줄은 출처와 같은 깊이·같은 정렬 자리라서 두 판의 줄이 서로 짝을 이루면 출처와 같은 번호다. 표 칸은 표의 번호를 따른다.
- WI는 단계 번호 아래로 `{단계}.{n}` — 한 단계의 Instruction과 Why를 이어 센다. 단계 없는 칸과 입구 2 문서(이미 쓴 문서, 절 경로)는 번호를 새로 매기지 않는다(번호 없음).
- 새 문장이 다른 칸·단계·문서로 옮겨지면 깊이는 0부터 다시 시작한다(깊이는 그 칸 앞뒤 줄에 기댄 값이다). 결과물 C에서 단계를 옮기며 깊이를 함께 보내면 그 값을 지킨다. 깊이만 바뀐 출처의 번역은 보류 없이 깊이만 따라간다.
- **번호 표시** (사용자 결정 2026-11-10): 줄마다 번호(기본)·번호 생략·주석 중 하나를 결과물 C에서 고른다. 생략·주석 줄은 번호를 받지 않고 세지도 않아 다음 번호 줄이 이어 센다(`5.1`, 생략, `5.2`). 깊이 눌러 읽기의 상한도 앞 번호 줄만 본다. 주석 줄은 글을 기울여 보인다(Excel 칸도 기울임). 표 칸은 표의 표시를 따른다(표가 번호가 없으면 칸도 없다). 결과물 A의 "새 문서 안 번호"는 그 새 문장 자리가 빈다.
- 한/영 짝은 한 줄로 센다 — 두 판에서 같은 번호다. 짝 원문 줄의 상대(출처 단위 하나의 짝의 다른 단위가 그 새 문서에 만든 새 문장 하나)는 표시를 함께 가지므로 한쪽만 바꿔도 서버가 상대에 옮긴다. 번역 줄은 출처의 표시를 따른다(깊이와 같다). 입구 2 문서는 번호를 매기지 않으므로 표시도 바꾸지 않는다. 다른 칸·단계·문서로 옮겨도 표시는 그대로다(깊이와 달리 앞뒤 줄에 기대지 않는다). (세부는 내 판단)

입구 2 새 문서에서는 한 칸 안 항목이 짝지은 옛 단위의 순서가 아니라 새 문서의 실제 자리 순서를 따른다. (계획 1에서 정함)

**언어별 요약 숫자** (정의는 내 판단):
- 옛 단위: 그 언어의 옛 커버 단위 수
- 배정: 처분이 미배정이 아닌 단위 수(삭제·이동 포함)
- 미배정: 처분이 미배정인 단위 수
- 중복 배정: §6.9 정의에 해당하는 단위 수
- 삭제, 이동: 각 처분의 단위 수
- 신규: 그 언어의 기원 `new_doc` 새 문장 중 출처가 없는 수
- 번역: 그 언어의 기원 번역 새 문장 수
- 확정률: 확정 상태 단위 수 / 옛 단위 수

### 7.14 Excel 내보내기

- 언어별로 파일 하나(내 판단), 시트는 "A 비교표", "B 흐름"(요약 숫자 + 옛 문서 × 보낸 곳 건수 표 + 흐름도 그림), "C 새 문서", "정보"(묶음 제목, 상태, 만든 시각 KST, 만든 사람, 지침 버전, 합성 데이터 여부). **[추천 채택: A·C 표 시트, B 요약 숫자와 흐름도 그림]**
- **수식은 쓰지 않는다**: 모든 글자 칸은 문자열로 쓰고, `=`·`+`·`-`·`@`로 시작하는 글도 수식이 되지 않게 한다. 원문은 바꾸지 않는다. **[추천 채택]**
- A 시트에 "새 문서 안 번호" 열(새 문서 안 위치 다음), C 시트에 "번호" 열(칸과 항목 사이 — 칸 줄은 칸 번호, 항목 줄은 섹션 번호, 표 칸 줄은 비움)을 둔다. 값은 결과물 A·C가 센 것을 옮겨 쓴다. 번호 생략·주석 줄은 번호 칸이 비고, 주석 줄은 C의 항목·AI 제안 글 칸과 A의 확정·AI 제안 문장 칸(보낸 새 문장이 모두 주석일 때)을 기울여 쓴다.
- 셀 하나의 글자 수 한계(32,767자)를 넘는 글은 다음 줄에 "(이어짐)"으로 나눠 싣는다(내 판단).
- 흐름도 그림은 백엔드가 PNG로 그린다. 서버는 외부에서 글꼴을 받을 수 없으므로 OFL 라이선스 한글 글꼴 하나를 저장소에 넣는다(라이선스 파일 동봉, 글꼴은 빌더가 고른다, 내 판단).
- 흐름도 그림은 열마다 문서 노드를 30개까지만 그려 그림 크기를 묶되, 미배정·삭제·이동 노드는 건수와 무관하게 늘 그린다. (계획 1에서 정함)
- 영어판 파일의 시트 이름은 영어다(`A Comparison`·`B Flow`·`C New documents`·`Info`). (계획 1에서 정함)
- 수식처럼 보이는 글(`=`·`+`·`-`·`@`로 시작)은 문자열 셀에 `quotePrefix`를 붙여 쓴다. (계획 1에서 정함)
- 파일 이름: `<묶음 제목>_<ko|en>_<KST yyyymmdd-HHmm>.xlsx`(파일 이름에 못 쓰는 글자는 정리). 작업 중에도 내보낼 수 있고, 상태가 "정보" 시트와 각 시트 머리에 적힌다(내 판단). 내보내기는 작업 기록에 남는다.
- 요청 처리·내부 확정·파일 생성은 서로 다른 상태다. 파일 생성 실패를 저장 실패처럼 보이지 않게 한다. **[추천 채택: 이전 시도의 교훈]**

### 7.15 완료와 검토

- **검토 요청(작성자)**: 묶음을 `in_review`로 넘긴다. 아래가 하나라도 남아 있으면 거절하고 막는 이유 목록을 돌려준다. **[추천 채택]**
  - 미배정, AI 제안, 보류 상태의 커버 단위 또는 새 문장. 막는 이유(`units_*`·`targets_*`)는 언어마다가 아니라 상태마다 하나이고 `lang`이 없다. 단위 건수는 줄 수(§6.5 커버리지, 진행 숫자와 같은 규칙 — `outputs.build_review_facts`가 `BundleSnapshot.pair_of`로 센다), 새 문장 건수는 새 문장 수다(그림·표를 두 번 세지 않는다). (사용자 결정 2026-11-12, 언어 축 — 예전의 "(두 언어 모두)"를 뺐다)
  - 이유 없는 중복 배정, 사유 없는 삭제·이동·표 구성 변경
  - 닫지 않은 "추출 누락 의심" 경고(§7.3)
  - 경계를 확인하지 않은 단위(§6.4 경계 확인, 옛·새 문서 모두). 막는 이유는 `unchecked_boundaries`(건수·문서 id), 다음 행동은 `check_boundaries`(쪼개기 단계) — 문서 문제(`resolve_documents`) 다음, To-Be 채우기 앞이다. (사용자 결정, 2026-11-10)
  - 의미 검토 확인 4항목(숫자 / 조건·예외 / 표 / 그림)을 작성자가 표시하지 않음. 기계적 커버리지와 사람의 의미 검토를 따로 보이라는 이전 시도의 교훈이다(내 판단)
  - 검토자 0명
  - 거절·실패한 문서가 남아 있음(지우거나 다시 올려야 한다). 결과물이 그 문서를 조용히 빠뜨리지 않게 한다. (계획 1에서 정함)
- 검토 요청 시 그 묶음의 대기 중인 AI 작업은 취소한다.
- `in_review`와 `done`에서는 내용 변경이 409다(읽기와 내보내기만).
- **검토 요청 거두기(작성자)**: `in_review` 묶음을 작성자가 `in_progress`로 되돌린다. 검토자가 끝내기 전에 고칠 것이 생겼을 때의 길이다. 자기 요청을 물리는 것이라 사유를 받지 않고(되돌리기·다시 열기는 사유 필수), 요청한 사람이 아니어도 그 묶음의 작성자면 된다. 요청 때 취소한 AI 작업은 되살리지 않는다. 작업 기록에는 `review.withdraw`로 남는다. (v0.10.1 전체 검토 뒤 더함, 2026-11-10)
- **검토자**: "검토 완료"(→ `done`) 또는 이유를 적어 되돌리기(→ `in_progress`).
- **다시 열기**: `done` 묶음을 작성자가 이유를 적어 `in_progress`로 되돌릴 수 있다. 정식 승인은 EQUIS에서 하므로 이 앱의 완료는 작업 단계 표시다(내 판단).
- 작업 중으로 돌아가면(요청 거두기·검토자 되돌리기·다시 열기) 의미 검토 확인 4항목은 모두 지워져, 작성자가 다시 표시해야 한다. (계획 1에서 정함)
- 검토 요청 조건은 원문 글자를 읽지 않고 계산한다(개요마다 불려서). (계획 1에서 정함)

## 8. AI와 코드의 경계

### 8.1 나눔 [결정]

| 코드가 하는 일 | AI가 하는 일 (제안만) | 사람이 하는 일 |
|---|---|---|
| 추출, 규칙 기반 쪼개기, 언어 판정, 표를 Markdown으로 바꾸기, 누락 대조, 숫자·단위 차이 경고, 커버리지와 요약 숫자, 결과물 A·B·C, Excel | 후보 추리기(임베딩), 칸 고르기와 이유(LLM), 고쳐 쓰기, 번역, 한/영 짝 제안, 입구 2의 옛·새 짝 제안, 복합 문장 나누기 제안 | 단위 경계 확인, To-Be 목록 작성, 배정·문장·짝 확정, 보류, 최종 검토 |

- AI가 자기 결과를 채점하게 하지 않는다. 누락이나 중복 검사는 반드시 코드로 한다.
- AI 응답은 형식, 단위 ID, To-Be 칸이 맞는지 검사한다. 일부가 실패하면 그 단위만 보류하고 나머지는 진행한다.
- 지침에는 규칙 ID를 붙여 두고 AI가 이유를 낼 때 인용하게 한다. 지침에는 특히 R03(작업 단위 끊기), R01·R11·R12(SOP와 WI 가르기), R10과 도메인 문서 §5(Instruction과 Why 가르기)를 넣는다. **[추천 채택]**

### 8.2 실행 방식 (계획 2, 내 판단)

- **작업 실행기**: AI 작업을 DB에 쌓고, 백엔드 안의 비동기 실행기(lifespan에서 시작, 기반의 단일 워커 전제 그대로)가 꺼내 처리한다. 동시 호출 수는 기존 `AI_MAX_CONCURRENCY` 세마포어가 정한다. 재시작하면 `running`이던 작업을 다시 `queued`로 돌린다.
- **DB 연결을 AI 호출 동안 잡지 않는다**: 스냅샷을 짧은 세션으로 읽고 닫은 뒤 AI를 부르고, 결과는 새 세션에서 `revision`을 확인하며 쓴다. 사용량 기록도 자기 짧은 세션으로 남긴다. 기반에서 남겨 둔 숙제(관리 화면 AI ping이 호출 동안 세션을 잡는 경로)도 같은 방식으로 고친다.
- **실패**: 시간 초과·5xx는 짧게 다시 시도한 뒤 `failed`. 연결 실패는 단위를 보류로 바꾸지 않고 미배정 그대로 두며, 묶음에 "AI 작업 실패 n건, 다시 시도"를 보인다(AI가 꺼져도 사람 경로는 그대로). 형식이 틀린 응답만 그 단위를 보류로 둔다.
- 작성자는 묶음의 작업 진행(대기·진행·완료·실패·낡음 건수)을 보고, 취소하고, 실패분을 다시 요청할 수 있다.
- 작업 상태는 묶음 밖에서도 보인다: 한 번의 요청이 쌓은 작업은 같은 요청 값(`request_id`)을 받고(입구 2 계획이 쌓는 `match` 작업은 계획 작업의 값을 잇는다), 멤버는 자기가 멤버인 묶음 전체의 대기·실행 중 작업과 하루 안에 끝난 작업을 요청별 진행 수(끝난 수 / 전체)와 함께 본다. 요청한 사람은 이름 없이 "나인지"만 싣는다. 상단 바 표시가 이것을 읽는다.
- 계획 2의 세부:
  - 대기 순서는 id 순이다. 묶음 사이 공평한 스케줄링은 하지 않아, 큰 묶음 뒤의 작은 묶음은 기다린다. (계획 2에서 정함)
  - AI가 꺼져 있으면 분류·번역·입구 2 짝·나누기 요청은 503이지만, 진행 조회·취소·다시 시도는 꺼져 있어도 된다. 쌓인 작업을 취소할 수 있어야 해서다(한/영 짝의 관문은 임베딩 사용이다, §7.11). 재시작으로 끊긴 작업은 AI가 꺼져 있어도 `queued`로 돌려 두고, 3번 시도한 뒤에는 `failed`(`interrupted`)다. 임베딩만 켜져 있으면 워커가 도니, 꺼진 채 실행되는 분류·번역·입구 2 계획·변경 종류·나누기 작업은 임베딩까지 아무것도 보내지 않고 재시도도 없이 `failed`(`config`)로 끝난다. 임베딩만 쓰는 `pair`는 그대로 돈다. (계획 2에서 정함)
  - 실패 코드는 `timeout`·`server_error`·`connection`·`client_error`·`config`·`interrupted`·`no_candidates`·`internal`이다. 서버 본문이 깨져 오면(JSON이 아니거나 필드가 없으면) `server_error`다. 429·408은 다시 시도하지 않고 `client_error`로 끝낸다(게이트웨이 근거가 아직 없어, 실제 모델 시험 때 다시 본다. 다시 시도 요청으로 풀 수 있다). (계획 2에서 정함)

### 8.3 스냅샷과 낡은 결과 [추천 채택: 이전 시도의 교훈]

- AI에 보내는 입력은 고정한 스냅샷이다(대상의 `revision`, 지침·프롬프트 버전, To-Be 목록 `revision`).
- 결과가 오면 다시 검사한다. 대상이 그사이 바뀌었으면 자동으로 적용하지 않고 낡은 결과로 남긴다. 늦게 온 응답이 다른 화면의 상태를 덮어쓰지 않는다.
- To-Be 목록의 변경은 묶음 `revision`이 아니라 응답이 고른 칸의 후보 유효성으로 낡음을 본다. 멤버 변경도 묶음 `revision`을 올려서, 그대로 쓰면 실행 중인 작업이 전부 낡음이 된다. 그래서 예전 목록으로 만든 제안이라도 고른 자리가 적용 때 살아 있으면 적용된다. (계획 2에서 정함)

### 8.4 임베딩

- 사내 임베딩 모델을 OpenAI 호환 `/embeddings`로 부른다. 새 env: `EMBED_ENABLED`, `EMBED_BASE_URL`, `EMBED_API_TOKEN`, `EMBED_MODEL`(settings·`.env.example`·compose 3곳). 한/영 짝 찾기에는 다국어 임베딩이 필요하다. **[결정: 사내 모델만]**
- **임베딩은 선택이다(내 판단)**: 꺼져 있으면 후보 추리기는 전체 칸(또는 글자 유사도), 입구 2는 같은 언어 글자 유사도, 한/영 따로 짝은 사람 손으로 한다. 사용 가능 여부와 "검색 실패 / 색인 없음 / 후보 없음"을 서로 다른 상태로 보여 준다. **[추천 채택]**
- 벡터는 캐시 표(§6.11)에, 유사도는 백엔드에서 계산한다(서버 postgres에 벡터 확장을 새로 넣지 않는다).
- 임베딩 호출도 사용량 기록을 남긴다(기능 이름으로 구분).
- 임베딩 호출의 재시도는 채팅과 같은 기준이다. 시간 초과·5xx·깨진 응답은 다시 시도하고 4xx는 바로 실패로 본다(검색 실패 상태로 간다). (계획 2에서 정함)

### 8.5 페이로드와 보안 [결정]

- SOP 원문은 사내 모델 주소로만 보낸다. 원문과 AI 응답 안의 지시문을 명령으로 실행하지 않는다: 원문은 구분자로 감싸 "데이터"로 넘기고, 응답은 정해진 JSON 필드로만 읽어 검증한다. 도구 호출·함수 호출은 쓰지 않는다.
- 앱이 덧붙이는 정보에 직원 실명·로그인 ID를 넣지 않는다(작성자·검토자 이름 등). 문서 원문은 그대로 사내 모델로 간다. (기반 원칙의 적용 범위, 내 판단)
- 모델 선택·후보 개수·프롬프트 문구는 빌더 몫이다. 프롬프트 문구는 지침 버전으로 관리한다(§6.10).

## 9. 권한과 공개 범위

- **새 권한 키**(기반 카탈로그에 추가, 프런트 미러·i18n과 한 커밋, 내 판단):
  - `bundle.create`: 묶음 만들기. 운영에서는 TF 부서들에 역할로 부여한다.
  - `bundle.admin`: 모든 묶음의 **메타 정보**(제목, 상태, 멤버, 진행 숫자) 목록과 멤버 변경. 내용은 멤버가 되어야 본다. 작성자가 모두 퇴직한 묶음을 정리하기 위한 권한이다. 자기를 멤버로 넣으면 작업 기록에 남는다.
  - `guideline.manage`: 지침·프롬프트 버전 올리기와 활성화.
- **묶음 내용은 멤버만 본다** **[추천 채택]**. 시스템 관리자(`APP_SYSADMINS`)도 멤버가 아니면 내용을 보지 않는다. 대신 `bundle.admin`을 가지므로 필요하면 자기를 넣을 수 있고 그 기록이 남는다(내 판단).
- **작성자**: 묶음의 모든 편집, 멤버 관리(마지막 작성자는 뺄 수 없음), 검토 요청과 요청 거두기, 다시 열기, 작업 중인 묶음 삭제(전부 영구 삭제, 전역 기록에 남음).
- 검토 대기 중에는 누구도 자기 역할을 바꾸지 못한다(409 `own_role_locked`, `bundle.admin` 경로 포함). 작성자가 자기를 검토자로 바꿔 자기 묶음을 검토 완료하지 못하게 한다. **(사용자 결정 2026-11-06)**
- **검토자**: 전부 읽기와 내보내기, 검토 대기 상태에서 검토 완료·되돌리기.
- 퇴직자(`active=false`)는 멤버여도 접근하지 못한다(기반 판정과 같은 규칙). 활성 작성자가 없는 묶음은 `bundle.admin` 목록에 표시한다.
- 권한 판정은 기반의 `get_effective_access` 하나에서 나오고, 멤버십 검사는 묶음 라우터의 의존성 하나에 모은다(새로 판정 함수를 흩뜨리지 않는다).

## 10. 제약

- **보안**: §8.5. 입력 검증은 API 경계에서 한다. 업로드는 §7.1의 거절·제한·별도 프로세스 파싱.
- **원문 불변 [결정]**: 원본 파일과 원문 글자는 바꾸지 않는다. 다시 추출해도 이전 검토 기록을 덮어쓰지 않는다.
- **밸리데이션 대상 아님 [결정]**: CSV(컴퓨터 시스템 밸리데이션) 대상이 아니다. 정식 검토와 승인은 EQUIS에서 한다. "확정"은 일반 버튼이고 전자서명·재인증이 없다. URS/FS, IQ/OQ 같은 밸리데이션 문서도 만들지 않는다.
- **작업 기록 [추천 채택]**: §6.11·§6.12. 원문과 인증값은 애플리케이션 로그에 남기지 않는다.
- **합성 검증 [결정]**: 실제 SOP와 사내 모델 자격증명은 아직 없다. 먼저 합성 자료로 검증하고, 합성 검증을 실제 연결 성공으로 기록하지 않는다(테스트 통과, 건너뜀, 실제 연동 결과를 따로 기록). 합성 문장은 합성이라고 표시하고 실제 SOP 인용처럼 보이게 만들지 않는다.
- **용어 [결정]**: SOP, WI, Binder, Instruction, Why 같은 문서 용어는 영문 그대로 쓴다. 화면 언어는 기반 규칙(영어 기본 + 한국어 전환)을 따른다.
- **배포 제약(기반 그대로)**: Python 3.11, Docker Hub 차단(베이스 이미지 태그 유지), backend env는 compose `environment:` 매핑, 단일 워커, Alembic. 새 의존성은 PyPI에서만 받고 서버 빌드 때 외부 다운로드(글꼴 등)를 하지 않는다.
- **새 의존성(후보, 버전·라이선스·3.11 호환은 빌더가 확인)**: 업로드 `python-multipart`, XML 안전 파싱 `defusedxml`, PDF `pdfminer.six`, 보조 `markitdown[docx,pdf]`, Excel `openpyxl`, 그림 `pillow`, 유사도 `numpy`. 개발용: 합성 DOCX 생성 `python-docx`.
- **메모리**: 파싱 프로세스와 MarkItDown 의존성 때문에 backend 메모리 상한(기반 1G)을 실측으로 다시 정한다.
  - 실측 결과 backend 상한을 2G로 올렸다(자식 최대 RSS 657MiB + backend 115MiB, `docs/qa/2026-11-sop-parse-dependencies.md`). (계획 1에서 정함)
- **백업**: DB에 SOP 원문과 원본 파일이 들어가므로 백업 덤프도 같은 대외비 자료다. 기존 백업 정책(디렉터리 0700, 오프서버 사본도 사적으로)을 그대로 적용하고 `docs/deploy/backup.md`에 적는다.
- **공개 저장소**: 저장소는 공개다. 도메인 문서(회의 자료의 SOP 번호·사례 포함)·지침 시드·이 설계 문서·합성 데이터는 저장소에 둔다. **(사용자 결정 2026-11-05)** 실서버 주소·시크릿·실제 SOP 원문은 기존 규칙대로 추적하지 않는다.

## 12. 화면 인수인계 (Claude Design 입력)

이 절은 프런트 1차 작업(Claude Design)에 넘길 내용이다. 모양·배치·디자인 컨셉·토큰은 그 단계에서 정하고, 큰 화면은 시안 2–4개를 보여 사용자가 고른다. **(사용자 결정, [결정])** 계획 1·2가 끝나면 이 절과 OpenAPI를 묶어 인수인계 문서를 만든다.

**화면 목록과 각 화면이 보여 줄 것·할 수 있는 것**
1. **묶음 목록**: 내가 멤버인 묶음(제목, 상태, 내 역할, 진행률), 새 묶음 만들기.
2. **묶음 개요**: 단계 ①–④ 진행, 언어별 요약 숫자, **지금 할 다음 행동**, 멤버, AI 작업 진행, 검토 요청 가능 여부와 막는 이유.
3. **문서**: 옛·새 문서 목록, 파일 이름에서 채운 번호·버전·제목(빈 칸은 채울 칸으로 표시), 언어 배치 선택, 추출 상태·경고·거절 사유, 보조 검사 결과.
4. **쪼개기(원문 대조)**: 원문을 인쇄본처럼 쪽 단위 용지로 보여 주고 그 위에서 바로 나누고 합친다. **[추천 채택: 이전 시도에서 반응이 좋았던 방식]**
   - 문장을 처음 누르면 선택만 된다. 다시 누르면 누른 자리에 나눌 선이 생기고, 나뉠 앞부분과 뒷부분이 다른 색으로 미리 칠해진다. 그 상태에서 버튼이나 `S`로 나눈다.
   - 줄을 더블클릭하면 그 줄이 선택된다(PDF 문단을 줄 단위로 나눌 때).
   - 글자를 끌어서 고르면 새 단위가 될 모습과 생길 경계를 미리 보여 준다.
   - 떨어진 문장은 "합칠 문장으로 고르기"로 번호를 붙여 고른 뒤 한 번에 합친다.
   - 경계 손잡이를 끌거나 방향키로 옮긴다. 되돌리기·다시 하기. 확인했던 판단이 사라질 때는 먼저 묻는다.
   - 키보드: `Enter` 확인하고 다음 단위로, `J`/`K` 다음/이전, `H` 사유를 남기고 보류, `U` 확인 취소, `S` 나누기.
   - 단위마다 KO/EN 표시와 바꾸기, 짝 표시, 누락 의심·병합 셀·자동 번호 경고.
5. **To-Be 목록**: 새 문서 표 편집(번호·제목·종류·부모·입구·장비 SOP), SOP 칸 N/A(사유), WI 단계, Excel 템플릿 내려받기·가져오기.
6. **분류(입구 1)**: 상태별 단위 목록(AI 제안 먼저). 한 단위(와 짝)를 원문, AI 제안(보낸 곳, 이유와 규칙 ID, 근거 위치, 한·영 고쳐 쓰기, 경고)과 함께 보고 확정 / 고쳐서 확정 / 보류. 나눔·합침 편집. 번역 요청. 키보드로 줄을 넘기며 확정.
7. **짝 맞추기(입구 2)**: 옛↔새 짝 제안(유사도는 확률로 보이지 않는다), 짝 없는 옛 단위(삭제 후보)와 새 단위(신규) 목록, 변경 종류 확정.
8. **결과물**: A·B·C × 한글판/영어판, 요약 숫자, Excel 내보내기, C에서 순서·단계 번호 바꾸기, 의미 검토 확인 4항목, 검토 요청.
9. **검토(검토자)**: 결과물 읽기, 검토 완료 / 이유 적어 되돌리기.
10. **관리**: 지침·프롬프트 버전(`guideline.manage`), 묶음 메타 목록과 멤버 변경(`bundle.admin`). 기존 관리 화면(권한·동기화·배치·AI)에 탭으로 붙인다.

**화면 규칙 [추천 채택: 이전 시도의 교훈]**
- 상태와 다음 행동을 먼저 보여 준다. 긴 설명은 도움말로 뺀다.
- 검색 실패, 색인 없음, 후보 없음을 다른 상태로 보여 준다. 유사도를 정답 확률로 보여 주지 않는다.
- 요청 처리 중, 내부 확정됨, 파일 생성됨을 다른 상태로 보여 준다.
- 팝업은 Esc, 포커스 복원, 바깥 클릭, 키보드 조작을 테스트한다(Esc 뒤에 다시 열리거나 스크롤과 엉키는 문제가 있었다).
- 합성 데이터와 실제 데이터를 구분해 표시한다.
- 오너가 화면 여러 개를 오가지 않게, 분류 화면에서 원문·제안·결과가 한눈에 보여야 한다.

## 13. 합성 데이터와 검증

- **합성 사례 [결정]**: 도메인 사례 §1의 QC Centrifuge. 옛 SOP 5개(`OLD-1`–`OLD-5`)를 새 SOP 1개와 WI 4개로 바꾼다. 합성 문서에는 한/영 문장(연달아·따로 배치 각각 한 문서 이상), 표, 그림(캡션 포함)을 넣는다. 본문은 대부분 표 밖 문단으로 쓰고, 레이아웃 표(한/영 두 열 또는 단계 | Instruction | Why)는 한 문서에만 하나 넣어 데이터 표 기본값과 레이아웃 표 바꾸기를 함께 검증한다. 일부러 누락 1건, 중복 배정 1건, 같은 문장 반복, 나눌 복합 문장, 삭제와 외부 이동 사례도 넣는다. 입구 1과 입구 2를 각각 한 번씩 거친다(입구 2용으로 새 SOP 또는 WI 문서 파일도 만든다).
- **만드는 법(내 판단)**: 합성 DOCX는 저장소의 생성 스크립트가 코드로 만든다(개발 의존성 `python-docx`). 파일 이름과 문서 속성에 합성 표시(`SYNTHETIC`)를 넣는다. 기대 정답(단위별 보낸 곳·변경 종류)은 같은 스크립트가 JSON으로 함께 만든다. 텍스트 PDF 1개도 합성으로 둔다. 메인 추출기가 놓치기 쉬운 자리(텍스트 상자 등)에 글을 넣어 보조 대조가 경고를 내는지도 본다.
- **API 수준 처음부터 끝까지 테스트**: 업로드 → 쪼개기 편집 → To-Be 입력 → (계획 1) 사람 경로 배정·짝 맞추기 / (계획 2) 가짜 AI가 기대 정답으로 답하는 경로 → 결과물 A·B·C → Excel(시트·칸·숫자 확인) → 검토 요청 → 검토 완료.
- **필수 테스트**
  - 옛 단위마다 상태가 정확히 하나다.
  - 미배정·AI 제안·보류가 0이 되기 전에는 검토 요청이 거절된다(일부러 남긴 누락 1건으로).
  - 중복 배정은 이유 없이 저장되지 않는다.
  - 커버 단위 범위가 블록의 공백 아닌 글자를 빠짐없이, 겹침 없이 덮는다(나누기·합치기·되돌리기 뒤에도).
  - 서로 다른 두 작성자가 같은 묶음을 각자 처리해도 결과물의 칸과 형식이 같다.
  - 낡은 AI 결과는 적용되지 않는다. AI가 꺼져 있어도 ①·④와 사람 경로가 돈다.
  - Excel에 수식이 들어가지 않는다(`=`로 시작하는 원문 포함).
- **채택률**: 묶음마다 AI 제안이 그대로 채택된 비율을 계산할 수 있다(§6.11). 이후 지침을 고치는 근거가 된다. **[결정]**
- **실제 SOP 시험**은 문서와 자격증명을 받은 뒤의 별도 단계다. 정확도 목표 숫자는 그 시험을 마친 뒤에 정하고, 그 전에는 배정 정확도를 숫자로 주장하지 않는다. **[결정]**
- **가짜 AI 검증은 합성 검증이다 (계획 2에서 정함)**: 가짜 AI(`tests/fake_ai.py` `SyntheticAnswers`)는 응답 하나에 담을 수 있는 답(한 자리, 같은 언어, 짝이면 자리와 변경 종류까지 같을 때)만 기대 정답으로 주고, 합침·중복 배정·표·외부 이동은 무효 응답으로 돌려 보류 → 사람 경로를 타게 한다. 이 시험은 실제 모델 연결의 증거가 아니다. 유사도 임계값(입구 2 임베딩·글자, 한/영 짝)도 합성 자료로만 잡은 값이라 실제 모델 시험 뒤 다시 정한다. 입구 2의 표 구성 변경 제안(`table_restructured`)은 합성 자료에 입구 2 표가 없고 입구 1 표는 사람 경로로 가게 해서, 끝까지 시험에는 넣지 않았고 단위 시험이 맡는다.
- **로컬 데모 시드**: 합성 묶음을 여러 단계(쪼개기 직후, 분류 절반, 검토 대기)로 로컬 DB에 넣는 스크립트를 둔다. 프런트 1차 작업(Claude Design)이 실제 모양의 데이터를 바로 쓰게 하기 위해서다(내 판단). 가짜 AI 서버(`frontend/scripts/fake-ai-server.mjs`)도 분류·번역·짝·임베딩 요청에 결정적으로 답하게 넓힌다(계획 2). 시드의 AI 단계는 프로세스 안의 가짜 전송 안에서만 돌고 시드는 AI 워커를 끈다. 합성 글이 실제 주소로 나가거나 떠 있는 워커가 시드의 작업을 다투지 않게 하려는 것이고, `reset_db`는 지침 첫 버전도 시드한다(없으면 떠 있는 백엔드의 Excel 내보내기가 500이다). (계획 2에서 정함)

## 14. 구현 순서

- **계획 1: 결정적 코어(AI 없음)**. 데이터 모델과 마이그레이션, 권한 키·멤버십, 묶음 상태 흐름, 업로드·거절·제한, DOCX·PDF 메인 추출, MarkItDown 누락 대조, 규칙 쪼개기·언어 판정·연달아 짝, 쪼개기 편집과 되돌리기, To-Be 목록과 Excel 가져오기, 사람 경로 배정·확정·보류(입구 1)와 수동 짝 맞추기(입구 2), 문장 검사, 결과물 A·B·C, Excel 내보내기, 검토 흐름, 작업 기록, 합성 데이터 생성기와 데모 시드. 끝나면 사람이 API만으로 두 입구를 끝까지 처리할 수 있다.
- **계획 2: AI 층**. 작업 실행기와 세션 분리(기반 숙제 포함), 임베딩 클라이언트·캐시, 지침·프롬프트 버전, 분류+고쳐 쓰기, 번역, 입구 2 짝 제안, 한/영 따로 짝 제안, 복합 문장 나누기 제안, 채택률, 가짜 AI 확장.
- **그다음**: 프런트 1차 작업(Claude Design)은 계획 2와 **병행**해 별도 워크트리에서 진행한다(시작 프롬프트는 v0.4.0 머지 뒤 삭제). 그래서 계획 2는 프런트가 읽을 AI API 계약을 계획 문서에 먼저 고정했고, 기존 응답에는 필드 추가만 했다. 두 작업이 main에 들어온 뒤 §12와 OpenAPI를 묶어 화면 연결 계획을 쓴다. (계획 2에서 정함) → 따로 계획은 쓰지 않았고 v0.4.0 화면은 `frontend/docs/design/2026-11-07-frontend-design-foundations.md`를 기준으로 만들었다(v0.5.0에서 계약 어긋남을 고쳤다).

## 16. 사용자 확인 결과 (2026-11-05)
