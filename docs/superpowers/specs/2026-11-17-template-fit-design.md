# 회사 템플릿·실사례 맞춤 설계

- 날짜: 2026-11-17 · 기준 코드: `dev` v1.1.18 (`12d8d20`). `파일:줄`은 이 시점 기준이라 밀릴 수 있다. 그래서 함수·상수 이름을 함께 적었다. 줄 번호가 안 맞으면 이름으로 찾는다.
- 성격: 브레인스토밍으로 사용자와 확정한 설계이고, 작업 세션에 넘길 프롬프트(§10)를 함께 담았다.
- 저장소 위치: `docs/superpowers/specs/2026-11-17-template-fit-design.md`. 첫 작업 세션이 이 위치에 넣고 `docs/README.md` 인덱스에 한 줄을 더한다.
- 근거 자료(작업 세션에는 없음): 사용자가 구해 온 회사 템플릿, 작성 가이드 덱(SOP용·WI용), QA 문서 PDF 5개, 실제 재구성 사례 2건. 2026-11-17에 사용자 PC에서 로컬로만 분석했다.

## 0. 먼저 읽을 것 (작업 세션용 전제)

1. **이 문서가 작업 세션이 받는 자료의 전부다.** 템플릿·실사례 원본은 회사 DRM이 걸린 기밀이라 세션에 넘길 수 없다. 구현에 필요한 사실은 부록 A–F에 글로 옮겼다. 거기에 없는 것은 추측하지 말고 사용자에게 묻는다. 사용자는 원본을 자기 PC에서 열어 볼 수 있다.
2. **시험 자료는 모두 합성이다.**
   - 부록 E대로 만들고, 파일 이름은 `SYNTHETIC_`로 시작한다.
   - 저장소에 넣지 않는 것: 실제 문장, 사람 이름, 회사 로고·아이콘 그림과 그 해시, 템플릿 파일.
3. **운영 DB에 작성 중인 문서가 없다고 가정한다(D3).**
   - 개발 스택의 기존 데이터는 옛 칸 값을 새 칸으로 옮기는 마이그레이션으로 살린다(D9).
   - 모델을 바꾸면 Alembic 리비전을 만든다.
4. **AI 규칙·프롬프트의 내용은 바꾸지 않는다(D6).** 칸 체계가 바뀌어 AI 후보의 배선을 맞추는 일만 한다(작업 1).
5. **파싱은 Word(DOCX)만 다룬다(D5).**
6. **"내 판단" 표시**: 설계 세션이 정했고 사용자가 아직 확인하지 않은 것이다. §9에 모아 두었다. 해당 작업의 계획을 사용자에게 보일 때 함께 확인받는다.
7. **저장소 규칙은 그대로 따른다.**
   - 화면·동작을 바꾸면 사용 설명서 글을 같은 커밋에서 고친다.
   - 새 권한은 3곳, 새 거절 코드는 i18n까지 넣는다.
   - `dev`에 푸시할 때마다 PATCH를 올린다.
   - 원문 글자는 로그에 남기지 않는다.
   - AI 페이로드에는 실명을 싣지 않는다.

## 1. 의도와 이유

- 사용자가 템플릿과 실사례를 구해 온 이유: **결과물과 미리보기가 사람들 눈에 익은 회사 템플릿 모양이면 좋겠다.** 그리고 실제 문서를 넣었을 때 쪼개기와 결과물이 실제 작성 관행과 맞는지 보고 싶었다.
- 실제 T/F는 두 입구를 모두 쓴다. 그런데 두 입구가 결과물·번호·미리보기를 따로 가지면 나중에 복잡해진다. 그래서 **모든 새 문서를 표준 골격 모델 한 벌로 다룬다(한 트랙, D10).**
- 최종 결과물은 두 입구 모두 **앱이 표준 양식으로 새로 만든 문서**다(D11). 그 단계는 다음에 하고, 이번에는 바탕을 깐다.
  - 올린 Word는 재료다.
  - 그 안의 메모와 변경 추적은 새 문서의 같은 문장 자리로 옮겨 붙인다(D12).
- 변경관리(CC/CCA)에는 앱의 Excel을 붙인다(D1).

## 2. 사용자 결정 (2026-11-17)

| # | 결정 |
|---|---|
| D1 | 실사례의 CCA 첨부 비교표는 사람마다 형식이 제각각이라 **참고만** 한다. 앱이 가진 정보로 보기 좋게 만든 Excel을 통일 양식으로 삼아 CCA에 붙인다. |
| D2 | SOP 절의 표준 골격은 **관리자가 고칠 수 있는 설정**이다. 템플릿이 바뀔 수 있기 때문이다. 표준은 권고다. 문서마다 벗어날 수 있되 사유를 남긴다. 기본값은 실제 작성자들이 쓴 형식, 즉 회사 SOP 템플릿 골격(부록 A)이다. |
| D3 | 운영에는 작성 중인 문서가 없다고 가정한다. 관리자가 표준을 바꿀 때 기존 문서를 어떻게 할지는 지금 고민하지 않는다. |
| D4 | WI는 실제 사용자 수준에 맞춰 서비스 방식을 조정한다. 세부는 작업 4에 있고 대부분 내 판단이다. |
| D5 | 파싱은 Word만 다룬다. 첫 업로드에서 100%를 노리지 않는다. 표는 묶음으로 잡고, 표 해제를 쓰면 다시 나눠도 된다. 목적은 사람이 편하게 나누고 합쳐 완결된 문장 구조를 만드는 것이다. |
| D6 | AI는 기존 규칙을 바탕으로 한다. 규칙 내용은 바꾸지 않는다. |
| D7 | 결과물 디자인: 화면 미리보기를 템플릿 모양으로 하는 것이 먼저이고, Word로 만드는 것이 최종 목표다. **PDF는 생략한다.** Excel을 Word처럼 꾸미지 않는다. 하이퍼링크·자동 번호·EQUIS 작성에는 Word가 맞다. |
| D8 | 변경 추적이 남은 Word도 받는다. 수락한 상태로 읽고, 메모는 해당 문장 옆에 보인다. 원래 변경 추적과 메모 정보는 버리지 않고 보관한다(D12를 위해). |
| D9 | 칸 체계를 바꿀 때 개발 스택에 남은 옛 칸 값은 **새 칸으로 옮기는 마이그레이션**으로 처리한다. 지우거나 "알 수 없는 칸"으로 두지 않는다. |
| D10 | **한 트랙.** 입구 2로 올린 새 문서도 표준 골격 위에 놓는다. 앱이 자리를 제안하고, 사람은 고칠 곳만 고친다. 결과물·번호·미리보기는 두 입구가 같은 코드로 만든다. 올린 문서의 번호가 엉성한 최악의 경우도 견뎌야 한다. |
| D11 | 최종 결과물은 두 입구 모두 **앱이 표준 양식으로 새로 만든 문서**다. 올린 원본 Word에 고침을 다시 써 넣지 않는다. 그래서 원본 왕복은 하지 않는다. 메모 답장도 원본 Word에 쓰지 않는다. |
| D12 | 올린 문서의 **메모와 변경 추적(누가 어디를 고쳤는지)**을 새 문서의 해당 문장 자리로 옮겨 붙인다. 변경 추적은 변경 추적 표시로 옮긴다. 가장 좋은 것은 메모 없이 정리된 문서를 올리는 것이고, 업로드 화면에서 그렇게 하라고 권한다. |

## 3. 목표 · 비목표 · 실패로 보는 것

**목표 (이번 범위)**
- 새 SOP의 결과물 C와 미리보기가 회사 SOP 템플릿과 같은 장·번호 체계를 따른다.
  - 번호: 장·절 제목(7.x·7.1.x 포함), 6장 내용, 부록 안
  - 그 밖의 내용은 글머리 기호
- 표준 골격은 관리자가 고친다. 작성자는 문서마다 사유를 남기고 벗어날 수 있다.
- 템플릿 문서, 표형 옛 SOP, 조항형 옛 SOP를 올렸을 때 다음 결과가 나온다.
  - 사람이 나누고 합치기 쉬운 단위
  - 맞는 번호와 절 위치
  - 한 번에 치울 수 있는 잡음
- 변경 추적이 남은 Word도 받아 읽는다. 메모는 해당 문장 옆에 보이고, 변경 추적·메모 원본 정보는 보관한다.
- WI 결과물이 실제 WI의 쓰임을 따른다.
  - 주의(Precaution) 자리
  - 장·단계·세부 단계 번호
  - WI로 가는 그림·표의 캡션은 선택
- 새 문서를 템플릿 모양으로 화면에서 미리 본다. 문서 번호는 EQUIS 링크, 목차는 문서 안 이동이다.
- 입구 2 문서도 표준 골격 위에 놓여, 결과물·번호·미리보기를 입구 1과 같은 길로 만든다.

**비목표 (이번 범위 밖)**
- Word 파일 만들기, 메모·변경 추적을 새 문서로 옮겨 붙이기, 앱 안 메모 답장. 설계만 해 둔다(§7).
- PDF 내려받기, PDF 파싱 개선.
- AI 규칙·프롬프트 내용 바꾸기, 실제 문서로 하는 AI 정확도 평가. §8에 기록만 남긴다.
- 실사례 CCA 비교표 모양 복제.
- 표가 레이아웃인지 코드가 정해 저절로 적용하는 것. 기본은 묶음이고, 해제는 사람이 한다.
- 입구 2 문서에 옛 단위를 새로 더해 넣는 것. 지금처럼 막는다(`match_doc_new_target`).

**실패로 보는 것**
- 표준 골격이 작성자를 막는다. 표준은 권고다. 사유만 남기면 벗어날 수 있어야 한다. 구조 지적은 경고일 뿐 검토 요청을 막지 않는다.
- 자동 판별을 늘리다 사람이 되돌리거나 고칠 수 없는 결과가 나온다. 모든 자동 처리는 기존 편집과 되돌리기로 풀 수 있어야 한다.
- 커버리지 불변식(보이는 모든 글자를 빠짐없이·겹침 없이 덮는다)이 깨진다. 잡음도 단위로 남기고 치우는 방식이다. 번호 떼기는 화면에서만 하고 범위는 고치지 않는다.
- 회사 로고, 템플릿 파일, 실제 SOP 문장, 사람 이름이 공개 저장소나 AI 페이로드에 들어간다.
- 템플릿 미리보기가 결과물 C와 다른 내용을 보인다. 같은 계산 결과를 다르게 그리는 것일 뿐이어야 한다.
- 입구 2 문서의 구조를 고쳤더니 이미 맞춘 짝이나 확정이 풀린다. 자리만 바뀌고 연결과 확정은 남아야 한다.

## 4. 방식 (고려한 길과 고른 길)

| 주제 | 고려한 길 | 고른 길과 이유 |
|---|---|---|
| 결과물 디자인 | (가) 화면 미리보기를 템플릿 모양으로 / (나) (가)에 Word 만들기를 더함 / (다) Excel만 템플릿 느낌 | **(가)를 지금, (나)를 최종으로(D7).** (가)는 원본 템플릿 없이 앱이 다시 그리므로 DRM·공개 저장소 문제가 없다. (다)는 화면과 따로 놀고, Word로 갈 길이라 버린다. |
| PDF | 브라우저 인쇄 / 서버 생성 | **생략(사용자).** 서버 생성은 빌드 제약 때문에 어렵다(PyPI·npm만 받고 Chromium·WeasyPrint는 설치할 수 없음). 나중에 필요하면 브라우저 인쇄 CSS가 가장 싸다. |
| 표준 골격 | 코드 상수(지금) / 관리자 설정 | **관리자 설정 + 문서마다 골격 사본 + 사유를 남긴 벗어남(D2).** 한 트랙에서 입구 2 문서의 표준 밖 구조를 담으려면 문서마다 사본이 있어야 한다. |
| 입구 2 문서 구조 | 두 트랙: 올린 문서 자신의 제목 구조 + 번호 검사 / 한 트랙: 표준 골격 위에 놓기 | **한 트랙(D10).** 두 트랙이면 이후 기능(미리보기, Excel 위치·번호, WI 번호, Word 만들기, AI 후보)마다 갈래가 하나씩 더 생긴다. 실측으로 확인했다.<br>• 실제 To-be 5개(SOP 2, WI 3)에 시험용 맞춤 규칙을 돌렸다. 구조 요소 619개 중 618개(99.8%)가 확실한 신호로 맞춰졌고, 갈 곳 없는 문장은 0개였다.<br>• 규칙을 같은 문서로 다듬었으므로, 처음 보는 템플릿 문서는 90–98%로 예상한다.<br>• 엉성하게 흉내 낸 문서도 골격은 대개 찾지만, 확실한 비율은 15–70%로 떨어진다(부록 D).<br>구조는 저장하지 않고 **규칙 + 사람의 고침으로 매번 계산**한다(작업 7). |
| 최종 Word | 원본 Word에 고침을 다시 쓰기 / 표준 양식으로 새로 만들기 | **새로 만들기(D11)** + 메모·변경 추적 옮겨 붙이기(D12). 원본에 다시 쓰려면 번호·제목 이동을 변경 추적으로 써야 해서 매우 어렵고 깨지기 쉽다. |
| 변경 추적 Word | 거절(지금) / 수락한 상태로 읽기 / 수락한 상태로 읽기 + 원래 정보 보관 | **수락한 상태로 읽기 + 보관(D8).** 지금의 거절은 사용자 결정이 아니라 내 판단이었다(제품 명세 §7.1). |
| 표 처리 | 데이터 표 기본(지금) / 코드가 레이아웃 제안 / 템플릿 표 자동 해제 | **데이터 표(묶음) 기본, 해제는 사람이 한다(D5).** 해제하면 칸 구조대로 다시 나눈다. 절 경로는 추출할 때 미리 잡는다. 같은 꼴 표를 한꺼번에 해제하는 단추는 편의로 둔다(내 판단). |
| 개발 데이터 | 마이그레이션으로 옮김 / 서버에서 비움 / 그냥 둠 | **마이그레이션(D9).** |
| 비교표 | 실사례 형식 복제 / 앱 정보로 통일 | **앱 정보로 통일(D1).** 세부는 사용자 확인 뒤에 정한다(작업 6). |

**2b. 표는 묶음, 해제하면 칸 구조대로 다시 나눈다. 절 경로는 추출 때 미리 잡는다.**
- 기본은 지금처럼 데이터 표다. 표 하나가 한 묶음이다.
  - 이미 있는 표 해제는 `editing.py`의 `SetLayoutTableOp`(`set_layout_table`, `_plan_set_layout_table`)다. 되돌리기가 되고, 지금은 칸 글을 행 순서·왼쪽부터 일반 문단처럼 읽는다.
- **절 경로는 추출할 때 잡는다(내 판단).** 블록은 바뀌지 않으므로, 해제 여부와 상관없이 다음이 블록의 `section_label`·`heading_level`을 정한다. 그러면 표 뒤의 일반 문단도 맞는 절 경로를 받는다. 해제는 단위 묶음만 바꾼다.
  - **표형 옛 SOP**:
    - 한 행짜리 띠 표(부록 C: 번호 칸 | 좁은 빈 칸 | 제목 칸)의 번호와 제목이 절을 만든다.
    - 수준은 번호의 점 개수로 센다("7" → 1, "7.4" → 2). 제목 스타일 수준은 믿지 않는다. 이 꼴은 스타일 수준이 언어마다 달라 판별할 수 없다.
  - **템플릿 WI**:
    - `Chapter N.` 행(음영 머리 행, `tblHeader`)과 공정 단계 행(`SBL_Process Step` 스타일 또는 numPr ilvl=1인 전체 폭 행)이 절 경로 "언어 절반 › Chapter N › N.M"을 만든다.
    - 앞장 표(작업 2c) 안의 제목 스타일은 무시한다.
  - 판별은 문서 꼴마다 따로 한다. 신호가 없으면 지금 동작을 유지한다.
- **해제하면 칸 구조대로 나눈다.** 2a에서 저장한 블록 신호를 쓴다.
  - 칸 안 문단 경계는 그대로 단위 경계 후보가 된다.
  - **라벨 칸**: 칸 글 전체가 `^[A-Z](-\d+)?$`(A, A-1)나 `^\d+(\.\d+)*$`이고 같은 행 다음 칸에 글이 있으면, 라벨을 그 행 첫 단위의 앞 범위로 붙인다. 블록을 넘는 범위는 이미 된다(`segment.build_unit_text`). 언어 판정에서 라벨은 중립이다.
    - 세로 병합(`vMerge`)으로 이어지는 행은 라벨을 물려받는다.
    - 같은 라벨이 연달아 반복되면 한 세부 단계로 본다.
  - **중첩 표**: 레이아웃 표 안의 중첩 표는 그대로 데이터 표 묶음이다.
  - **아이콘**: 아이콘은 그 문장의 표시가 된다(2c).
- **같은 꼴 표 한꺼번에 해제**(편의, 내 판단): 한 표를 해제할 때 "이 문서의 같은 꼴 표도 모두 해제"를 고를 수 있다.
  - 같은 꼴은 첫 행 글 패턴과 열 수로 본다. 예: 첫 행 `Chapter \d+\.`, 머리 `단위 업무 | 세부 업무 내용`.
  - 저절로 적용하지는 않는다.
- 시험(부록 E): 템플릿 WI 꼴과 표형 옛 SOP 꼴로 확인한다.
  - 추출 때 절 경로가 맞는다.
  - 해제 전에는 표가 한 묶음이다.
  - 해제 뒤에는 단계마다 단위가 있고, 라벨은 앞 범위이며, 중첩 표는 묶음이다.
  - 되돌리면 원래대로이고, 커버리지는 그대로다.

**2d. 제목 스타일 조항 → 문장 (조항형 옛 SOP)**

  - 번호 없는 한글 짝 제목이 자기 글 전체를 절 이름으로 삼는다(`docx_reader.py` `_update_section_label`, 호출 약 1105행). 그런 블록이 106개다.
  - 제목이 된 원인은 `_HEADING_STYLE_RE`(fullmatch라 "제목 N수준"에 안 맞는다)가 아니라 개요 수준 상속(약 789–793행)이다.
- 고칠 방향:
  - `heading_level`은 구조 수준으로 남겨 절 경로에 쓴다.
  - 단위 종류는 "제목다움"으로 정한다. 문장 끝이 둘 이상이거나, 라벨 뒤 글이 약 60자를 넘고 마침표로 끝나면 `sentence`로 보통 나누기를 한다.
  - 번호 없는 짝 제목은 앞의 번호 있는 제목의 라벨을 물려받는다.
  - 남는 것을 위해 편집 연산 **"제목 ↔ 문장 바꾸기"**를 양방향으로 더한다. `editing._write_change` 길에 얹어 되돌리기가 되게 한다. 굵은 글씨로만 쓴 제목을 사람이 "제목으로" 바꿀 때도 이 연산을 쓴다.
- 측정:
  - 조항형 합성 문서에서 여러 문장인 제목 단위가 0이다.
  - 본문 블록의 절 라벨이 번호나 짧은 제목이다.
  - 템플릿 SOP의 제목 수준은 바뀌지 않는다.

### 작업 3 – 변경 추적·메모 읽기와 보관

**지금**: 변경 추적(ins·del·moveFrom·moveTo)이 있으면 `docx_reader.py` `_check_revisions`가 `ExtractionRejected("tracked_changes")`로 거절한다. 메모는 읽지 않는다.

**바꿀 것**
1. **수락한 상태로 읽는다.**
   - 남기는 것: `w:ins`, `w:moveTo`
   - 버리는 것: `w:del`·`w:delText`·`w:moveFrom`
   - 문단 표시가 지워졌거나(`w:pPr/w:rPr/w:del`) 옮겨 간(`w:moveFrom`) 문단은 다음 문단과 합친다. `moveFrom`을 빠뜨리면 빈 번호 제목이 생긴다(실측).
   - 지운 표 행도 뺀다.
   - `*PrChange`는 무시한다.
   - 결과는 Word의 "모든 변경 내용 적용"과 같아야 한다.
   - 경고 `tracked_changes_accepted`(건수)를 남기고 화면에 보인다.
   - 여러 문단이 합쳐져 생긴 문단은 "수락하며 합쳐진 문단"으로 표시해 사람이 보게 한다. 실측에서 제목 하나가 여러 문단 조각으로 합쳐진 경우가 있었다.
2. **변경 추적 원래 정보를 보관한다(D12).** 수락한 글 위의 위치(블록 + 글자 범위)에 다음을 묶어 새 표에 남긴다.
   - 넣은 글의 범위
   - 지운 글(지운 내용 그대로)과 그 자리
   - 옮긴 글
   - 작성자(파일에 적힌 이름)와 시각
3. **메모를 읽어 보관한다.**
   - 읽을 곳: `comments.xml`, `commentsExtended.xml`(스레드 `w15:paraIdParent`, 해결 `done`), `commentsIds.xml`, `people.xml`

   - 보관하는 것: 메모 id, 작성자, 시각, 글, 부모, 해결 여부, 위치
4. **보인다.** 쪼개기·배정 화면에서 해당 단위 옆에 메모 표시와 스레드, 변경 추적 흔적("고친 곳 있음")을 보인다.
   - 모든 DOCX(Old·New)에서 읽는다(내 판단).
   - 업로드 화면에 "메모·변경 추적은 정리하고 올리기를 권장"한다는 안내를 단다.
5. **지킬 것.**
   - 작성자 이름, 메모 글, 지운 글은 AI 페이로드에 넣지 않는다.
   - 로그에도 남기지 않는다.
   - 화면에 이름을 보이는 것은 된다(사내, 묶음 멤버만 – Excel의 확정자 이름과 같은 판단).

**검증**

### 작업 7 – 입구 2 문서를 표준 골격에 얹기 (한 트랙, D10)

**지금**
- 입구 2 문서의 새 문장은 올린 문서의 제목 경로(`section_path`, 제목 글을 " › "로 이은 것)로만 놓인다(`match.py` `_plan_targets`, `_refresh_targets`, `sync_new_doc_targets`).
- 결과물 C는 그 글로 줄을 묶고(`outputs._plan_sections`의 match 갈래) 번호를 매기지 않는다.
- 입구로 갈라지는 코드는 backend 22곳, frontend 26개 파일이다.
- 번호 글이 엉성하면 문제가 생긴다. 같은 번호가 두 번 나오면 다른 절이 한 칸으로 합쳐지고, 굵은 글씨 제목은 제목으로 안 잡힌다.

**방식: 자리는 저장하지 않고 계산한다(파생 배치).**
- 새 문장 행에는 지금처럼 `section_path`를 두고(출처 정보, AI 맥락), **`section_key`(그 문장을 담는 제목 블록의 seq)**를 더한다. 블록은 바뀌지 않으므로 편집·되돌리기에도 안정하다.
- **구조 맞춤 = 규칙 + 사람의 고침.** 제목 블록 → 골격 항목의 대응은 순수 함수가 매번 계산한다. 사람이 고친 것만 표(문서, 제목 블록 seq, 골격 항목, 사유)에 남긴다.
- 결과물을 만드는 맨 앞의 어댑터 하나가 스냅숏을 받아 다음을 정한다.
  - 각 새 문장의 골격 자리
  - 깊이
  - 한글 짝 번호 생략(한/영 짝은 영어 번호 하나를 같이 쓴다. 입구 1과 같다)
  - 번호 라벨 떼기(화면에서만)
- 그다음은 입구 1과 같은 길이다. `outputs._plan_sections`의 match 갈래와 `_format_target_location`의 `section_path` 대체를 지운다.
- 이 방식이면 새 문장 행이 구조 맞춤 때문에 바뀌지 않는다. 그래서 다음은 건드리지 않는다.
  - `sweep_translations`(확정 번역 보류)
  - 판단 되돌리기
  - `match_target_locked`·`settle_pairs`
- 짝 맞추기·확정은 구조와 상관없이 지금처럼 돈다. AI `match_plan`도 구조를 쓰지 않는다.

**맞춤 규칙** – 시험용 맞춤기로 실제 문서와 엉성하게 흉내 낸 문서 27가지에서 검증한 최소 규칙이다.
- 각 판정은 **확실(HIGH)** 또는 **추정(LOW)**이고, 맞출 수 없으면 **미맞춤**이다.
- 번호 글자(타자든 자동이든)로 구조를 정하지 않는다. 번호는 다시 세고, 원문 번호와 견주는 데만 쓴다.

| 대상 | 규칙 |
|---|---|
| 빼는 것 | 목차 줄(`toc N` 스타일, 또는 끝이 탭 + 쪽 번호), 제목 문단, 첫 장 앞의 모든 것(표지, 안내 글) |
| 언어 절반 | 작업 2a P-LAYOUT과 같다 |
| 장 | 확실: 표 밖 문단이고, 스타일이 `SBL_Text 1*`이거나 개요 수준 0이며, 앞 번호를 뗀 글이 장 9개 이름(영어 + 한글 변형)에 있다.<br>추정: 이름만 맞거나 40자 이내 굵은 줄이 맞는데, 장 순서를 앞으로 나아가게 할 때만.<br>모르는 이름의 1수준 스타일 제목은 미맞춤(벗어남 후보)이다. 하위 수준 스타일은 장이 될 수 없다. |
| 6장 | 절차: `SBL_Text 2*` 또는 개요 수준 1이면 확실. 굵은 짧은 줄, 또는 바로 뒤에 3수준 항목이 오는 짧은 줄이면 추정.<br>깊이: `SBL_Text N`이면 N-2. 없으면 numPr ilvl이나 타자 번호 "6.n.m".<br>흐름도: 첫 칸이 "Flow chart"인 표.<br>한·영 절차 이름은 수가 같을 때 순서로 짝짓는다. 한글 절반의 절차·범주 이름은 한글이다. |
| 5장 | 머리가 `Category \| Requirement`인 표. 첫 열 칸이 범주이고, 권장 목록(영어 + 한글)에 있으면 확실, 아니면 추정. 전체 폭 행은 범주 없는 항목이다. 표 해제가 필요하다(작업 2b). |
| 2–4장 | 머리 행으로 표를 알아본다(Site\|Building\|Functional Unit\|Product, Manufacturer\|Model Name, Term\|Definition, Role\|Responsibility). |
| 7장 | 7.x는 이름(Associated Documents, Work Instructions, References)으로 맞춘다. 7.1.x는 제목이 아니라 번호 붙은 내용 문단이므로 그 글(Form, Visual Aid, Training Material, Quality Risk Assessment)로 맞춘다. |
| 8·9장 | "Attachment N.", "Appendix N.", `SBL_Appendix title` 스타일 |
| WI 장 | 맨 위 표의 첫 행이 전체 폭 한 칸이고 "Chapter N"이다. 음영이나 `tblHeader`가 있으면 확실, 없으면 추정. 장 머리 스타일은 믿지 않는다(한글은 `heading 1`, 영어는 대개 `Normal`). |
| WI 단계 | `SBL_Process Step*`이면 확실. 아이콘이 없고 Key Point가 아닌 전체 폭 한 칸 행이거나, 굵게 + numPr ilvl 1 또는 타자 "N.M"이면 추정. |
| WI 세부 단계 | 첫 칸이 `^[A-Z](-\d+)?\.?$`이면 확실(A-n은 깊이 1). 느슨한 라벨 꼴이나 글 칸 앞의 "A. "이면 추정. |
| WI 주의 줄 | 그 문서 Key Symbol 범례 행의 아이콘과 같은 그림이 든 문단. 첫 라벨 앞이면 단계 줄, 아니면 그 세부 단계 줄이다. |
| WI 고정 틀 | Document Information, Governing SOP, Table of Contents, Instruction 띠, Document Relationships(Associated / Reference Documents / Attachments)를 이름으로 찾는다. Process Flow는 선택이다. |
| 나머지 | 가장 가까운 맞춘 윗항목 아래의 **사용자 항목**이 된다(작업 1의 문서 사본). |

**번호**
- 이 문서가 최종 결과물의 재료이므로(D11), 결과물·미리보기·Excel의 번호는 앱이 센 번호다.
- 숨긴 도우미 문단까지 세면, 실제 문서의 원문 번호와 앱이 다시 센 번호가 모두 같았다(SOP 35/35·36/36·40/40·40/40, WI 단계 11/10/3).
- 다른 곳은 지울 필요가 없는 **알림**(구조 지적)으로 남긴다. 실측된 예:
  - 번호를 끈 번호 스타일 문단
  - 끝에 남은 빈 번호 문단
  - 타자로 친 "1.10"
  - 빠진 라벨(G-3)
- 타자로 친 번호 라벨은 화면에서만 뗀다(블록 신호의 라벨 범위, 작업 2a P-SIGNALS). 단위 범위는 고치지 않는다.

**구조 지적 창 (막지 않음)**
- 문서마다 **한·영 절반의 골격을 나란히** 보이고, 어긋난 곳에 표시를 한다.
  - 실측에서 5개 중 2개 문서에 절반 차이가 있었다: 한 절의 항목 4 대 5, 한 단계의 세부 단계 28 대 50.
  - 한쪽 절반에만 빠진 항목은 그 내용이 앞 항목에 조용히 섞이므로, 이 비교로만 드러난다.
- 지적 목록:
  - 미맞춤 장 → "표준 항목에 잇기" 또는 "사유 달고 벗어남으로 두기"
  - 추정(LOW) 절차·단계 → 받아들이기 또는 내리기. 굵은 글씨가 많은 문서에서는 거짓 절차가 생긴다. 다른 절반과 수를 견주어 드러낸다.
  - 한·영 절차·범주 수 차이와 이름 짝
  - 같은 라벨 반복 → 이어지는 행인지 새 세부 단계인지
  - 라벨·번호 건너뜀, 중복, 수준 건너뜀
  - 타자 번호와 자동 번호가 섞임
  - 수락하며 합쳐진 문단(작업 3)
  - 제목으로 안 잡힌 굵은 글씨 줄 후보
- 사람은 제목 하나를 골라 다른 골격 항목으로 옮기거나, 사유를 달거나, 추정을 받아들이거나 내린다.
- 지적이 없으면 따로 확인할 일이 없다. 별도 "구조 확인" 단계는 두지 않는다. v1.0.18에서 경계 확인 단계를 없앤 것과 같은 판단이다.
- 검토 요청은 막지 않고 경고만 한다(D2).
- 실측 기준으로 문서당 사람이 볼 지적 수: SOP 0–8개, WI 0–6개.

**템플릿 꼴이 아닌 업로드**
- 장 제목이 거의 안 맞으면(문턱값은 빌더 재량) "자유 구조"로 둔다. 같은 모델 안에서 사용자 항목만 쓰고, 번호는 원문 번호를 보인다.
- 실측에서 표형 옛 SOP는 장 0/12, 조항형 옛 SOP는 7/22만 맞았다.
- "입구 1로 다시 하기를 권장" 안내 띠를 보인다.

**한/영 절반이 어긋날 때**
- 장은 절반마다 따로 맞춘다.
- 절차·범주·줄을 번호나 순서로 짝짓는 것은 수가 같은 항목 안에서만 한다.
- 수가 다르면 지적을 남기고, 사람이나 기존 AI 짝에 맡긴다.

**구조를 나중에 고칠 때**
- 자리만 다시 계산되고 짝과 확정은 남는다.
- 결과물에는 "확정 뒤 자리 바뀜" 표시를 단다.

## 7. 다음 단계 설계 (이번 범위 밖, 설계만)

**Word 만들기 (두 입구 공통, D11)**
- 관리자가 템플릿 DOCX(DRM 해제본)를 앱에 올린다. DB에 보관하고 공개 저장소에는 넣지 않는다. 작업 1의 관리자 설정 화면과 같은 자리다.
- 생성기는 그 파일을 복사해 작업 5와 같은 구조로 채운다.
  - 스타일은 이름으로 찾고(부록 A·B), styleId는 올린 템플릿에서 해석한다.
  - 목차 필드는 열 때 갱신한다(`w:updateFields`).
  - 문서 번호에는 EQUIS 하이퍼링크를 건다.
  - 4수준 이하 번호는 템플릿 자체가 이상하다(부록 A "번호의 함정"). 그래서 깔끔한 다단계 목록을 쓸지 정한다.
- 그림·표는 원본 파일(`document_files`)에서 가져온다. 병합 칸이 많은 표, 그림 캔버스, WI 장 표의 세로 병합은 손실 없이 옮기기 어렵다. 이 부분을 가장 먼저 시험한다.
- 라이브러리: python-docx를 `requirements.txt`로 옮긴다(지금은 dev 전용 1.2.0). lxml은 이미 운영 의존성이다.

**메모·변경 추적 옮겨 붙이기 (D12)**
- 작업 3이 보관한 메모와 변경 추적을, 새 문서의 같은 문장(새 문장 ← 출처 단위 연결) 자리에 다시 단다.
  - 메모는 Word 메모로 다시 달고, 스레드와 해결 상태를 지킨다.
  - 변경 추적은 같은 범위에 `w:ins`/`w:del`로 다시 그린다. 작성자와 시각은 원래 값이다.
- 앱에서 그 문장을 다시 고쳤거나 다른 문서·자리로 옮겼다면 옛 변경 추적이 새 글에 맞지 않는다. 그때는 **메모로 바꿔 붙인다**("원본 변경 추적: 누가, 언제, 무엇을").
- 앱의 고침 자체를 변경 추적으로 보일지는 그 단계에서 정한다.

**앱 안 메모 답장**
- 앱에서 메모에 답하고 해결을 표시한다. 그 결과는 새 문서로 옮겨 붙일 때 스레드로 함께 간다.
- 원본 Word에는 쓰지 않는다(D11).

**새 판 올리기 (입구 2)**
- 작성자가 Word를 고쳐 다시 올리면 지금은 문서를 지우고 새로 올려 짝이 모두 풀린다.
- 짝을 지키는 "새 판으로 바꾸기" 업로드가 필요하다. 그 단계에서 일정을 잡는다.

## 8. 이번 범위 밖으로 둔 발견 (기록)

- **AI 규칙 후보** (D6으로 미룸):
  - R02 문체: 실제 To-be SOP 한글은 대부분 "~한다" 그대로다. 문단 끝 기준으로 의무형 4·6 대 "~한다" 28·29다.

  - 규칙에 없는 실제 삭제 근거:
    - Policy 절(템플릿에 없음)
    - 일반 책임(교육받고 따른다, 이 SOP를 승인한다)
    - 절차 안에서 할 일이 없는 역할
    - 본문에서 인용하지 않은 참고 문서(한 사례에서 16개 중 10개)

  - 옛 SOP 절 → 템플릿 장 기본값 표가 있으면 도움이 된다.
- **실제 문서 평가 (로컬 전용)**:
  - 사례 1을 시험용, 사례 2와 QA 문서를 개발용으로 쓴다. 사례 1은 옛 조항 254행 → 새 SOP 1·WI 3·삭제다. QA 문서는 한·영 절반의 절 번호가 같아 짝 정답이 된다.

## 9. 내가 정한 것 (사용자 확인 대상)

모두 **미확인**이다. 해당 작업의 계획을 보일 때 함께 확인받는다.

1. 관리자의 표준 변경은 새 문서부터 적용한다(작업 1).
2. 장비 SOP의 N/A 권장을 없애고, 장비 표시는 권장 절 이름 띄우기에만 쓴다(작업 1).
3. 옛 AI 칸 ID → 새 후보 대응표(작업 1 #11).
4. 8장은 배정할 수 있는 글머리 기호 항목이고 "Attachment 1. Document Change History"는 시스템 항목이다. 9장은 선언하는 부록이고 안은 부록 번호로 센다. 7.1.x 번호는 남은 항목끼리 세고, 5장에는 범주 없는 항목을 허용한다(작업 1).
5. 병합 경고 정리(P-MERGEWARN), DRM 판정은 업체 이름 없이 일반 신호로 한다(P-DRM).
6. 절 경로는 추출 때 잡고, 표형 옛 SOP는 띠 표 번호의 점 개수로 수준을 정한다(작업 2b).
7. 같은 꼴 표 모두 해제(자동 적용 아님), 범례 없는 아이콘은 `unknown`, 새 문서의 잡음 단위는 새 문장을 만들지 않는다(작업 2).
8. 메모·변경 추적은 Old·New 모든 DOCX에서 읽는다(작업 3).
9. WI의 장 모델, 깊이 2 이상 `A-1-1`, `unknown` 아이콘은 주의로 제안, WI 캡션 선택(작업 4).
10. 미리보기 표지를 위한 선택 입력 칸, 2장 표는 빈 칸으로 두고 In Scope 아래에 둠, 3·4장 줄 라벨 입력은 하지 않음, 언어 절반 순서와 짝 번호 공유(작업 5).
11. 작업 7: 파생 배치, 별도 확인 단계 없음, 지적은 막지 않음, 자유 구조 모드, 앱 번호 우선 + 차이는 알림.
12. 작업 6 전체(사용자 확인 뒤 시작).

## 부록 A – 회사 SOP 템플릿 사실

**쪽**: A4 세로, 여백 사방 2 cm, 머리글 1.5 cm, 바닥글 1.75 cm, 구역 하나.

**순서**
1. 제목 문단(스타일 `Title`, 글 "Document Title")
2. 표지 표
3. 녹색 안내 글
4. 쪽 나눔, 영어 목차(`TOC \o "1-2" \h \z \u \b Eng`)
5. 쪽 나눔, 한글 목차(`\b Kor`)
6. 쪽 나눔, **영어 본문 전체**(책갈피 `Eng`)
7. 쪽 나눔, **한글 본문 전체**(책갈피 `Kor`)

**표지 표 "Summary of Changes for Current Version"**
- 8행 × 4격자, 너비 약 1.7 | 1.7 | 4.8 | 7.7 cm.
- 테두리는 모두 실선 0.5 pt.
- 라벨 칸은 음영 `E6E6E6`, 굵게. 라벨이 값의 **위 칸**에 있다.

| 행 | 내용 |
|---|---|
| R0 | 병합 제목 "Summary of Changes for Current Version" |
| R1 | `Document No.`(3칸 병합) \| `Ver.` |
| R2 | 값 |
| R3 | `Record No.`(2칸) \| `Title`(2칸) |
| R4 | 값 |
| R5–R6 | `Section No.`(아래에 `ENG` \| `KOR`) \| `Description of Change`(세로 병합, 2칸) |
| R7 | 값(Description은 글머리 기호) |

- 승인·서명 칸, 판 이력 표, 시행일 칸은 없다. EQUIS가 렌디션에 찍는다.

**골격** (영어 절반)
- 한글 절반도 같은 번호다. 장 제목, 7.x 이름, 표 머리, "Note."는 한글 절반에서도 영어 그대로이고, 절차 이름만 한글("절차 1/2/3")이다.

```
1. Purpose                      – 글머리 기호(문장 줄기 1줄)
2. Scope                        – 표 Site|Building|Functional Unit|Product, 이어서 "Equipment information" 표 Manufacturer|Model Name,
                                  글머리 기호 "In Scope" / "Out of Scope"(각각 아래 대시 항목)
3. Definitions                  – 문장 줄기 "...provided in EQUIS Glossary:" + 대시 항목 "용어 (GS-번호)",
                                  문장 줄기 "...provided below:" + 표 Term|Definition
4. Responsibilities             – 표 Role|Responsibility
5. General Requirements         – 표 Category|Requirement 하나 (5.x 제목 없음)
6. Procedures                   – 먼저 `Flow chart` 표(그림 캔버스: 상자에 "WI-00000 / <작업 이름>", End, Yes/No)
   6.1 Procedure 1 / 6.2 Procedure 2 / 6.3 Procedure 3   – 작성자가 이름 붙이고 반복. 6.n.n.n.n까지
7. Document Relationships
   7.1 Associated Documents
      7.1.1 Form / 7.1.2 Visual Aid / 7.1.3 Training Material / 7.1.4 Quality Risk Assessment   – 제목이 아니라 번호 붙은 내용 문단(굵게)
   7.2 Work Instructions
   7.3 References
8. Attachments                  – 실제 문서는 늘 "Attachment 1. Document Change History"
9. Appendices                   – 굵은 타자 글 목록 "Appendix 1./2./3." 뒤에 부록마다 쪽 하나(제목 "Appendix N.").
                                  부록 안 번호는 그 부록 번호에서 다시 센다(Appendix 2 안은 2., 2.1.)
```

**SOP 가이드 덱에서**
- 5장 범주 후보: Safety, Account, Qualification, Equipment, Work, Excursion/Alarm, Material, Training, Record, Quality, Caution. 한글 덱에는 Data Management가 더 있다.
- 6장:
  - 절 이름은 작성자가 정한다.
  - 흐름도가 먼저이고, 상자에 WI 번호와 제목을 넣는다.
  - 제목 수준은 최대 5다.
  - "Note."는 그 항목 아래에 둔다.
- 7장:
  - 둘째 수준(7.1/7.2/7.3)은 비어도 N/A로 남긴다.
  - 셋째 수준(7.1.x)은 비면 지운다.
  - 본문에서 인용한 문서는 목록에 있어야 한다.
- 본문에서 다른 문서는 번호만 쓴다. 문서 안 참조는 '8.1 Cleaning'처럼 따옴표 안에 번호와 이름을 쓴다.
- SOP의 그림·표에는 캡션을 단다.

**스타일과 번호** (Word 만들기와 파싱에 필요)

| 스타일 이름 (EN / KO) | 쓰임 | 번호 꼴 |
|---|---|---|
| `SBL_Text 1_Eng` / `_Kor` | 장 1–9, 개요 수준 0 | `%1.` |
| `SBL_Text 2_Eng` / `_Kor` | 6.1, 7.1 …, 개요 수준 1 | `%1.%2.` |
| `SBL_Text 3_Eng` / `_Kor` | 6.1.1(내용 있는 번호 문단), 7.1.x | `%1.%2.%3.`. 영어 쪽은 numId를 `SBL_Text 2_Eng`에서 **물려받고** 자기 ilvl=2만 준다(P-NUM1의 원인). |
| `SBL_Text 4–6_Eng` / `_Kor` | 6.x.x.x 이하 | 따로 된 목록으로, 글자 "6."이 박힌 꼴 `6.%2.%3.%4.` |
| `SBL_Dot 1–5` | 글머리 기호의 들여쓰기 단계 | Wingdings 작은 검은 원(U+F09F) |
| `SBL_Dash text` | 대시 하위 항목 | `-` |
| `SBL_Text contents` | 표 글, 목차 제목 | |
| `SBL_Appendix title_Eng` / `_Kor` | 부록 제목(개요 수준 1) | 글자 "Appendix N." |
| `SBL_Appendix 1–4_Eng` / `_Kor` | 부록 안 번호 | `%1.` `%1.%2.` … |
| `Title` | 문서 제목 | |

- 기본 `heading 1/2` 스타일은 쓰지 않는다. 제목은 `outlineLvl`로 잡힌다.
- 실제 문서에서는 한글 절반이 `_Eng` 스타일을 쓴 경우가 있었다. 절반 판정은 책갈피가 확실하다.
- **번호의 함정**: 4수준 이하는 숨긴 도우미 문단(문단 표시를 숨긴 빈 `List Paragraph`)으로 카운터를 움직인다. 영어 절반에 19개가 있다. 그래서 Word 자체도 위계와 맞지 않는 번호를 보인다(예: `6.1.2.` 아래 `6.1.1.2.`). 절 위계는 번호 글자보다 스타일 수준으로 정하는 편이 안전하다.
- 내용 컨트롤은 바닥글 쪽 번호 sdt뿐이다. 녹색 안내 글은 글자 색 `189018`의 `<Template Guide>` 세 줄이다.

**General Template**: A4 가로에 본문이 빈 껍데기다. 머리글 "[Enter Document Type]", 바닥글 "CONFIDENTIAL"이고, 같은 스타일 라이브러리를 쓴다. Form·Visual Aid·Attachment 같은 다른 문서 종류용이며, 앱은 To-Be 종류로 두지 않는다(`move_external`로 충분).

## 부록 B – 회사 WI 템플릿 사실

**쪽과 구역**
- A4 세로, 여백 사방 2 cm, 머리글 1.2 cm, 바닥글 1 cm.
- 모든 표의 폭은 17 cm다. 가이드는 이 폭을 바꾸지 말라고 한다.
- 구역은 둘(연속)이다. 1 = 공통 앞장 + 한글 절반, 2 = 영어 절반 + Document Relationships.
- 본문의 **거의 모두가 표 안**이다. 실제 WI의 본문 밖 문단 수 대 칸 블록 수는 3 대 170, 3 대 334, 7 대 962였다.

**순서**
1. 제목
2. Summary of Changes 표(SOP와 같은 칸, 값 자리 `WI-#####`·`0.0`)
3. 녹색 안내 글. 쪽 나눔.
4. **Document Information**: 띠 표 + 5열 표(칸 배치는 부록 F). 쪽 나눔.
5. **Table of Contents**: 띠 표 + 표 `Language | Chapter | Description`. 국문 행(흐름도 자리 N/A, 1, 2, 3, Appendix 1), English 행, 마지막에 "Document Relationships". 쪽 나눔.
6. 한글 절반: Process Flow(띠 + 1열 표 안의 그림 캔버스, 선택), "Instruction" 띠, Chapter 표들, Appendix(한글 부록 스타일)
7. 영어 절반: 같은 구성
8. **Document Relationships**(영어만, 끝에 한 번)
   - Associated Documents: Governing SOP / Form / Quality Risk Assessment / Other Associated Documents
   - Reference Documents
   - Attachments
   - 모두 글머리 기호. 비면 지우지 말고 N/A(가이드).

**WI 가이드**
- 구조는 고정이다. 더하거나 빼지 않는다. 흐름도만 선택이다.
- 항목 제목은 영어 그대로 쓴다.
- 한글 절반 다음 영어 절반이다.
- 칸 하나에 동작 하나를 쓴다.
- 시각 자료는 세부 단계 오른쪽 열에 두고 캡션은 달지 않는다.
- 표는 세부 단계와 함께 쓴다.
- 장 전체 주의는 장 머리의 Key Point에, 단계 주의는 단계 칸에 둔다.

**Chapter 표** (격자 1.2 | 7.9 | 7.9 cm)

| 행 | 내용 |
|---|---|
| 머리 | `Chapter N. 제목`, 3칸 병합, 음영 `D9D9D9`, 굵게 가운데, 표 머리 반복(`tblHeader`) |
| Key Point | 굵은 "Key Point" 행 + 장 전체 주의 줄(선택) |
| 공정 단계 | `N.M.` 제목 행(스타일 `SBL_Process Step [Kor]`/`[Eng]`, 전체 폭, 굵게, "무엇을") |
| 세부 단계 | 라벨 칸(타자로 친 `A`, `B`, `A-1`) \| 글("어떻게") \| 그림 칸(선택) |
| 단계 안 표 | 세부 단계 칸 안의 중첩 표(머리 행 음영 `BFBFBF`) |

- 번호:
  - 공정 단계는 자동 번호다(문단 numPr ilvl=1, `%1.%2.`).
  - 장 번호는 장마다 따로 된 목록의 lvl0 **시작값**으로 넣는다. lvl0 문단은 없다.
  - "Chapter N." 글은 타자로 쳤다.
  - 실제 문서에는 타자로 친 "1.10."이 섞이고, 숨긴 빈 lvl0 문단으로 장을 넘기기도 한다(P-NUM2).
- 라벨 칸은 세로 병합으로 글 행과 그림 행·중첩 표 행을 묶는다. 같은 라벨이 여러 행에 반복되기도 한다.
- 아이콘은 0.4 × 0.4 cm 인라인 그림 셋이다. `w:drawing`과 VML `v:imagedata` 두 방식으로 들어온다.
  - "!": Quality/Process Precaution
  - "⚠": Safety
  - "?": Why(가이드 이름 "Purpose/Reason")
- 문서 안 참조는 `'<번호> <이름>'` 꼴이다. 외부 문서는 번호만 쓰고 하이퍼링크를 건다.

## 부록 C – 실사례에서 본 쓰임 (문장 인용 없음)

**사례 구성**
- 사례 1: 표형 옛 SOP 1개(한글 절반 → 영어 절반) → 새 SOP 1 + WI 3. 목적이 다른 작업 셋으로 나눴다.
- 사례 2: 조항형 옛 SOP 1개(한·영 문단 교차) → 새 SOP 1 + WI 1. WI 파일은 받지 못했다.

**옛 SOP의 앞장**
- 머리글 "Standard Operating Procedure"(가운데, 11pt 굵게). 표형은 머리글에, 조항형은 바닥글에 "CONFIDENTIAL"이 있다.
- 표지 "Summary of Changes for only current version" 표:
  - 1행: 병합 제목
  - 2행: `Document No.` | `Ver.` | `Title` 라벨(음영 `D9D9D9`, 굵게)
  - 3행: 값
  - 라벨이 값의 **위 칸**이다(P-META).
- 표형만: 문서 맨 앞에 겹줄 테두리 한 칸 띠 표(음영 `D9E2F3`)가 셋 있다. "Summary of Change (…)" 띠와 제목 띠 둘(14pt 굵게)이다.

- **앱이 막아야 할 수작업 비교표 실수 유형**(설계 가정):

  - 없는 절을 가리킴
  - 삭제 표시가 제각각
  - "1.10" 같은 번호를 숫자 칸으로 저장(프로그램이 읽으면 1.1)
- 1:N은 한 칸에 줄바꿈으로 여러 단계를 적었다. N:1은 같은 목적지를 반복했다. 같은 사유가 이어지면 칸을 병합하기도 했다.
