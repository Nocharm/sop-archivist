# 표·그림 묶음과 캡션 — 설계

- 날짜: 2026-11-16 · 기반 v1.1.3(dev)
- 위에 얹는 명세: [`2026-11-05-sop-restructuring-e2e-design.md`](2026-11-05-sop-restructuring-e2e-design.md)(이하 "제품 명세"). 여기 적지 않은 것은 제품 명세를 따른다.
- 표기: **(사용자)** = 사용자가 이 대화에서 정한 것, **(내 판단)** = 설계자가 정한 것(사용자가 읽으며 확인), 표시 없음 = 위에서 따라 나오는 설명.

## 1. 왜

Assign에서 표·그림을 어떻게 처리해야 할지 사용자가 감을 잡지 못하고, 표·그림과 캡션·본문 사이의 연결이 끊긴다(사용자). 합성 묶음 2(SOP-ABC-1016)를 실제로 띄워 확인한 현재 모습:

- 표 칸을 눌러도 아무 일도 없다. 표 전체를 고르는 입구는 표 위 글자 없는 2.5px 선뿐이고(`frontend/src/components/paper/paper.tsx` `renderTable`의 `ptbl-cap`), 골라도 Shape에 ID만 보인다.
- 그래서 이미 있는 **Treat as layout table**·**Split into rows**(표 단위 우클릭 메뉴)까지 가기가 사실상 불가능하다.
- 그림은 캡션과 한 단위라 고를 수 있지만, 골라진 테두리가 약하다.
- 표 캡션("표 1. …")은 잡지 않아 일반 문장 단위가 된다 — 표와 다른 SOP·WI로 보내도 경고가 없다.
- 표·그림을 가리키는 문장("아래 표를 따른다", "see Figure 2")은 표·그림과 이어져 있지 않다. 번호는 어디서도 다시 매기지 않는다.
- 새 문서 칸은 표·그림을 "Table"/"Figure" 글자로만, 결과물 C·Excel은 그림을 `[Figure]` 한 줄로 낸다(그림 새 문장에 글자가 없어 캡션이 사라진다, `backend/app/sop/decisions.py` `_resolve_text`). 결과물 A의 `[표 n]`은 추출 순서 번호다(`backend/app/sop/output_labels.py`).
- 좁은 Old 칸에서 열이 많은 표는 칸이 좁아져 세로로 길게 늘어난다(사용자).

## 2. 목표 · 비목표 · 실패로 보는 것

**목표**
1. 표·그림과 그 캡션을 **한 묶음**으로 다룬다. 묶음은 REF 줄처럼 종류 표시가 붙는 단위이고, 새 문서에 넣기·삭제 등이 묶음째로 된다(사용자).
2. 묶음은 **문장과 같은 로직**으로 처리한다 — 같은 Shape → Where it goes → Decide → Confirm, 같은 보낼 곳, 같은 단축키. 묶음만의 동작은 최소로(사용자: "다른 문장들 처리처럼 같은 로직, 헷갈리지 않게").
3. 묶음을 새 문서의 **문장 사이 아무 자리**에 넣을 수 있다(사용자: 템플릿의 빈 표·그림 자리 채우기보다 이것을 먼저).
4. 표는 **좌우 스크롤**로 보여 세로로 늘어나지 않는다(사용자).
5. 표 안에 쓰인 템플릿(레이아웃 표)을 **벗겨 문장 단위로** 나눌 수 있다(사용자) — 이미 있는 기능을 보이는 자리로 꺼낸다.
6. 결과물에서 표·그림 번호를 **새 문서 안 순서대로 다시 매기고**, 캡션과 본문의 "표 N 참조"도 함께 바꾼다(사용자).

**비목표**
- PDF의 표·그림·캡션 인식. PDF에는 표·캡션 구조가 없어 모양으로 짐작해야 하고 틀리기 쉽다. **Word(docx) 기준으로 작업한다**(사용자). PDF는 지금처럼 문단으로만 읽는다.
- 템플릿에 미리 놓인 빈 표·그림 자리를 채우는 흐름(사용자: 이번엔 문장 사이 넣기부터). 기존 "같은 표·그림 새 문장에 잇기"(입구 2 짝 맞추기)는 그대로 둔다.
- 레이아웃 표 자동 판별 — 제품 명세 §6.4의 결정(드물어서 제안하지 않음)을 유지한다(내 판단).
- 그림 내용 읽기·그림 변경 추적(제품 명세 §3 비목표 그대로).
- Excel 결과물에 이미지 넣기. Excel에는 캡션 글만 낸다(사용자).
- 표 캡션이 아닌 표 제목 행(표 첫 행이 제목인 경우)을 캡션으로 보는 것.

**실패로 보는 것**
- 묶음 처리가 문장 처리와 다른 규칙·단추·순서를 따로 익혀야 하는 모양이 되는 것.
- 캡션과 표·그림이 다른 곳으로 흩어질 수 있는 것.
- 번호를 다시 매기다 사람이 확정한 글을 몰래 바꾸는 것 — 바뀐 번호는 화면에서 보여야 한다.
- 극단 자료(넓은 표, 긴 캡션, 캡션 없는 표, 참조가 많은 문서)에서 Old·New 칸이 무너지는 것.

## 3. 묶음 모델

### 3.1 무엇이 묶음인가
- **표 묶음** = 데이터 표 단위(또는 행으로 나눴으면 행 단위들 — 캡션은 첫 행 묶음에 딸린다, 내 판단) + 표 캡션 0~1개.
- **그림 묶음** = 그림 단위 + 그림 캡션 0~1개.
- 레이아웃 표는 묶음이 아니다(칸 문장이 일반 문장이다). 레이아웃 표의 캡션은 일반 문장으로 돌아간다(내 판단).
- 표 칸 안의 그림은 지금처럼 캡션을 자동으로 붙이지 않는 독립 그림 단위(제품 명세 §7.2)이고 그림 묶음이 된다 — 캡션은 사람이 써 넣는다(§3.4).

### 3.2 캡션의 자리 (내 판단)
캡션은 **묶음에 딸린 글 단위**로 둔다 — 표의 칸 문장이 표 단위의 처분을 따르는 것과 같은 방식이다.
- 캡션 단위는 묶음의 처분·보낼 곳·상태를 그대로 따르고, 따로 배정할 수 없다(사용자: 캡션은 묶어서 하나로).
- 캡션 글은 칸 문장처럼 다듬기·번역·문장 검사 대상이다(내 판단). 한/영이 한 줄에 같이 있는 캡션("그림 1. 로터 장착 위치 (Figure 1. Rotor mounting position)")은 지금 문장처럼 언어 판정·짝 규칙을 따른다.
- 그러면 그림 새 문장에 글자가 없어 캡션이 결과물에서 사라지는 문제(§1)가 캡션 새 문장으로 풀린다.
- **캡션은 칸 문장과 같은 길을 따른다**(내 판단, "같은 로직"): 캡션 새 문장은 언어를 가진 일반 문장 새 문장으로 묶음 새 문장 아래에 붙는다. 한/영 결과물 판에는 칸 문장과 같은 규칙으로 나간다 — 한 언어만 있으면 "한 언어만 있는 줄"에 잡히고 번역 흐름을 탄다. 한/영이 한 줄에 같이 있는 캡션은 문장의 **KO/EN pair** 나누기와 같은 방법으로 짝 두 개로 나눌 수 있다.
- **확정은 묶음 한 번**(내 판단): Confirm·Edit and confirm·Hold·Clear는 묶음에 대해 한 번 하고, 캡션은 그 처분·상태를 따른다(칸 문장과 같음). 캡션 글 고치기는 묶음의 Edit and confirm 안에서 한다. 캡션만 따로 보류·확정하는 상태는 없다.
- **행으로 나눈 표**(내 판단): 캡션은 첫 행 묶음에 딸린다. 나머지 행은 캡션이 없는 채로 시작하는 표 묶음이고 각각 골라진다 — 새 표가 되므로 캡션을 써 넣어야 한다(§3.4). 번호를 셀 때는 새 문서 안의 표 새 문장 하나를 표 하나로 센다.
- **표 칸 안 그림**(내 판단): 그림을 누르면 그림 묶음이 골라지고(안쪽이 이김), 표 묶음과 따로 보낸다(지금과 같음).
- 지금 그림 블록의 글자가 곧 캡션인 구조(`backend/app/sop/extract/docx_reader.py`, `backend/app/sop/segment.py`)를 어떻게 옮길지(블록을 나눌지, 단위만 나눌지)와 기존 묶음 데이터의 이행(Alembic)은 빌더 재량이다. 기존 묶음에서 그림 단위의 판단·새 문장이 끊기지 않아야 한다.

### 3.3 캡션 찾기 (docx)
- 그림: 지금 규칙(캡션 스타일, 또는 `그림/Figure/Fig. n`으로 시작, 바로 뒤 → 바로 앞 문단)을 유지하고 `Fig 2`·`Fig.2`처럼 띄어쓰기·점 변형을 더 받는다(내 판단).
- 표: 같은 규칙을 `표/Table n`으로 적용한다. 표 캡션은 보통 표 **앞**에 오므로 바로 앞 → 바로 뒤 문단 순으로 본다(내 판단).
- 이웃 문단이 캡션 꼴이 아니면 캡션이 없는 채로 시작한다. 사람이 이웃 문장을 캡션으로 붙이거나 떼는 동작을 둔다(Shape 도구, 내 판단).

### 3.4 모든 표·그림에는 캡션이 있어야 한다 (사용자)
- 새 문서로 보내는(배정하는) 묶음은 캡션이 있어야 확정할 수 있다. 캡션이 없으면 **Confirm**을 흐리게 끄고 까닭을 툴팁으로 보인다 — REF 카드를 정리하기 전에 Confirm이 꺼지는 것과 같은 방식(내 판단). 삭제·이동 처분은 캡션이 없어도 된다.
- 캡션을 얻는 길: 자동으로 붙은 캡션, 이웃 문장을 캡션으로 붙이기, 또는 **캡션 써 넣기**(출처 없는 캡션 새 문장 — 묶음의 Edit and confirm 안에서, 내 판단).
- 캡션 없는 묶음 수는 위쪽 줄에 REF 확인 남은 수처럼 보이고, 누르면 다음 묶음으로 간다(내 판단).

## 4. Assign 화면

### 4.1 Old 칸의 묶음 모습
- 묶음 위에 **머리 줄**을 둔다: 종류 표시 `TABLE`/`FIGURE`(REF 표시와 같은 자리·꼴, 늘 보임) + 캡션 글(없으면 경고색 "캡션 필요"와 표 첫 행 미리보기) + 표시 ID. 용지에 앱 글자를 넣지 않던 원칙의 예외다 — 표시는 REF처럼 테두리 위 표시로 둔다(내 판단, 시안에서 확인).
- **묶음 어디를 눌러도 묶음 전체가 골라진다**(머리 줄·표 칸·그림). 글자 긁기는 지금처럼 Alt(메모리: 끌기는 상자 전체). 골라진 테두리는 문장과 같은 굵기·색.
- 표는 묶음 안에서 **좌우 스크롤**한다. 칸 글은 줄바꿈을 최소로 해서 세로로 늘어나지 않게 하되, 아주 긴 칸 글은 적당한 최대 폭에서 접는다(값은 빌더가 극단 자료로 잰다).
- 데이터 표에서 칸 하나만 다른 곳에 보내는 일은 지금처럼 없다 — 행 단위가 필요하면 **행으로 나누기**, 칸 글을 문장처럼 다뤄야 하면 **표 벗기기**.

### 4.2 오른쪽 칸 — 문장과 같은 세 단계
- **Shape**: 캡션 줄(언어 칸·글 앞부분, 문장과 같음) + 묶음 도구 — **표 벗기기**(= 지금의 Treat as layout table), **행으로 나누기**/**행 다시 합치기**, **캡션 붙이기/떼기**. 할 수 없는 도구는 두지 않고, 지금 못 하는 도구는 흐리게 + 까닭 툴팁(지금 Shape 규칙과 같음).
- **Where it goes**: 문장과 같은 목록·같은 순서. 다른 점은 후보가 종류에 맞게 걸러지는 것뿐 — 새 문서의 칸 안 문장 사이 자리(넣기), 같은 종류의 기존 새 문장(잇기), 삭제·이동.
- **Decide**: 문장과 같음(Edit and confirm·Hold·Clear·Remark·Confirm, 같은 단축키). 표 구성 변경일 때 Remark 필수는 지금 규칙 그대로.
- 우클릭 메뉴도 같은 항목을 같은 이름으로 둔다.
- 끌어 놓기: 문장을 끌어 놓을 수 있는 곳이면 묶음도 같은 방식으로 끌어 놓는다. `feat/drag-and-drop`(워크트리 `sop-archivist-dnd`) 작업과 맞물리므로 순서는 계획에서 정한다.

### 4.3 문장 사이 넣기
- 묶음을 새 문서 칸의 두 문장 사이(또는 칸 맨 앞·끝)에 넣는다 — 문장을 넣는 것과 같은 자리 고르기다.
- 지금 표·그림 새 문장이 출처 하나에서만 오는 규칙(R28, `_check_source_kinds`)은 유지한다. 넣는 위치 제약이 따로 있으면 풀어 문장과 같게 한다(빌더가 확인).
- 표를 일반 문장 새 문장에, 문장을 표·그림 새 문장에 잇는 것은 계속 막는다(내 판단).

### 4.4 New 칸의 묶음 모습
- "Table — linked by AI or marked new"/"Figure" 글자 대신 **실제 표(좌우 스크롤)·그림 이미지·캡션**을 보인다(내 판단). 이미지는 Old 칸과 같은 경로로 원본 docx에서 꺼낸다.
- 캡션에는 다시 매긴 번호를 보이고, 원문 번호와 다르면 `표 1 → 표 3`처럼 바뀐 것이 보이게 한다(내 판단).

## 5. 번호 다시 매기기와 참조 (사용자: 다시 매긴다)

- **번호 읽기**: 캡션 머리의 `표/Table/그림/Figure/Fig. n`을 묶음의 원문 번호로 읽는다.
- **참조 잡기**: 같은 원문 문서의 문장에서 `표 n`, `Table n`, `그림 n`, `Figure n`, `Fig. n`(와 그 한/영 변형)을 찾아, 같은 번호를 가진 묶음에 잇는다. 번호 없는 "아래 표/위 그림/the following table" 꼴은 **바로 뒤(또는 앞)의 묶음**에 잇는다(내 판단). 잡은 연결은 Shape에 보이고 사람이 떼거나 고칠 수 있다(내 판단).
- **다시 매기기**: 결과물을 만들 때(모든 표·그림을 센다 — 모두 캡션이 있다, §3.4), 새 문서(SOP·WI)마다 결과물 순서대로 표와 그림을 따로 1부터 센다. 캡션의 번호와, 이어진 참조 문장의 번호를 그 값으로 바꾼다. 규칙으로 하는 계산이고 AI가 아니다.
- **사람 글을 몰래 바꾸지 않는다**: 확정 글은 원문 번호 그대로 저장하고, 화면(New 칸·결과물 미리보기)과 결과물에서 바뀐 번호를 표시한다. 사람이 글을 고쳐 참조 꼴이 사라졌으면 바꾸지 않고 경고한다(내 판단).
- **바꾸는 대상**(내 판단): 새 문장의 확정 글에서, 그 새 문장의 출처 단위들이 가진 참조 연결의 원문 번호와 같은 토큰만 바꾼다. 같은 원문 번호가 서로 다른 묶음을 가리켜 어느 쪽인지 정할 수 없으면 바꾸지 않고 경고한다.
- **연결의 수명**(내 판단): 업로드(추출) 때 잡고, 단위 편집(나누기·합치기·캡션 붙이기/떼기·표 벗기기)이 그 단위를 바꾸면 번호 토큰이 든 쪽 단위로 옮긴다. 사람이 손으로 고친 연결은 다시 잡을 때 덮지 않는다.
- **경고(검토 Checks, 막지 않음 — 내 판단)**:
  - 참조 문장은 남았는데 그 묶음이 삭제됐거나 다른 새 문서로 갔다.
  - 번호 없는 참조("아래 표")의 묶음이 새 문서에서 그 문장 바로 뒤에 오지 않는다.
  - 참조가 가리키는 번호의 묶음을 원문에서 찾지 못했다.
- 한/영 결과물 두 판 모두에서 같은 번호를 쓴다.

## 6. 결과물

- **A**: `[표 n, r×c]` 대신 다시 매긴 캡션 글(`표 3. 운전 조건`)을 쓴다. 배정된 묶음은 모두 캡션이 있으므로(§3.4) 번호는 모든 표·그림을 센다.
- **C 화면·Excel**: 그림은 `[Figure]` 대신 다시 매긴 캡션 글. 표는 지금처럼 칸을 내고 캡션 줄을 표 앞에 둔다.
- 결과물 화면에서 표는 좌우 스크롤.
- 커버리지·진행 숫자: 묶음은 지금 표·그림처럼 한 줄로 센다. 캡션 단위는 따로 세지 않는다(칸 문장처럼).
